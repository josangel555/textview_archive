# Test Suite Review — TextView / MarkdownViewer

**Date:** 2026-05-25
**Scope:** Read-only review of `Tests/` (ViewerKitTests, ViewerCoreTests, ViewerUITests)
**Method:** Read every test file at least skim-deep; sample 40+ files line by line; cross-check against `Sources/` layout and `docs/UI_TEST_GAPS_2026-05-22.md`.

The aggregate test count is large and most pure-logic models are well-covered. Coverage rot lives at three boundaries:
1. **LSP runtime** (real wire path) — env-gated smoke + decode-only tests; the 1.4-KLoC `LSPClient`/`LSPPool` happy-path is effectively untested except behind `MDV_RUN_LSP_SMOKE=1`.
2. **UI dispatch chain** (NSEvent → menu → model) — explicitly deferred to VM per `UI_TEST_GAPS_2026-05-22.md` and not exercised on host. Tests at the boundary (`OpenInNewSessionTests`, `DragDropTests`) prove only that closures stored on a model invoke when called — tautological.
3. **Tab-bar / sidebar / mode-bar UI introspection** in `ComponentVisualTests` — several tests assert their *named* surface but actually only check model state, or check `descendants.count > N`, never the thing in the name.

## Section 1 — Tests that don't test what they claim ("dishonest tests")

These are the highest-priority finds. Each is named to suggest it exercises a real surface but the assertion landing inside is at a different layer (or non-existent).

### 1.1 `ComponentVisualTests.test_modeBar_filenameLabel_reflectsCurrentFile`
```swift
// (file: Tests/ViewerUITests/ComponentVisualTests.swift:109)
XCTAssertTrue(model.currentFilePath?.contains("uniquelynamed") ?? false, ...)
```
The test name asserts a UI label. The body asserts `model.currentFilePath`, which is the source of the binding. **A bug in the modeBar's text rendering would not fail this test.** The mode bar is never instantiated.

### 1.2 `ComponentVisualTests.test_tabBar_oneTab_hasOneTabItem`
```swift
// (file: ComponentVisualTests.swift:135)
XCTAssertEqual(model.tabs.tabs.count, 1)
```
Same shape — name claims tab-bar UI assertion; body asserts model state only. No `renderHost(...)` or NSView traversal. Trivially passes regardless of TabBar code.

### 1.3 `ComponentVisualTests.test_sidebar_defaultVisibility_followsPreferences`
```swift
XCTAssertEqual(model.sidebar.isVisible,
               PreferencesStore(defaults: defaults).sidebarVisible)
```
**Tautology.** LHS and RHS are constructed from the same `defaults` instance moments apart. Always true. Provides no signal about the binding being correctly wired.

### 1.4 `ComponentVisualTests.test_sidebar_visibleAfterToggle_changesViewTree`
The test name promises a before/after comparison. Body sets `isVisible = true` once and asserts `descendants.count > 10`. **No "before" snapshot, no toggle**. The threshold of 10 will pass for almost any non-trivial SwiftUI tree.

### 1.5 `InteractionScriptTests.test_newTabAndClose_changesTabCount`
```swift
if nNew == 0 && nClose == 0 { return }   // silently passes
XCTAssertGreaterThanOrEqual(nNew, nClose, ...)
```
The test acknowledges (in the comment) that SwiftUI's accessibility id often fails to propagate. When that happens, both counts are zero and the test **returns success without asserting anything**. In the common case this is a green-but-empty test. The fix is to fail explicitly when the page object can't see tabs, not to silently skip.

### 1.6 `InteractionDeepTests.test_sidebar_setRoot_andWalkUp`
```swift
XCTAssertEqual(dumps.count, 4, ...)
// Just verify no crash and all 4 dumps were produced.
```
Name claims sidebar root manipulation + walk-up. Body asserts only that the script runner produced 4 step dumps. **A regression where `sidebar-set-root` silently no-ops would still pass.** Needs an assertion on the rendered sidebar root, or at minimum on the model's `sidebar.rootURL`.

### 1.7 `InteractionDeepTests.test_palette_showAndDismiss_modelStateUpdates`
Asserts only that `totalNodeCount` shrinks then grows. **Any unrelated tree change between scenarios — a tooltip, a focus ring, a stale @State — perturbs this count.** Test will pass for "anything that adds a subview when palette opens" rather than for the palette specifically. Should be combined with a `model.isPalettePresented` probe (which is in fact tested in `test_palette_isPresented_togglesViaModel`).

### 1.8 `DragDropTests.test_drop_singleFile_opensIt`
```swift
// Comment in file: "We can't construct the View itself trivially;
//                   we replicate the handler body here."
```
The test **inlines a copy of the production drop handler** rather than invoking it. The two copies can drift independently. Any bug introduced into `ContentView.handleDrop` will not be caught. Should refactor the handler into a testable static (e.g. `DropRouter.handle(...)`) so production and test share one code path.

### 1.9 `OpenInNewSessionTests` (entire file)
The four tests verify that:
- a `var closure: ((URL) -> Void)?` defaults to nil, and
- when you assign it and call it, it gets called.

This is **a property of Swift closures**, not of the feature. The actual contract — that the right-click menu item invokes this closure when chosen — is never tested anywhere. The file's docstring is honest about this ("the rendering is a VM live-app concern"), so this is more an "expensive zero-signal test" than a defect, but the tests should be deleted or replaced with a real menu-tap probe.

### 1.10 `FileTreeRecencyConcurrencyTests.test_capBoundary_dropsCache_thenRebuilds`
```swift
XCTAssertNotNil(post.modifiedAt ?? Date())
```
`x ?? Date()` is **never nil** by construction. Always-true assertion. The intent ("doesn't crash") is captured implicitly, but the explicit assertion is a no-op.

### 1.11 `FileTreeRecencyConcurrencyTests.test_concurrentReads_*`
> "If we got here without a crash, the lock did its job."

Three of four tests in this file have **no XCTAssert** — they're crash-detector tests. That is sometimes a valid testing shape but should be documented as such and have at least one positive invariant (e.g. final cache size, distinct values returned, etc.). Right now it's `XCTAssertTrue(true)` with extra steps.

### 1.12 `LSPClientSmokeTests.test_initialize_andHover_swiftFile`
```swift
let hover = try? await client.hover(...)
_ = hover
let defs = try? await client.definition(...)
_ = defs
```
**Discards both responses.** Test passes as long as the calls don't throw. Hover/definition could return garbage, return empty, return wrong fields — silently green. Same pattern in `LSPMultiLanguageSmokeTests` (3 tests) and `LSPPoolSmokeTests` (1 test). At least one of these should assert the response structure once the test environment can be reasonably depended on.

## Section 2 — Brittle / timing-sensitive shapes

These tests will work *most* of the time but have failure modes that depend on the host clock.

### 2.1 Hard-coded sleeps with no replacement primitive

| File | Sleeps | Notes |
|---|---|---|
| `AppLauncher.swift` | 0.3s + 0.6s + 0.1s loop + 0.5s | Bake-in: ~1.5s minimum per L4/L5 test method × 18 spawning tests ≈ 27 s of pure sleep |
| `SourceViewVisualRegressionTests` | 1.5s + 1.5s + 0.2s + 0.1s loop | App-foreground race; sleeps because there's no API for "WindowServer composited frame ready" |
| `EditorFlowIntegrationTests` | 0.05s settling | One spot, low-risk |
| `FileWatcherIntegrationTests` | 200 ms + 200 ms + poll 100 ms | Real FSEvents — unavoidable; reasonable |
| `CrossSearchIntegrationTests.test_runCrossSearch_withoutFolder_returnsNothing` | 200 ms | Asserts empty result after a fixed sleep. No actual wait for completion — if the search ever takes >200 ms to produce its initial empty publish, the test silently passes from a stale snapshot |
| `SidebarModelTests.test_refreshGitStatus_outsideRepo_clearsMap` | 100 ms | Asserts a freshly-constructed map is still empty. The model starts empty; the assertion would pass with `sleep 0`. Tests nothing meaningful |
| `DocumentModelTests.test_selectTab_rotatesFileWatcher` | 0.2 s | After mutating `a` while `b` selected, asserts `b` unchanged. If the watcher fires after 200 ms (slow CI / VM), the bug would slip through |

**Pattern fix:** every "fire then assert no effect" test should poll for an explicit deadline with `XCTAssertFalse(predicate)` checked at multiple sample points, not rely on a single sleep. The existing `waitFor(timeout:until:)` helper in `CrossSearchIntegrationTests` and `DocumentModelTests` is correctly shaped — port the pattern over.

### 2.2 `FolderWatcherTests.test_burst_coalesces`
Asserts `XCTAssertLessThanOrEqual(counter.value, 3, ...)`. The "≤3" threshold is a contract guess. On a slow VM where FSEvents bursts arrive in a different cadence, this can spuriously fail. Stronger: assert `counter.value ≥ 1 && counter.value < 50` (we got coalescing of some kind) plus a separate, deterministic test against a mocked debouncer.

### 2.3 `LongFlowTests.test_dayInTheLife_15Interactions_noBrokenStates`
- Test name says "15" but expects 16 dumps.
- Asserts only "title non-empty" + "zoom in (0, 100)" — bounds so loose that virtually any bug leaving the model alive passes.
- The expensive 16-step app spawn is largely a smoke test masquerading as integration coverage.

### 2.4 `LongFlowTests.test_tabChurnAndZoomPersistence` "primer" scenario
The test relies on PreferencesStore state being shared across scenario re-launches in the same test method. Each scenario starts a fresh `.app` process; preferences persist via `defaults` *only* if the same defaults domain is reused. Check `LaunchHarness` — if it gives each scenario a fresh domain (which is the safe default), this test passes by accident.
The pattern of using one scenario to "prime" another and a third to "cleanup" is fragile — scenarios should be self-contained.

## Section 3 — State leakage / hermeticity issues

### 3.1 `FileTreeRecencyTests.testAppStorageKeyRoundTripPersistsMode`
```swift
let key = "MarkdownViewer.sidebar.recencyMode.test"
let defaults = UserDefaults.standard
defer { defaults.removeObject(forKey: key) }
```
**Only test in the suite touching `UserDefaults.standard`.** Cleanup happens in `defer`, but if the test process crashes mid-test the key persists to the developer's machine. Should use a per-test suite-name `UserDefaults(suiteName:)` like every other test. The `test.` suffix in the key partially mitigates collision risk but doesn't justify touching standard defaults.

### 3.2 `PluginGrantStoreTests` — inconsistent cleanup
`test_status_required_for_unseen_plugin` calls `tempFile()` and never removes the file. Other tests in the same class use `defer { try? remove }`. Each run leaks one `MDVGrants-<uuid>.json` under `/var/folders/.../T/`. Move the cleanup into a `setUp/tearDown` pair.

### 3.3 `SessionStateTests` — no tearDown
Class uses `lazy var tmpDir` but no `tearDown`. Every test run leaves a `SessionStateTests-<uuid>` directory under `temporaryDirectory`. macOS eventually GCs this, but tests should clean up after themselves.

### 3.4 `FileTreeRecencyConcurrencyTests`
Uses `FileTreeRecencyCache` (a global singleton) and calls `invalidateAll()` in setUp/tearDown — correct hygiene. But the same singleton is also used by `FileTreeRecencyTests.testCachePopulatesAndInvalidates`. If both classes ran in parallel (`-parallel-testing-enabled`), they'd race. SwiftPM defaults to serial within a target, so currently safe — but flag the latent dependency.

### 3.5 Shared global state in `AppLauncher`
The launcher (a) writes `mdv-step-NN.json` files into the per-user tmpdir with no UUID isolation, (b) calls `killall MarkdownViewer` unconditionally. If a developer is running the app while tests run, the tests kill their session and may collide with prior step dumps. The cleanup loop `for n in 1...99 { remove json/png }` runs at the *start* of each `runScript` but only for the fixed name pattern. Adding a per-run UUID prefix would fix both.

## Section 4 — Over-coverage / suspected redundancy

### 4.1 SessionStore vs SessionTabPersistenceRestart vs SessionsMigration
Three test files exercise overlapping persistence + migration paths:
- `SessionStoreTests.swift` (15 tests, 293 LOC) — store-level CRUD + coalescer + trash + migration
- `SessionTabPersistenceRestartTests.swift` (9 tests, 266 LOC) — store-level CRUD + trash + migration
- `SessionsMigrationTests.swift` (4 tests) — migration

Specifically:
- `SessionStoreTests.testMoveToTrash*` (3 tests) ≈ `SessionTabPersistenceRestartTests.test_moveToTrash*` (2 tests).
- `SessionStoreTests.testMigrateLegacy*` ≈ `SessionTabPersistenceRestartTests.test_legacyMigration_*` ≈ `SessionsMigrationTests.testLegacyFixtureLiftsIntoSessionStore`.

Roughly 5–7 tests look like duplicates of work already done in `SessionStoreTests`. Worth consolidating.

### 4.2 Zoom-persistence trio (already flagged by `TESTS_AUDIT.md`)
Three app-spawning tests do the same zoom-persists check (`InteractionDeepTests`, `LongFlowTests`, `ScenarioTests`). At ~3 s per app spawn this is ~9 s of duplicated wall-clock.

### 4.3 Tab-open coverage spans 5 files
`InteractionDeep`, `InteractionScript`, `LongFlow`, `Scenario`, `DocumentModel`. `TESTS_AUDIT.md` already documents this — same conclusion.

### 4.4 Rendered/Source toggle: 2 app-spawn tests doing the same toggle
`InteractionScriptTests.test_toggleView_swapsRenderedAndSourceViews` and `ScenarioTests.test_tabAndModeScenarios` (sub-scenario "rendered-source-roundtrip-keeps-content"). Drop one.

### 4.5 Decode-shape LSP tests
`LSPProtocolDecodeTests` (9), `LSPDocumentSymbolDecodeTests` (6), `LSPWorkspaceSymbolDecodeTests` (9) — each tests a different LSP request type's JSON shape. These are individually small but together cover only **decoding** — there's no parallel "encode" test for any of these. Asymmetric: decode is rigorously tested, encode (which we send to the server and is harder to spot bugs in) is not.

## Section 5 — Coverage gaps in production code

`UI_TEST_GAPS_2026-05-22.md` is exhaustive on **UI** gaps. The complementary gaps in **non-UI / model code** worth flagging:

### 5.1 `LSPClient.swift` — 821 LOC, no host-runnable tests
The largest source file in the LSP area has zero test coverage of:
- The framing layer (covered by `LSPFramingTests`, ✓)
- The request/response correlation table
- The cancellation flow (`LSPCancellationTokenTests` covers the token, not the wire integration)
- Server crash + restart
- Garbled response handling
- Timeout enforcement

Only `LSPClientSmokeTests` exercises it, and that's `MDV_RUN_LSP_SMOKE=1`-gated (i.e. skipped in CI). A `FakeLSPServer` actor would let several scenarios run on host without spawning `sourcekit-lsp` — high-leverage addition.

### 5.2 `LSPPool.swift` — 589 LOC, error-path-only coverage
`LSPPoolTests` tests "binary not found" branches via `makeRegistryThatNeverSpawns()`. The happy paths (server starts, multiple sessions pool correctly, dead-cooldown recovery) are not tested. Same fix as above — a fake launcher that returns a deterministic in-process server.

### 5.3 No `DocumentModel.openInSplit` test
The split-pane open path is wired through `model.openInSplit` (referenced in `UI_TEST_GAPS_2026-05-22.md`) but I don't see a corresponding test in `DocumentModelTests`. Worth a unit test that asserts the split URL is stashed and the model publishes the change.

### 5.4 No tests for `Sources/MarkdownViewer/main.swift`
Entrypoint logic (`MDV_BACKGROUND=1`, `MDV_SKIP_WORKSPACE_RESTORE=1`, `--script` arg parsing, windowID-file write) has no direct test. Tested only indirectly through `AppLauncher`-spawned scenarios. Some of this is now load-bearing for the test harness itself — if it regresses, every L4/L5 test goes silent. A small `mainArgs(_ argv:)` extractor + unit test would isolate.

### 5.5 No filesystem-walker timeout test
`CrossFileSearch`, `FileTreeService`, `FolderWatcher` — none have a test that confirms they bail on a pathological directory (symlink loop, very deep tree, huge file count). On a developer's home dir, accidentally scanning `~/Library` could hang the app. This is the "didn't bother to test the bad path" gap.

### 5.6 `PluginSubprocessHost.test_env_is_scrubbed_only_HOME_passes` is asymmetric
Tests "PATH/USER/LANG/TMPDIR not set" — but the prod scrubber may pass *other* env vars (HOMEBREW_PREFIX, SHELL, …). Test should iterate every key in `ProcessInfo.processInfo.environment` and assert the scrubbed result is a strict subset of `{HOME}`. As written, a new env-passthrough leak would not regress the test.

## Section 6 — Test-tier asymmetry

`UI_TEST_GAPS_2026-05-22.md` characterises the test pyramid well. From the host side I see the same shape plus these specifics:

| Layer | Strength | Notes |
|---|---|---|
| L1 (pure data / decode / math) | **Strong** | CMBridge V1/V2, TabsState, FuzzyMatcher, FoldRegion, CSV/SQLite parsers, Walkthrough decoder, MCP — all rigorously covered. |
| L2 (services hitting FS / git) | **Strong** | FileWatcher, FolderWatcher, GitClient, BookmarksStore, SessionStore, PluginGrantStore — all use per-test tmpdirs and assert on side-effects. |
| L3 (host-actor models) | **Strong** | DocumentModel, SidebarModel — 42 + 18 tests; both files set up suite-name UserDefaults correctly. |
| L4 (in-process SwiftUI host) | **Mixed** | ComponentVisualTests has several dishonest assertions (§1). Other in-process tests are honest. |
| L5 (app spawn + script) | **Mixed** | InteractionScript / InteractionDeep / Scenario / LongFlow are slow (≈ 3 s each) and several have weak or no real assertions; the value-per-second ratio is low. The dedicated visual-regression test is genuinely unique. |
| VM-only UI dispatch (NSEvent → menu) | **Absent** | Documented gap; no live-key tests in `Tests/`. |

## Section 7 — Suggested re-investment (ranked)

If you have 8 hours of testing work to spend, here's where I'd spend them:

1. **Build a `FakeLSPServer` actor** (~2 h) and write 10 happy-path tests against `LSPClient` + `LSPPool` — the two biggest uncovered prod files (1.4 KLoC combined). Single biggest signal-per-hour move on the list.
2. **Fix the dishonest UI assertions (§1.1–1.7, 1.10–1.11)** (~1 h). Either delete the misleading test or wire it through to assert what its name claims. Tests with no real assertion erode trust.
3. **Refactor the drop handler** (~30 min) so `DragDropTests` exercises production code, not its twin (§1.8).
4. **Replace `Thread.sleep` with `waitFor`-style polling** in `CrossSearchIntegrationTests`, `SidebarModelTests`, `DocumentModelTests.test_selectTab_rotatesFileWatcher` (~1 h). Removes ~30 s of dead time from the suite and converts flake-prone tests into deterministic ones.
5. **Consolidate Sessions persistence/migration tests** (~1 h). Merge the moveToTrash + legacy-migration overlap between `SessionStoreTests`, `SessionTabPersistenceRestartTests`, and `SessionsMigrationTests`. Delete ~5 duplicates.
6. **Apply `TESTS_AUDIT.md` recommendations** (~1 h). Save ~25 s of suite wall-clock by deleting strictly-weaker app-spawn tests already enumerated there.
7. **Add LSP encode-side tests** (~1 h) to mirror the existing decode-side coverage. Currently only decode is asserted; outbound encoding is invisible.
8. **Add filesystem-walker bail tests** (~30 min) for `CrossFileSearch` / `FileTreeService` — symlink loop, max-depth, max-file-count. Defensive.

## Section 8 — Things to NOT touch

These are doing genuinely useful work — don't let any refactor sweep them up:

- `SessionStoreTests.swift` — exemplary: per-test tmpdir, `flushSync` in teardown, future-schema refusal tests, coalescer semantics with the "last value wins" check rather than just "some value wrote."
- `FileWatcherTests.swift` — careful use of `expectation` + `assertForOverFulfill = false` + injectable `reattachDelay` + concrete coverage of atomic-rename / delete-then-recreate / hard-stop. Sleeps are present but justified and bounded.
- `PluginSubprocessHostTests.swift` — real subprocess boundaries (timeout, stderr tail, stdout cap, audit log, env scrub). Production-grade.
- `SourceViewVisualRegressionTests.swift` — uniquely catches the SwiftUI compositor regression (LESSONS.md). The XCTSkip-on-TCC handling is appropriate.
- `CMBridgeV1Tests` + `CMBridgeV2Tests` + `CMV2IntegrationTests` — thorough envelope-rule coverage with a clear story across the three files (decoder shape, length-mismatch detection, paste-over-selection round-trip).
- `WalkthroughAnchorKeyTests.swift` — well-targeted reducer tests with explicit "zero-rect must return nil" guard for the SwiftUI PreferenceKey race (matches commit `e7d3517`).
