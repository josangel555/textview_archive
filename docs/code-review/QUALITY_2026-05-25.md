# TextView / MarkdownViewer — Quality Review (2026-05-25)

Read-only review focused on **code quality**: architecture, modularity,
abstractions, duplication, dead code, leaky boundaries, fragile
patterns, refactor-ripe seams. Scope: 164 Swift files, ~38.9k LOC
across 4 packages. Bug, security, perf are out-of-scope (covered by
`CODE_REVIEW.md` round-2 + sibling agents).

Severity rubric: **H** (load-bearing — pay this down or it gets worse
fast) · **M** (real friction, contain it) · **L** (nit). Confidence:
**high** (read the code), **medium** (pattern inference), **low**
(guess from one or two call sites).

---

## Headline assessment

This is a fast-growing codebase with a *strong pure-logic core* and a
*concentrated UI-shell debt*. The four-package split
(`ViewerKit` → `ViewerCore` → `ViewerUI` → `MarkdownViewer`) is real
and mostly respected; `ViewerCore` could be lifted into a separate
repo with minor work. The problem is on the UI side: ~37% of total
LOC lives in two files (`DocumentModel.swift` 2377 + `main.swift`
1882 + `TextDisplayView.swift` 1108 = 5367 LOC, ~14% of the codebase
in three god-files). Several feature seams that look orthogonal in
the design docs (Sessions vs Workspace, GitClient vs GitService,
WalkthroughDropTransport vs FolderWatcher) have not yet been merged
or retired post-feature-landing — classic parallel-agent drift.

Healthy areas: `TabsState`, `FileWatcher`, `HistoryStore`,
`BookmarksStore`, `JSONFileStore`, `TreeSitterEngine`, `LSPClient`,
`PluginSubprocessHost`, the markdown safety story
(`HTMLRenderer.safeURL` + CSP).

Top three things to actually pay down, in order:

1. **Decompose `DocumentModel`** — it owns 71 `@Published` properties
   and 107 public methods across 12+ distinct domains. Cut into
   child `ObservableObject`s by domain (Find, CrossSearch, Editor,
   LSPBridge, Workspace, Bookmarks, …). Today every keystroke
   into the cross-search field forces every TabBar row to re-evaluate
   because they all observe the same model.
2. **Collapse the two git layers.** `ViewerCore/GitService.swift`
   (190 LOC, used only by `SidebarModel` for status) and
   `ViewerCore/Git/GitClient.swift` (468 LOC, used everywhere else)
   duplicate the protective-flags table, the subprocess+pipe drain
   pattern, and the repo-root discovery walk. Keep one.
3. **Retire the `WorkspaceSnapshot` / `WorkspaceStore` layer** now
   that Sessions supersedes it. `WorkspaceStore` is still wired
   live in `DocumentModel.saveWorkspaceAutoSlot` /
   `restoreWorkspaceAutoSlot` (`DocumentModel.swift:1658`,
   `:1677`), but those calls are dead under Sessions and the
   migration bridge already lives in
   `Sessions/SessionState.swift:168`. Drop the orphan path.

## Architecture & module boundaries

### What works (no action)

- **Layering is honored.** `ViewerKit` (433 LOC) is pure data;
  `ViewerCore` (~14.5k LOC) has zero AppKit / SwiftUI imports;
  `ViewerUI` (~14.3k LOC) owns the AppKit glue. `MarkdownViewer`
  (the app target) is a single `main.swift` plus `@main` wiring —
  the right shape. Tested with `grep import AppKit`: zero hits in
  `ViewerCore`.
- **`TabsState` is a textbook value type** with thorough mutating
  methods and round-trip-tested semantics. Re-read
  `Sources/ViewerCore/TabsState.swift:43-77` — `close(at:)` and
  `move(from:to:)` are the kind of crystalline logic the rest of
  the codebase should aspire to.
- **`JSONFileStore` (76 LOC)** is the right abstraction for
  HistoryStore / BookmarksStore / WorkspaceStore / SessionStore —
  one encoder config, one max-size guard, one atomic write. Used
  consistently.
- **Plugin layering.** `PluginRegistry` + `PluginSubprocessHost` +
  `PluginGrantStore` is a clean tri-split (lifecycle vs IPC vs
  trust). The Tier 0/A/B taxonomy is well-codified in
  `PluginRegistry.swift:23-40`.
- **`HTMLRenderer.safeURL`** is a tight scheme allowlist with
  per-context (link vs image) policy. Defense-in-depth alongside
  the CSP and the navigation delegate.

### `DocumentModel` is a god object — **H, high confidence**

`Sources/ViewerUI/DocumentModel.swift` — 2377 LOC, **71 `@Published`
properties, 107 public methods**, plus two extension files
(`DocumentModel+Walkthrough.swift`, `DocumentModel+AutomationHost.swift`).
It owns, at minimum:

| Domain | Properties / methods | Lines |
|---|---|---|
| Tabs + selection | `tabs`, `openTabURLs`, `materializeTasks`, openX/closeX/moveX | ~400 |
| Bookmarks | `bookmarks`, `bookmarkedLinesCache`, toggle/remove/clear, line variants | ~120 |
| CSV filter | `csvFilterStates` per-tab map + getters/setters | ~30 |
| HEX width | `hexBytesPerRow` per-tab map | ~25 |
| Rendered find | `isRenderedFindBarPresented`, query, case, next/prev nonce, summary | ~50 |
| Source find | `isSourceFindBarPresented`, query, regex, match-set, minimap lines | ~80 |
| Editor (CM6) find | `isEditorFindBarPresented`, query, regex, nonces, summary | ~60 |
| Cross-file search | `crossSearchQuery`, results, generation counter, preset scope | ~80 |
| Editor mode (CM6) | `editorBuffers`, cursor/scroll by tab, pending diagnostics | ~150 |
| LSP bridge | `lspPool`, `lspDiagnostics`, `lspNavigation`, hover/def/menu | ~250 |
| Git diff marks | `sourceDiffMarks`, `diffMarksTask`, refresh | ~50 |
| Formatter / language | `formattedTabIDs`, `formattedTextCache`, `languageOverrides` | ~80 |
| Highlight cache | `highlightCache`, `highlightInFlight`, pruning | ~80 |
| Rendered HTML cache | `renderedHTMLCache`, FNV-1a, pruning | ~50 |
| Split view | `splitURL`, open/close/swap | ~30 |
| Workspace (legacy) | save/restoreWorkspaceAutoSlot | ~50 |
| Theme | `themeOverride`, `activeTheme` | ~10 |
| Go-to-path | `isGoToPathPresented`, `lastGoToError`, commit | ~60 |
| Sessions hook | `openFolderInNewSession` callback | ~10 |
| Go-to-line / scroll | `sourceScrollLineTarget`, nonce, scroll method | ~20 |
| Git panel | `gitPanelFocusRequest`, `gitPanelDesiredTab` | ~25 |
| Show-git-log | builds markdown, writes cache file, opens tab | ~70 |

Concrete consequences of letting this grow:

- **SwiftUI republish blast radius.** `@ObservedObject var model:
  DocumentModel` is held by `ContentView`, `TabBar`, `Sidebar`,
  `StatusBar`, `ModeBar`, every find bar, the palette, the cross-
  search panel, every per-tab content view, and the gutter. Bumping
  *any* of 71 published fields fires `objectWillChange` and forces
  every observer to re-evaluate. The codebase has bolted on
  dedupe-before-publish in roughly a dozen setters (the inline
  pattern is `if x != newX { x = newX }`) but the only durable fix
  is to split observers by domain. The current dedupe pattern is
  fragile — e.g. `setSourceFindMatchSummary`,
  `setRenderedFindMatchSummary`, `setEditorFindMatchSummary` are
  three nearly-identical methods that exist solely because
  `@Published` is value-blind.
- **Test friction.** 16 test files define their own `makeModel()`
  helper (`grep -rn "func makeModel" Tests | wc -l` = 16). The
  helper is duplicated because the constructor surface is large
  (controller, history, goToPathHistory, bookmarks, sidebar,
  preferences) and each test wants a freshly-isolated set of stores.
  A single `DocumentModel.ephemeral()` factory in a shared test
  support module would eliminate the duplication and is already
  called out in `CODE_REVIEW.md` item 36.
- **Cyclical "publish loop" risk.** Long-form lesson lives at
  `TextDisplayView.swift:266-272`: the find-summary callback fires
  on every `apply()`, the model republishes via `@Published` (value-
  blind), SwiftUI re-renders, `apply()` runs again. The fix is a
  per-callback `lastFindSummary` cache. This shape will reappear
  every time someone adds a new `@Published` setter on
  `DocumentModel` that's mutated from a view callback. Splitting
  the model removes the class of bug at its root.

**Suggested refactor** (incremental, not a rewrite):

```
DocumentModel
 ├── TabsCoordinator          (tabs, selection, materialize, viewMode)
 ├── FindCoordinator          (rendered + source + editor find)
 ├── CrossSearchCoordinator   (query, results, generation, preset scope)
 ├── EditorCoordinator        (editorBuffers, diagnostics, CM6 bridges)
 ├── LSPCoordinator           (pool, diagnostics, nav, hover/def routing)
 ├── HighlightCache           (already a struct value; pull out the cache)
 ├── RenderedHTMLCache        (same)
 └── WorkspaceCoordinator     (Sessions glue; retire WorkspaceStore)
```

Each becomes a child `ObservableObject` published on the parent.
SwiftUI re-renders only the slice that actually changed. Could be
done one coordinator per PR; the `Tab`-id-keyed maps
(`csvFilterStates`, `hexBytesPerRow`, `formattedTextCache`,
`languageOverrides`, `editorBuffers`, `editorCursorByTab`,
`editorScrollByTab`, `pendingEditorDiagnostics`) follow a single
pattern that begs for a `TabKeyedStore<T>` generic.

### `main.swift` is doing too much — **M, high confidence**

`Sources/MarkdownViewer/main.swift` (1882 LOC) holds:

- `AppDelegate` (menu, services, drag, lifecycle) — fine.
- **`runScript` interpreter** (lines 308-443) — 40-verb match
  statement that's grown into a parallel command dispatcher for VM
  tests. Belongs in its own file (`Sources/MarkdownViewer/
  ScriptRunner.swift`) — the `case` arms reach all the way into
  `sessions.openFolder` and reproduce model API surface by hand.
- **`captureStepArtifacts` + `scheduleAutoSnapshot` +
  `installDiagnosticSignalHandler` + `runDiagnoseAndExit`**
  (lines 445-616) — diagnostic dump plumbing. Already paired with
  `DiagnosticDump.swift` in ViewerUI; would slot naturally next to
  it (or as `MarkdownViewer/Diagnostics.swift`).
- **`startMCPServer`** in an extension at line 1814 — fine as-is,
  but the entire MCP-stdio dispatch should be a top-level
  `MCPMode.run()` if/when the host mode grows further.
- **`buildMenu` is 450 lines** (lines 980-1429) building NSMenuItems
  one at a time. A small DSL (`item("Save", #selector(...),
  key: "s", modifiers: [])`) would cut it by 3-4×. Lower-priority
  than the script extraction; aesthetic.

### Two git layers — **H, high confidence**

`Sources/ViewerCore/GitService.swift` and
`Sources/ViewerCore/Git/GitClient.swift` are nearly disjoint islands:

| Concern | `GitService` | `GitClient` |
|---|---|---|
| Public type | `GitStatusEntry` (typed `.modified` etc.) | `StatusEntry` (raw chars) |
| Repo-root walk | `repoRoot(for:)` | `discoverRoot(from:)` |
| Protective `-c` flags | `protectiveFlags` (`GitService.swift:79`) | `protectiveFlags` (`GitClient.swift:396`) — byte-identical |
| Subprocess drain | `_DataBox` + concurrent reads | local `Data` + concurrent reads |
| Caller | `SidebarModel` for status | `DocumentModel` diff, log, panel everything else |

Net: the same critical-path flags table is defined twice; if
someone adds `-c core.attributesFile=/dev/null` they'll add it to
one and not the other. The fact that `GitClient.swift:394` cross-
references `GitService.protectiveFlags` in a comment suggests the
author noticed but never closed the gap.

**Fix shape:** merge into `GitClient`; `SidebarModel` switches its
status call to `GitClient.status()`. The `GitStatusEntry.Status`
enum (`.modified`, `.added`, …) can be lifted into `GitClient` so
the typed parse stays.

### Workspace vs Sessions — **M, high confidence**

`Sources/ViewerCore/Workspace/WorkspaceStore.swift` (145 LOC) is
clearly pre-Sessions plumbing. `SessionSnapshot` now carries every
field `WorkspaceSnapshot` does plus more, and
`SessionState.swift:140-188` already implements the migration bridge.
But `DocumentModel.saveWorkspaceAutoSlot()` and
`restoreWorkspaceAutoSlot()` (`DocumentModel.swift:1658-1708`) still
exist and still get called somewhere (need to confirm — search
suggests they're orphaned). Either:

- The methods are dead — delete them and `WorkspaceStore` together.
- They're a fallback path — document that explicitly at the call
  site and add a `// TODO(sessions): remove after Phase 2` marker.

Either way, the duplication of `openTabs: [TabSnapshot]` /
`sidebarRootPath: String?` / `themeOverride: String?` between
`WorkspaceSnapshot` and `SessionSnapshot` is real surface area.

### Subprocess pattern lives in 5 places — **M, high confidence**

Same "spawn `Process`, drain stdout+stderr concurrently with a
`DispatchGroup` (avoid the 64 KB pipe-buffer deadlock), timeout"
recipe in:

- `Sources/ViewerCore/Git/GitClient.swift:405-468`
- `Sources/ViewerCore/GitService.swift:97-142`
- `Sources/ViewerCore/JQRunner.swift:48-118`
- `Sources/ViewerCore/Plugins/PluginSubprocessHost.swift:121-300`
- `Sources/ViewerCore/LSP/LSPDiscovery.swift:285+`

Each has a different `_DataBox` / `_Box` / `LockedBuffer` shim around
the same problem. A pure-logic `Subprocess.run(executable:args:
stdin:env:timeout:cwd:)` in ViewerCore would shave 200+ LOC and
ensure the pipe-deadlock fix lives in one place. The protective-
flags / env-scrub policies stay caller-side (they're per-tool).

### FSEvents pattern lives in 2 places — **L, medium confidence**

`FolderWatcher` (sidebar tree) and `WalkthroughDropTransport` (drop
inbox) both use FSEvents with the same retain/release C-callback
shim and the same debounce-then-deliver pattern. The header comment
on `WalkthroughDropTransport.swift:16` explicitly says "we do not
share the watcher type because the responsibilities diverge" —
that's a real call, the responsibilities *do* differ (cache
invalidation vs script ingestion). But the retain/release C
plumbing (`FolderWatcher.swift:84-117`) is mechanical and worth
extracting to an `FSEventsStream` value-type wrapper. Lower
priority.

## Concrete leaky boundaries / fragile patterns

### `WeakModelBox` smuggles `DocumentModel` across actor boundaries — **M, medium**

`DocumentModel.swift:2363`:

```swift
private struct WeakModelBox: @unchecked Sendable {
    weak var value: DocumentModel?
    init(_ v: DocumentModel) { self.value = v }
}
```

Used once, at line 183, to capture `self` weakly in a non-isolated
closure that hops back to MainActor before deref. The pattern works
but the `@unchecked Sendable` is the canary: Swift 6 strict-
concurrency can't see the hop. If a future caller drops the
`MainActor.run` and dereferences directly, the type system won't
catch it. Two ways out:

- Make `LSPPool.setOnDiagnostics`'s closure `@MainActor` so the
  weakness can live on the model itself (preferred).
- If the closure must stay nonisolated, document the contract in
  the box's doc-comment with a "callers MUST hop to MainActor
  before deref" line and assert it in debug builds.

### `EditorMenuTarget` lifetime managed via side-dict — **L, medium**

`DocumentModel.swift:1227`:

```swift
private var editorMenuTargets: [ObjectIdentifier: EditorMenuTarget] = [:]
```

`NSMenu.popUp` doesn't retain `target`, so the closure-backed shim
would deallocate before the user clicks. The fix is correct but
the dict grows monotonically — each right-click adds an entry,
nothing removes them. In practice the dict tops out at a few entries
(menus are short-lived and the keys are reused), but a long session
of right-clicks accumulates. Either:

- Clear the dict in `menuDidClose` (NSMenuDelegate hook), or
- Wrap the target lifetime in `objc_setAssociatedObject` on the
  menu item itself (the comment at `:1188` already mentions this
  pattern but it wasn't used).

### `LineNumberRulerView.swift` is dead code (kept as toggle) — **L, high**

`Sources/ViewerUI/LineNumberRulerView.swift` is referenced only by
the `MDV_ENABLE_BROKEN_RULER=1` diagnostic toggle at
`TextDisplayView.swift:357`. The class exists to document a
regression test surface, not to ship. Either:

- Annotate `#if DEBUG` so it doesn't ship in release builds.
- Move into `Tests/Fixtures/` (it's regression-test scaffolding).
- Delete and let the failing-pattern doc live as a comment.

`CODE_REVIEW.md` item 34 already flagged this. Still there.

### `MarkdownStylesheet.load()` is `cached` with a different name — **L, high**

`Sources/ViewerUI/MarkdownRenderedView.swift:453`:

```swift
public static func load() -> String { cached }
```

Documented as "tests use it, production uses `cached`" — but the
test wouldn't be exercising any code different from production.
Delete `load()`, point the one caller (`ContentView.init`) at
`cached`. `CODE_REVIEW.md` item 38 already flagged this. Still
there.

### `NSSelectorFromString("openDocument:")` in `ContentView` — **L, high**

`Sources/ViewerUI/ContentView.swift:746,750` uses string-literal
selectors to invoke the app's open-file action. `CODE_REVIEW.md`
item 35 flagged this; not yet fixed. Brittle to method renames
that `grep` won't catch. Hoist to `DocumentModel.openFromMenu()`
methods or pass an `@EnvironmentObject` action sink.

### `NSColor: @retroactive @unchecked Sendable {}` — **L, medium**

`Sources/ViewerCore/Highlight/SyntaxTheme.swift:114` retroactively
makes `NSColor` Sendable. Bridges a real impedance mismatch (themes
live in ViewerCore but `NSColor` is AppKit), and is module-scoped
to the file. But: if the theme types are crossing actor boundaries,
the right move is to define an abstract `ThemeColor` type in
`ViewerKit` (no NSColor) and convert to `NSColor` only at the view
boundary — exactly what `DESIGN.md §11` already specifies as the
ideal architecture. The current shortcut violates the design
contract its own design doc lays out.

### Three coexisting "find" implementations — **M, high**

`DocumentModel` has parallel state for three find modes:

| Mode | `is...Presented` | `...FindQuery` | `...FindNextRequest` | `...FindMatchSummary` |
|---|---|---|---|---|
| Rendered (WKWebView) | `isRenderedFindBarPresented` | `renderedFindQuery` | `renderedFindNextRequest` | `renderedFindMatchSummary` |
| Source (NSTextView) | `isSourceFindBarPresented` | `sourceFindQuery` | `sourceFindNextRequest` | `sourceFindMatchSummary` |
| Editor (CM6) | `isEditorFindBarPresented` | `editorFindQuery` | `editorFindNextRequest` | `editorFindMatchSummary` |

15 published fields where one `FindState` value would do, plus three
near-identical `set...FindMatchSummary` methods. The cleanest
extraction is a `FindStateBag` enum (`.rendered(State)`,
`.source(State)`, `.editor(State)`) on a `FindCoordinator` child
object. `Cmd+F` routing already lives in `main.swift:1714` —
that's the natural seam.

### "Nonce" pattern is load-bearing and undocumented — **L, medium**

The codebase uses a `Published var nonce: Int` + `&+= 1` idiom in
~15 places to force SwiftUI's value-blind dedupe to re-fire:
`renderedFindNextRequest`, `renderedFindFocusRequest`,
`sourceFindNextRequest`, `sourceFindPrevRequest`,
`sourceFindFocusRequest`, `sourceScrollLineNonce`,
`editorFindNextRequest`, `editorFindPrevRequest`,
`editorFindFocusRequest`, `gitPanelFocusRequest`. Each is a separate
ad-hoc one-liner. Three options:

- Document as a project convention with one comment in
  `HACKABILITY.md` (cheapest).
- Wrap in a `RequestNonce` struct so the intent is type-visible:
  `@Published var findNext: RequestNonce = .initial`.
- Use a Combine `PassthroughSubject<Void, Never>` per command —
  semantically correct ("this is a signal, not a value") and
  republish-safe.

### Caches with hand-rolled "drop 1/3 when full" — **L, high**

Three caches on `DocumentModel` (`highlightCache`,
`renderedHTMLCache`, `formattedTextCache`) and one on
`TreeSitterEngine` (the fold cache) all implement the same pattern:

```swift
if cache.count > maxN {
    let dropCount = cache.count - maxN * 2 / 3
    for k in cache.keys.prefix(dropCount) { cache.removeValue(forKey: k) }
}
```

`Dictionary.keys.prefix(n)` is *not* insertion-order on Swift's
hashed `Dictionary` — it's iteration order, which is hash-bucket
order plus seed randomization. So you're dropping arbitrary entries,
NOT oldest. Comments at `DocumentModel.swift:1512-1514` and
`:1602-1604` acknowledge "arbitrary drop", but it's worth either:

- Lifting to a tiny `LRUCache<Key, Value>` with explicit insertion
  order (NSMutableOrderedSet under the hood, or a doubly-linked
  list).
- Documenting at the type level that these are *anti-OOM caps*,
  not LRUs — the difference matters for callers reasoning about
  performance.

### `formattedTextCache` is shared with `Tab.id` — **L, high**

`DocumentModel.swift:1523` — `formattedTextCache: [UUID: (sourceLength:
Int, formatted: String)]`. The cap is 8 entries, max 8 tabs of pretty-
printed JSON in memory. Fine. But the pattern repeats: every per-tab
cache (`csvFilterStates`, `hexBytesPerRow`, `editorBuffers`,
`editorCursorByTab`, `editorScrollByTab`, `pendingEditorDiagnostics`,
`languageOverrides`, `formattedTabIDs`, `formattedTextCache`) needs
the same close-path cleanup. The close paths (`closeTab`,
`closeOtherTabs`, `closeTabsToRight`) each repeat the cleanup list
(see `DocumentModel.swift:1989-1996`, `:2030-2035`, `:2068-2072`).
Adding a new per-tab cache requires touching three call sites; easy
to forget. A `tabClosed(id:)` hook that fans out to registered per-
tab stores would centralize this.

### `displayText` length-keyed memoization can serve stale on length-equal edits — **L, medium**

`DocumentModel.swift:1499-1521` keys on `sourceLength` only. The
comment notes this is intentional (length usually differs on file-
watcher reload). But pretty-printing a JSON that's edited to the
same byte count (rename a 4-char key to another 4-char key) will
serve the stale formatted view. The rendered-HTML cache at line
1639 (`fnv64`) does it right; the formatted cache should follow.
Cheap: hash 64 bytes of prefix+suffix instead of just length.

### `BookmarksStore.urlIndex` rebuild on every mutation — **L, medium**

`Sources/ViewerCore/BookmarksStore.swift:141` `rebuildIndex()` walks
`entries` and rebuilds the Set on every `add` / `remove` / load.
For the cap of 200 entries, that's irrelevant performance-wise.
But it's incrementally maintainable: `add` knows the URL it
inserted; `remove` knows the URL it removed. The pattern of "mutate
the array, then rebuild the index" pops up in a few places
(`SidebarModel.expanded`, `DocumentModel.openTabURLs`,
`BookmarksStore.urlIndex`). Pull the pattern into a tiny
`IndexedSet<URL, Element>` if it grows.

### `WeakModelBox` + nonisolated LSP callbacks vs strict-concurrency — **L, high**

Most `nonisolated(unsafe)` annotations in the codebase are correct
(documented with the contract that makes them safe). But the
combinator pattern (Notification observer that calls
`MainActor.assumeIsolated` to deref a `@MainActor` thing) is being
copy-pasted into more places than it should:

- `TextDisplayView.swift:390-407` (three observers)
- `SidebarModel.swift:77-80` (folder change)
- The Walkthrough engine's delegate hookup

Each repeats the `addObserver { [weak self] in MainActor.assumeIsolated
{ self?.x() } }` shape. A tiny helper `MainActor.observe(name:
object:queue:) { event in ... }` would cut the repetition and
centralize the "you must be on main" assertion.

## Naming nits

- **`uiSize(_:)` and `zoom`** are aliases — `uiSize(base)` is just
  `base * CGFloat(zoom)`. Either keep `uiSize` as the only call
  site (then it documents intent) or inline at every call (then
  the method is dead). Currently both forms appear in the codebase.
- **`csvFilterStates` vs `formattedTabIDs` vs `editorBuffers`** —
  same conceptual shape (per-tab side state) but three different
  naming conventions. Pick one (suffix `By Tab`, or `States`, or
  whatever) and apply.
- **`recentlyChangedFile` / `currentURL` / `currentFile` /
  `currentState`** — `DocumentModel`'s "what's selected" surface
  has accreted four near-synonyms. None of them is wrong but the
  reader has to disambiguate per use.
- **`HighlightLanguage` vs `LSPLanguage`** — both enumerate
  programming languages, with different ergonomics. They overlap.
  Could be unified at the kit boundary.

## Notable strengths worth preserving

Beyond what `CODE_REVIEW.md` already calls out:

- **`TabsState` is the gold standard.** Pure value type, full
  mutating-method API, every edge documented, round-trip tested.
  Use as a model for any future state-machine extractions.
- **`TreeSitterEngine`'s `paintOver` sweep-line is genuinely well-
  done** (`Sources/ViewerCore/Highlight/TreeSitterEngine.swift:102`)
  — O(K log K) in run count, allocation-light, with a clear comment
  explaining why naive per-character was bad.
- **`LSPClient`'s timeout + cancellation + transport-closed
  failAllPending** (`Sources/ViewerCore/LSP/LSPClient.swift:124-168`)
  is exemplary actor code: one entry point per lifecycle event,
  pending continuations resumed exactly once, no leak path.
- **`PluginSubprocessHost`'s defense surface** — env scrub, 1 MB
