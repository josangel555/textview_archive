## 3. Why can't I select a variable and see all instances? Is that LSP?

Yes, that's LSP — and half of it already exists: **"Find References" is in the command
palette** (`lsp.findReferences`, TSK-950) and lists every reference in the LSP navigation
panel; Go-to-Definition is also wired. What's missing is the *ergonomics* you're describing:

- **Click/select a variable → all instances highlight in-editor automatically** — that's LSP
  `documentHighlight`, not implemented yet. (The green matches you see today are CM6's
  *textual* selection-match — same characters, not same symbol.)
- **Right-click → Find References** in the editor context menu (today it's palette-only).

Filed as **I-15** (semantic occurrences + context-menu affordance). Note LSP only runs where
a server is configured (Swift/Java/TS…); plain-text/markdown falls back to textual match.

## 4. "Starting fresh; your sessions are still saved." — how do I get it back?

That toast is the **crash-loop breaker** (`RestoreCrashGuard`, `main.swift:508`): the previous
2 launches crashed *during session restore*, so it skipped restore ONCE to give you a working
app instead of a permanent boot loop. Nothing was deleted — sessions live in
`~/Library/Application Support/MarkdownViewer/Sessions/`.

**To get it back: just quit and relaunch.** The skip clears the marker, so the next launch
restores normally (if it crashes again, the doc that's crashing restore is the real bug —
tell me and I'll chase it). Gap filed as **I-18**: the toast should carry a "Restore now"
button instead of making you discover the relaunch trick.

## 5. `MDV_SESSIONS_DIR=/tmp/scratch-sessions` — why dirs at all? Can't it be in-memory?

That env var is **test-only isolation**: test-spawned app instances point session persistence
at a scratch dir so the suites never touch your real sessions
(`SessionStoreDirOverrideTests`, `AppLauncher`). Your real app never sets it.

Why a directory exists at all: the Sessions dir is **not a render cache — it's durable
state**: per-session tab lists, scroll/cursor positions, and the **hot-exit copies of unsaved
buffers** (the mechanism that let Local History save you in today's conflict incident).
In-memory-only would lose unsaved work on quit/crash. Renders are NOT persisted anywhere —
on restore the document re-renders from the file; the warm-WebView cache that avoids
re-render cost on session *switching* is in-memory only. So: disk = state that must survive
the process; memory = everything expensive-but-recreatable.

## 6. Why not build AutoSave?

Deliberate so far, not an oversight — two reasons:

1. **The data-safety half is already covered by hot-exit**: unsaved edits survive quit,
   crash, and relaunch without ever touching your file.
2. **Autosave-to-disk changes semantics**: every pause writes the file, which fires watchers
   (git status churn, build tools re-triggering), kills "revert to last save", and
   *multiplies* the external-edit conflict windows — the exact family that bit you today.

But opt-in autosave (VS Code-style `afterDelay`, plus save-on-focus-loss) is cheap to build on
the existing save funnel and lots of people want it. Filed as **I-14 (M)** with one ordering
constraint: it lands AFTER the false-conflict bug (**I-01**) is fixed, because autosave would
amplify that bug — every timed save would re-open the same false "changed on disk" window.
