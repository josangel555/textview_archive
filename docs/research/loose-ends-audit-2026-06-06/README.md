### LSP teardown leaks: fire-and-forget cleanup in tests + applicationWillTerminate budget too small for >=2 servers
- **action:** file-task  ·  **severity:** low  ·  **effort:** S
- **evidence:** raw [S3] findings: test cleanup 'defer { Task { await pool.closeAll() } }' never awaited; app-quit close uses ~2s budget while sequential shutdown is ~2.4s/server
- **detail:** Merged from two raw findings. Test teardown spawns a detached close Task that may not run before exit (leaked LSP child processes during test runs), and the quit-time close budget (2s) is exceeded by sequential ~2.4s/server shutdowns once 2+ servers are live, leaking to launchd. Both are leaks rather than correctness bugs.
- **recommendation:** Await closeAll() synchronously in test teardown; parallelize closeAll() and/or raise the quit budget, and at minimum log a warning instead of silently leaking.

### PARSE-03 depth cap guards the HTMLVisitor but not cmark-gfm's own recursive parse (nested-blockquote SIGSEGV)
- **action:** file-task  ·  **severity:** medium  ·  **effort:** M
- **evidence:** Sources/ViewerCore/HTMLRenderer.swift:16 (unguarded Document construction); PARSE-03 maxDepth applies only downstream at visit(); raw repro SIGSEGV at ~6000 nested '>' (8-12KB, far below the 4MB cap)
- **detail:** cmark-gfm parses input via recursive descent before the visitor (and PARSE-03) runs, so a deeply nested document blows the C stack with a hard SIGSEGV, synchronously in a SwiftUI body. - **recommendation:** Add an input-side pre-scan that rejects documents whose leading-'>'/list-indent nesting exceeds a few hundred, BEFORE handing bytes to cmark. Add a 10k-nested regression test.

### Plugin subprocess timeout kills only the target pid — grandchild can leak pipe fds + reader threads
- **action:** file-task  ·  **severity:** medium  ·  **effort:** M
- **evidence:** Sources/ViewerCore/Plugins/PluginSubprocessHost.swift:262-281 (single-pid kill); :235-255 (reader closures parked in availableData); no process group
- **detail:** On timeout only the direct child is signalled; if the plugin forked a grandchild inheriting the stdout/stderr pipes, the parent's reads never hit EOF and two reader closures park forever, leaking ~4 fds + 2-3 threads per invocation. PluginRegistry re-invokes on sidebar refresh, so repeated timeouts can exhaust RLIMIT_NOFILE. Verify line numbers (may have drifted).
- **recommendation:** Spawn the plugin in its own process group (POSIX_SPAWN_SETSID) and signal the whole group on timeout; force-close the pipe handles; consider DispatchSource on a serial queue instead of two parked global-queue read loops.
