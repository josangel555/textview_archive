### [S3] cm_apply ships the FULL document across FFI in BOTH directions per edit batch (~10x doc-size memory traffic per 200ms debounce tick)
- **Where:** `/Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/core/src/cm_edit.rs:46`
- **Why:** This is the highest-frequency FFI path the Swift app has (typing). O(doc) work per O(1) edit means latency and allocator pressure scale with file size, not edit size; on multi-MB docs the 200 ms debounce window can be eaten by copying alone, and GC/allocator churn on both sides hits the editor's responsiveness.
- **Fix:** For the production core: make the editor doc STATEFUL Rust-side (a handle owning a rope/gap-buffer keyed in UTF-16 code units, or piece-table over the original + add buffer), so the wire carries only `{from,to,insert}` per batch and an occasional full-resync. Interim cheap wins in the current stateless shape: `#[serde(borrow)] base: Cow<'a, str>` to skip the decode copy; skip the full Vec<u16> materialization by walking UTF-8 with a UTF-16 offset cursor (convert only the edited spans); pre-size `out` with `base_units.len() + Σ insert.len()`.
- **Verifier:** The Rust-side evidence is accurate: cm_edit.rs:100-104 ApplyRequest carries the full base String; apply_wire (:131-140) decodes it owned; apply (:46-93) materializes full Vec<u16> base (:51) and out (:73) and re-validates the whole doc (:93); the full text returns in ApplyResponse, and CoreClient.swift:297-336 round-trips full-doc frames with an extra Swift Array copy (:325). Full-doc-both-ways per batch is real, and for a production typing path the stateful-rope fix sketch is correct. HOWEVER the impact claim is materially wrong: the live editor call site (Sources/ViewerUI/CodeMirrorEditorView.swift:572) invokes the pure-Swift CMEditApplier.apply directly and never routes through RustCMEditAdapter — the adapter's ONLY caller is the A/B test (Tests/RustCoreTests/CMEditApplyABTests.swift:56) — so even with the .cmEdit gate ON (it is default-OFF per RustCoreGates.swift:10-15), no keystroke crosses mdvcore_cm_apply today. Additionally, the Swift incumbent and the onTextChange consumer already do O(doc) work per debounce tick (full String delivered downstream), so the wire seam adds constant-factor copies to an existing O(doc) path rather than creating a new asymptotic class. Real as a design/efficiency finding for the production core the owner mandated, but not a live serious perf bug on the hot path: downgrade S2 → S3.

### [S2] Level-triggered snapshot serializes ALL surviving rows per pull; full-table frame per filter change, and the 16 MiB MAX_FRAME_LEN hard-fails large tables
- **Where:** `/Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/core/src/session.rs:162`
- **Why:** Filter-as-you-type against a CSV session does an O(table) encode+decode per keystroke instead of O(visible-delta); and the frame cap silently breaks the Rust path for exactly the large files where Rust should win. The level-triggered model is sound, but "full truth" need not mean "full rows".
- **Fix:** Make the snapshot indices-only (header/version/total/query + surviving u32 indices); Swift projects rows from the Table it got at open — frame shrinks from O(rows×cells) to 4 B/row (~400 KB for 100k rows). Or add a windowed pull `snapshot_window(offset, limit)` returning only viewport rows. Either also moots the 16 MiB cap for realistic tables; the full-table `session_table` open-time pull should get a chunked variant for >16 MiB tables.
- **Verifier:** Every cited fact checks out against the code.

VERIFIED CLAIMS:
1. `snapshot_frame` serializes header + indices + ALL visible rows + query on every pull — confirmed at /Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/core/src/session.rs:162-184; `SnapshotView` (lines 224-233) includes `rows: &'a [&'a Vec<String>]`, projected from every surviving index (lines 170-173). The borrow-based encoding avoids the row CLONE but not the row SERIALIZATION — the wire frame still carries O(visible rows × cells) bytes per pull.
2. FFI path confirmed: `mdvcore_session_snapshot` (rust-core/crates/ffi/src/lib.rs:560-592) calls `snapshot_frame()` and maps `WireFault` → `MdvStatus::WireError` (line 587). `mdvcore_session_table` (lib.rs:472-500) already ships the full table once at open, so the snapshot's rows are indeed duplicative — its only new information is indices/version/total_rows/query.
3. Swift decodes everything: `CoreClient.decodeSnapshot` (Sources/RustCore/CoreClient.swift:260-277) decodes `rows` via `stringMatrix()` — a full per-cell walk per pull.
4. 16 MiB cap confirmed: `MAX_FRAME_LEN = 16 * 1024 * 1024` (rust-core/crates/core/src/wire.rs:73); `encode_frame` rejects larger bodies (wire.rs:163-167) → `WireFault::Framing` → `MdvStatus::WireError`. This applies to BOTH `session_table` and `session_snapshot`, so a table whose MessagePack body exceeds 16 MiB cannot cross the FFI at all.
5. Cap inconsistency confirmed: `csv::Limits::default()` allows `max_total_cells: 32_000_000` (rust-core/crates/core/src/csv.rs:47; finding cited :48, immaterial) — the parser happily accepts tables that the wire layer can never carry. 32M cells at even a few bytes each is vastly over 16 MiB; the cap bites at roughly ~170k rows × 10 cols of 8-byte cells (~9.6 MB msgpack for 100k rows, matching the finding's ~9 MB estimate).

ONE OVERSTATEMENT (does not kill the finding): the "filter-as-you-type per keystroke" loop is not yet a live app path. The only production consumer is `RustCSVAdapter.rustParse` (Sources/ViewerCore/RustCSVAdapter.swift:55-69), which pulls `table()` once and leaves filtering to the existing Swift CSV viewer; `setFilter`/`snapshot` are exercised only by tests (BridgeTests/ABTests). Also `RustCoreFallback.run` means a WireError on a >16 MiB table degrades gracefully to the Swift parser — no user-visible breakage today, but it does mean the Rust path is silently disabled for exactly the large files where it should win, which is a real, current effect on the live `table()` path.

SEVERITY: S2 stands. The audit's subject is the core as the production-grade reusable engine (owner mandate: compact binary RPC, hyper-efficient, FFI is the key path), and the session/snapshot API is its flagship Stage-2 state-sync design. An O(table) encode+decode per pull, plus an internal inconsistency where the parser's own limits (32M cells) exceed what the wire can ever carry (16 MiB), is a serious scalability/design defect in that deliverable — not exploitable/UB/data-loss (so not S1), but more than a moderate nit given it hard-fails the target workload and already silently disqualifies large CSVs from the Rust path today. The fix sketch (indices-only snapshot and/or windowed pull, chunked table transfer) is sound: indices-only shrinks the snapshot to ~5 B/row of msgpack and Swift already holds the full table from open.

### [S3] CSV parser is char-at-a-time with per-char cap checks and per-char String::push — several× slower than bulk byte-span scanning
- **Where:** `/Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/core/src/csv.rs:174`
- **Why:** CSV open is the entry cost of every table session (FFI `mdvcore_session_open`, TUI and web table views). Hand-rolled char loops typically parse at ~100-200 MB/s where span-based scanning reaches 1+ GB/s; on a 50 MB CSV that's the difference between ~0.4 s and ~0.05 s of pure parse.

Quoted-state same idea with `"` as the only sentinel. Keep the existing tests as the parity oracle.
- **Verifier:** Verified at rust-core/crates/core/src/csv.rs. Severity S3 is correct: pure performance, no correctness issue, but on the declared key path with 256M-scalar default limits and an explicit hyper-efficiency mandate.

### [S3] Table storage is Vec<Vec<String>> — 2 allocations + 48B header overhead per row plus one heap String per cell; ~2M+ allocations for a 1M-cell CSV
- **Where:** `/Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/core/src/wire.rs:28`
- **Why:** Owner's brief is a HYPER-EFFICIENT production core; the table is the core's central data structure and is rescanned per filter keystroke. Allocation count dominates open time and the scattered layout dominates filter-scan time on large files.
- **Fix:** Arena layout: one contiguous `String` (or Vec<u8>) holding all cell bytes + a flat `Vec<u32>` of offsets (cells addressed as `offsets[row*cols+i]..offsets[...+1]`), with `cell(row, col) -> &str` accessors. Filter scans become a linear walk over one buffer (memchr-friendly); serialization can emit straight from spans. Keep `Table` as the wire DTO; introduce the compact type as the session's internal store and project to wire shapes on demand.
- **Verifier:** Verified against the code. (1) wire.rs:28-30 defines `header: Vec<String>` / `rows: Vec<Vec<String>>` exactly as cited. (2) This type is the session's live store, not just a wire DTO: session.rs:28 `CsvSession { table: Table, ... }`, with snapshots projected from `self.table.rows`. (3) filter.rs:100-108 `matching_indices` touches every cell per query; set_filter caches only identical queries (session.rs:104-106), so each keystroke triggers a full rescan that pointer-chases individually-allocated Strings — the cache-hostility claim is accurate. (4) The scale is reachable: csv.rs default `max_total_cells: 32_000_000`, so a 1M-cell table is well within caps. (5) The allocation math holds: ~1.1M allocations for 100k×10 cells, ~24B String header + ~16B malloc block overhead per cell ≈ 40MB+ overhead on ~10MB payload. Existing mitigations (indices-only filter cache, borrow-based snapshot_frame) avoid clones but do not change the storage layout or scan locality. Severity S3 is correct: no correctness/UB/data-loss issue (not S1/S2), but a quantifiable efficiency cost in the core's central data structure on its hottest per-keystroke path, squarely within the owner's hyper-efficiency brief (not S4).

### [S4] Swift boundary does a DOUBLE full copy of every response frame: MdvBuf→Array, then unframe's Array(frame[4...])
- **Where:** `/Users/me/Documents/workspaces/claude/markdown_viewer/Sources/RustCore/CoreClient.swift:234`

## Hot-path map (how Swift actually drives the FFI)

| FFI entry | Swift driver | Frequency | Payload |

| `mdvcore_cm_apply` | `CodeMirrorEditorView` → `CMEditApplier.apply` (`Sources/ViewerUI/CodeMirrorEditorView.swift:15,572`), 200 ms JS debounce | **per typing burst** | full doc both ways |

## S2 — serious

### 1. `cm_apply`: full-document round trip per edit batch
`crates/core/src/cm_edit.rs:100-104` (`ApplyRequest { base: String, … }`), `:46-93` (`apply`), `crates/ffi/src/lib.rs:119`.
The stateless contract means each 200 ms debounce tick while typing moves ≈10× the document size through allocate/copy stages: Swift msgpack encode of `base` → frame; Rust decode to owned `String`; `encode_utf16().collect::<Vec<u16>>()` (2× bytes, `:51`); spliced second `Vec<u16>` (`:73`); validating `String::from_utf16` (`:93`); full response frame; Swift `Array` copy; Swift unframe copy; Swift String decode. **1 MB doc ⇒ ~10 MB traffic per tick to apply a few bytes of edit.**
**Fix:** stateful doc handle Rust-side (rope/piece-table indexed in UTF-16 units), edits-only wire. Interim: `#[serde(borrow)] Cow<str>` base; splice UTF-8 spans directly without materializing the full UTF-16 mirror; pre-size the output.

### 2. Snapshot pulls serialize all surviving rows; 16 MiB frame cap breaks big tables
`crates/core/src/session.rs:162-184`, `crates/core/src/wire.rs:73,163`, `crates/ffi/src/lib.rs:560`.
`snapshot_frame` is admirably clone-free Rust-side (borrow-based `SnapshotView`), but the *frame* still carries every visible row — data Swift already received via `mdvcore_session_table` at open. 100k×10 cells ≈ 9 MB encode + full Swift decode per filter change. And `MAX_FRAME_LEN = 16 MiB` hard-fails tables whose body exceeds it, while `csv::Limits` admits up to 32M cells (`csv.rs:48`) — the Rust path simply errors (`WireError`) on exactly the large inputs it should excel at.
**Fix:** indices-only snapshot (4 B/row) + Swift-side projection from the retained Table; or windowed `snapshot(offset, limit)` viewport pulls; chunked transfer for the >16 MiB open-time table pull.

### 3. TUI per-frame O(file)/O(table) recomputation
`crates/tui/src/main.rs:2520-2529` — every Text-mode frame: `String::from_utf8_lossy(&p.raw)` (full pass; full **copy** if the file has any invalid UTF-8) + `meta::text_metrics` (`crates/core/src/meta.rs:113-122`, 3 separate full passes) + `meta::line_ending` (full pass) ⇒ ~5 file scans per keypress, for a static badge.
Table mode: `filtered_table_indices` re-runs the full filter match per frame (`:2319`) and *again* in `content_len()` during scroll handling (`:198`); `find_in_table` rescans all shown rows per frame (`:2367`). The codebase already knows better — `ListRow` (`:127-136`) and `hl_cache` (`:166`) exist precisely to avoid per-frame rebuilds; these paths missed the pattern.
**Fix:** compute badge/metrics once per `Preview`; cache filter indices keyed by needle (the `CachedView` pattern from `session.rs:36-45`); cache table find hits keyed by (query, needle); single-pass `text_metrics`.

## S3 — moderate

### 4. `highlight()` recompiles the tree-sitter query per call; web pays per request
`crates/highlight/src/lib.rs:268-274` (+ owned query Strings / `format!` concats in `grammar()`, `:112-177`). The web tier calls `highlight_lines(&lines.join("\n"), lang)` per HTTP request (`crates/web/src/main.rs:1066`) — query compile + full reparse + full-document `join` for every navigation click. **Fix:** cache `HighlightConfiguration` per `Lang` (thread_local / OnceLock) inside the crate; all front-ends inherit the win.

### 5. CSV parser: char-at-a-time tokenization
`crates/core/src/csv.rs:174-227` — per Unicode scalar: 2 cap compares + state branches + `field.push(c)`. Bulk span scanning (byte-find the next `delim/\n/\r/"` then `push_str` the run) is typically 5-10× faster; this is the open-time cost of every CSV session. `memchr` would help (dep **PROPOSAL** — owner approval required); a hand-rolled byte loop already gets most of it.

### 6. `Table` = `Vec<Vec<String>>` — allocation-heavy, cache-hostile
`crates/core/src/wire.rs:28-30`. 1M-cell table ≈ 1.1M allocations, ~40-60 MB overhead for ~10 MB of payload; per-keystroke filter scans pointer-chase scattered cells (`filter.rs:100-110`). **Fix:** arena layout (one contiguous byte buffer + flat `Vec<u32>` offsets, `cell(r,c) -> &str`) as the session's internal store; keep `Table` as a wire DTO.

### 7. `find_matches` allocates per line; `Case::Sensitive` copies every line despite a "no allocation" doc claim
`crates/core/src/find.rs:190-195` (`fold` → `s.to_string()`), used per line in `:53-77`; multiplied across files by `grep_lines` (`:138-154`, TUI folder grep `tui/main.rs:1372`). **Fix:** `Cow` for Sensitive; replace the Insensitive fold-then-find with the no-alloc ASCII window scan already present at `filter.rs:123-130`.

### 8. Zero-copy misses in wire request structs
`crates/core/src/diff.rs:410-413` (`ParseRequest { text: String }` — used by *both* `parse_wire` and `hunk_marks_wire`, so one refresh decodes the same diff text twice) and `cm_edit.rs:100-104`. rmp-serde supports `#[serde(borrow)]` `&str`/`Cow` from the frame slice the FFI already holds. A combined `diff_parse_and_marks` call would also halve the crossings.

### 9. `hex_search_find` is O(n·m) position-by-position
`crates/core/src/hex.rs:171-189` — bounds-checked subslice compare at every offset, no first-byte skip. 5-20× available from memchr-style skipping (memchr = dep **PROPOSAL**; an `iter().position(|&b| b == first)` pre-filter is dependency-free and already a big win).

### 10. Named-map MessagePack repeats key strings per element in hot collections
`crates/core/src/diff.rs:28-38` (`Line`: ≈41 B/line of key text + string enums ⇒ ≈4-5 MB of literals in a 100k-line diff frame), `:528-532` (`MarkWire`). The Swift decoder is the hand-rolled `MsgPackReader`, not Codable, so positional tuples for per-element records are feasible while keeping named maps at the envelope level. The owner's "compact binary RPC" goal argues for this.

### 11. Swift boundary double-copies every response frame
`Sources/RustCore/CoreClient.swift:221` (MdvBuf → `Array`) then `:234` (`Array(frame[4...])` — second full copy to drop 4 bytes). Hex render: ~36 MB transient copying for a 4 MB file. Rust's `MdvBuf` is already zero-copy-out; consume it via `Data(bytesNoCopy:deallocator:)`/raw-buffer reads with an offset-aware reader. (Swift-side, but it is the FFI boundary cost model.)
