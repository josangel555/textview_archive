# unsafe-ffi — rust-core audit 2026-06-09 (final, post-resume)

## Adversarially confirmed findings

### [S2] cbindgen header can silently go stale: build.rs rerun-if-changed misses buf.rs/status.rs/handle.rs (ABI-drift → memory corruption enabler)
- **Where:** `rust-core/crates/ffi/build.rs:32`
- **Why:** Edit buf.rs (add/reorder a field of MdvBuf) or status.rs (renumber/resize the enum) → the staticlib is rebuilt with the new layout, the header is NOT regenerated, build-rust-core.sh happily stages the stale header, and Swift reads/writes MdvBuf with the old field offsets. That is silent cross-language memory corruption — the precise 'cbindgen contract drift' failure mode, with no compile-time or gate-time detection today.
- **Fix:** 1) `println!("cargo:rerun-if-changed=src")` (directory form) so any source change re-runs cbindgen. 2) Make header-gen failure fatal when MDV_RUST_PROFILE is the app-link path (keep the warn-only fallback for bare `cargo test` if desired). 3) Add a gate step in scripts/rust-core-gate.sh: regenerate the header into a temp file and `diff` against `include/mdvcore.h`, failing on drift.
- **Verifier:** Every factual claim in the finding checks out against the code:

1. **Rerun list is exactly as claimed** — `rust-core/crates/ffi/build.rs:32-34` emits only `cargo:rerun-if-changed=src/lib.rs`, `cbindgen.toml`, `build.rs`. Per documented cargo semantics, emitting any rerun-if-changed disables the default whole-package rerun, so editing other source files recompiles the crate WITHOUT re-running the build script.

2. **The ABI-load-bearing types live off-list** — `#[repr(C)] MdvBuf {data, len, cap}` at `rust-core/crates/ffi/src/buf.rs:13-22` and `#[repr(C)] MdvStatus` (explicit discriminants 0-4, 98, 99) at `rust-core/crates/ffi/src/status.rs:14-35`, exactly as cited. Both are emitted into the generated header (`rust-core/crates/ffi/include/mdvcore.h:19-38` MdvStatus, `:47-55` MdvBuf) because cbindgen parses the whole crate via `Builder::with_crate` (build.rs:40). So a layout/discriminant edit in those files rebuilds the staticlib but leaves the header stale. (The 16 `extern "C"` fns are all in lib.rs, so function *signatures* are covered — the gap is precisely the repr(C) types.)

3. **The stale copy is the one that gets shipped** — `scripts/build-rust-core.sh:78` runs an incremental `cargo build` (no clean, no touch), and `:104-122` prefers `HEADER_SRC="$RUST_DIR/crates/ffi/include/mdvcore.h"` (the build.rs mirror) and copies it into `Sources/CMdvCore/mdvcore.h` for the Swift compile. The mirror is gitignored but persists across incremental builds on the dev host — and rides the rsync to the VM. So the common dev path (`build-app.sh debug --install`) compiles Swift against the stale layout.

4. **No detection anywhere** — build.rs:61-64 tolerates cbindgen failure with only `cargo:warning`, and `scripts/rust-core-gate.sh` contains zero header/cbindgen drift checking (grep empty).

Consequence is as stated: e.g. adding/reordering a field in MdvBuf → Swift allocates/reads the struct with old offsets while Rust writes new ones → silent cross-language memory corruption with no compile-time or gate-time signal. Mitigations that keep this at S2 rather than S1: clean builds (fresh CI checkout, no pre-existing mirror) regenerate correctly; status.rs documents a never-renumber discipline; nothing is corrupted today. It is a real, latent ABI-drift enabler on the declared key path (SwiftUI↔Rust FFI) with zero automated detection — S2 (serious) is correctly calibrated. The fix sketch (directory-form rerun-if-changed, fatal header-gen on the app-link path, gate-time header diff) is sound.

### [S3] mdvcore_hex_render: unvalidated `width` (u32) drives a width-proportional allocation — width=0xFFFFFFFF requests ~17 GiB; alloc failure aborts the host app past the panic guard
- **Where:** `rust-core/crates/ffi/src/lib.rs:283`
- **Why:** A buggy (or hostile) Swift caller can OOM the GUI process from a 1-byte buffer. Worse for the 'rock solid' goal: a failed heap allocation in Rust calls handle_alloc_error → abort(), which `catch_unwind` in ffi_guard! cannot intercept even in the panic=unwind `dist` profile — the exact host-kill the guard architecture exists to prevent.
- **Fix:** Clamp/validate at the FFI edge: reject width outside a sane envelope (e.g. 1..=512 bytes-per-row → return a new MdvStatus or reuse NullArg/Internal), or saturate width to min(width, 512) before calling render_all. Also consider capping `rows*per_row` against a MAX_RENDER_BYTES constant inside render_all as defense in depth.
- **Verifier:** Every factual claim verified against the code. (1) rust-core/crates/ffi/src/lib.rs:283 passes the caller's u32 width to hex::render_all with zero validation (the usize::try_from is infallible on 64-bit, so the raw value flows through). (2) rust-core/crates/core/src/hex.rs:25-28 gives per_row ≈ 4×width+12; with a 1-byte buffer and width=u32::MAX, hex.rs:33-38/64 yields rows=1 and hex.rs:72 issues a single ~16-17 GiB Vec::with_capacity; hex.rs:86-107 would then physically write ~17 GiB of padding via two 0..width loops. Only width==0 is guarded (hex.rs:60). (3) The abort claim is correct: a failed infallible allocation calls handle_alloc_error → abort(), which the ffi_guard! catch_unwind cannot intercept under any panic strategy — defeating the guard architecture's stated purpose. (4) The buggy-caller vector is realistic: Sources/RustCore/CoreClient.swift:520 uses UInt32(truncatingIfNeeded: width), so a Swift-side width = -1 becomes exactly u32::MAX. Severity check: all current first-party callers clamp width to {16,32,64} via HexLayout.clampWidth (HexLayout.swift:11,20; TabCoordinator.swift:351-356; PreferencesStore.swift:160-163) and RustHexAdapter is currently test-only behind a default-OFF gate, so there is no live trigger today — this is an FFI-boundary hardening gap (self-DoS on caller bug), not an exploitable bug. That is exactly S3 territory given the owner's production-grade/rock-solid mandate for the FFI as the key path; the finding itself acknowledges the buggy-caller threat model, so no recalibration needed. Fix sketch (reject/clamp width at the FFI edge, e.g. 1..=512, plus a MAX_RENDER_BYTES cap inside render_all) is sound.

### [S3] Handle free-vs-call race is unprotected UB and contradicts the advertised 'misuse is rejected, not UB' model; free drops a possibly-locked Mutex
- **Where:** `rust-core/crates/ffi/src/handle.rs:87`
- **Why:** The crate's own threading story creates the expectation that concurrent misuse is detected and surfaced as Busy. The one misuse a real Swift app is most likely to commit under ARC/deinit timing — freeing a handle while a background snapshot is in flight — is the one that's still raw UB (UAF/double-drop), not a status code. For a production reusable core this is the top remaining soundness hole in the ownership model.
- **Fix:** Production-grade: stop passing raw Box pointers across the ABI — keep a global registry (Mutex<HashMap<u64, Arc<SessionHandle>>>) and hand Swift a generation-counted integer id; free removes from the registry (stale ids → NullArg, in-flight calls keep their Arc alive). Minimal hardening: have `free` do `handle.inner.try_lock()` first and, on WouldBlock, leak with a debug_assert / return-without-free (leak beats UAF), documenting the changed semantics.
- **Verifier:** Every factual claim checks out against the code. (1) `SessionHandle::free` at /Users/me/Documents/workspaces/claude/markdown_viewer/rust-core/crates/ffi/src/handle.rs:87-93 does an unconditional `drop(Box::from_raw(ptr))` — it never inspects or acquires the Mutex, so freeing while another thread is inside `with` destroys a logically-held Mutex and frees the CsvSession out from under the executing closure (UAF). (2) The advertised model is quoted accurately: lib.rs:29-34 says "a misbehaving multi-threaded caller is *rejected*, not silently serialized", and handle.rs:23-29 frames `try_lock`→Busy as making contract violations LOUD — but that mechanism only guards call-vs-call; free-vs-call has zero runtime detection. (3) `as_ref` (handle.rs:74-80) hands back an unbounded-lifetime `&'a SessionHandle` whose validity rests purely on the caller "not racing a live borrow" (the SAFETY comment at handle.rs:76-79 says exactly this), and `mdvcore_session_snapshot` (lib.rs:560-592) is precisely the long-running borrow a Swift background thread would hold when ARC/deinit fires `mdvcore_session_free` (lib.rs:601-607, which adds no protection beyond catch_unwind on Drop).

Refutation angles considered: (a) "It's a documented unsafe precondition, standard C-FFI practice" — true (lib.rs:597-599 and handle.rs:84-86 state the exactly-once / no-race contract), so this is not an unsoundness bug in the Rust sense; but the audit brief is a production-grade, super-secure reusable core, and the crate's own design narrative sells runtime misuse-rejection, making the one remaining undetected-misuse → UB path a legitimate hardening finding, not speculation. (b) "The docs scope Busy-rejection to calls only, so no contradiction" — partially valid as a wording quibble (the finding's "contradicts" is slightly overstated; the docs are internally consistent), but the substantive point stands: the misuse most likely in practice (free racing an in-flight call under Swift deinit timing) is the one with no detection. The fix sketch (registry + generation-counted ids, or minimal try_lock-then-leak in free) is sound and standard.

Severity: S3 is correctly calibrated. Not S1/S2 — the UB requires the caller to violate a clearly documented safety contract, and a well-behaved Swift wrapper (single owner, free after quiescence) never hits it; it is a design-hardening gap, not an exploitable defect in conforming use. Not S4 — it is a real UAF/double-drop path on the key SwiftUI↔Rust FFI boundary with a concrete production fix, exactly the class of soundness-model gap a "rock solid" core should close.

## Full reviewer report

# UNSAFE + FFI Soundness Audit — rust-core (mdvcore-ffi, mdvcore-highlight, wire decode paths)

**Date:** 2026-06-09 · **Scope:** every `unsafe` in `crates/ffi/src/*.rs` and `crates/highlight/src/*.rs`, the 14 `extern \"C\"` exports, `catch_unwind`/profile interaction, ownership conventions, cbindgen contract, and `crates/core/src/wire.rs` decode paths reachable from FFI with attacker-controlled bytes.

## Verdict

The unsafe edge is unusually disciplined for a PoC: `unsafe_op_in_unsafe_fn = deny`, `undocumented_unsafe_blocks = deny`, `multiple_unsafe_ops_per_block = deny` (ffi/Cargo.toml), per-block SAFETY comments, null+len pairing checks before every `from_raw_parts`, out-params pre-initialized to safe defaults on every entry, and an allocate-and-free-on-the-same-side convention throughout. **No S1 (currently-manifest UB) was found.** The serious items are *drift/robustness enablers*: a stale-header hole in the cbindgen pipeline (the one path that can manufacture cross-language memory corruption later), an unbounded allocation at one boundary parameter, and the free-vs-call race that the crate's own threading story implies is handled but isn't.

## Findings (ranked)

### F1 — S2 — cbindgen header can silently go stale (ABI drift → memory corruption enabler)
`crates/ffi/build.rs:32-34` emits `rerun-if-changed` for **only** `src/lib.rs`, `cbindgen.toml`, `build.rs`. Cargo semantics: once any rerun-if-changed is printed, *only those paths* re-trigger the build script. The two `#[repr(C)]` ABI types live elsewhere: `MdvBuf` in `src/buf.rs:13-22`, `MdvStatus` in `src/status.rs:14-35` (cbindgen does parse the whole crate via `Builder::with_crate`; it just never re-runs on their change). So: edit `buf.rs` field layout → staticlib rebuilds with the new layout, header does **not** regenerate, and `scripts/build-rust-core.sh` (HEADER_SRC block) prefers exactly the stale mirrored copy `crates/ffi/include/mdvcore.h`. Swift then accesses `MdvBuf` at old offsets — silent cross-language corruption with no gate-time detection. Compounding: `build.rs:61-64` tolerates cbindgen *failure* with only a `cargo:warning`.
**Fix:** `cargo:rerun-if-changed=src` (directory form); make header-gen failure fatal on the app-link path; add a gate step that regenerates the header to a temp file and diffs against `include/mdvcore.h`.

### F2 — S3 — `mdvcore_hex_render` width is unvalidated → ~17 GiB allocation; alloc failure aborts past the guard
`crates/ffi/src/lib.rs:283` forwards the caller's `u32 width` unclamped. `hex.rs:25-27` makes `per_row ≈ 4×width`; `hex.rs:72` does `Vec::with_capacity(rows*per_row)`. A 1-byte input with `width=0xFFFFFFFF` → one ~17 GiB capacity request; if macOS lazily grants it, the per-row loops (`hex.rs:86-107`, two `for i in 0..width` passes) physically write ~17 GiB of padding. Only `width==0` is guarded (`hex.rs:60`). Critically, a **failed** allocation calls `handle_alloc_error → abort()`, which `ffi_guard!`'s `catch_unwind` cannot intercept even in the panic=unwind `dist` profile — the exact host-app kill the guard architecture exists to prevent.
**Fix:** validate at the edge (reject/clamp width outside `1..=512`), plus an internal `MAX_RENDER_BYTES` cap in `render_all` as defense in depth.

### F3 — S3 — free-vs-call race is raw UB and contradicts the advertised misuse model
`handle.rs:87-93` `free` does `Box::from_raw` + drop unconditionally, never touching the Mutex. The crate docs (`handle.rs:23-29`, `lib.rs:29-34`) advertise that a misbehaving multi-threaded caller is \"*rejected*, not silently serialized\" — true for call-vs-call (`try_lock` → `Busy`), but `mdvcore_session_free` racing an in-flight `h.with(...)` (e.g. a background snapshot vs. a Swift deinit) is a use-after-free and destroys a logically-held Mutex. It is a documented caller contract (standard C practice), but it's the misuse a real ARC-managed host is *most* likely to commit, and the design's stated goal is loud rejection.
**Fix (production):** stop passing raw pointers — registry of `Arc<SessionHandle>` keyed by generation-counted integer ids; stale id → `NullArg`, in-flight calls hold their own Arc. **Minimal:** `free` try_locks first; on `WouldBlock`, leak-and-log rather than UAF.

### F4 — S4 — poisoned-lock recovery silently serves possibly half-mutated state
`handle.rs:104-109` recovers `Poisoned` via `into_inner()` and proceeds. The drop-and-recreate-after-`Panic` rule lives only in prose (`status.rs:29-31`, `guard.rs:19-21`). A caller that ignores one `Panic` gets confident `Ok` answers from a session whose invariants may be torn.
**Fix:** taint flag on the handle (set on poison recovery / caught panic in a handle call); return `Internal` (99, already reserved) until recreated.

### F5 — S4 — `MdvBuf.data` \"null when len==0\" is false (dangling non-null), and `free_in_place` trusts the C-visible `len`
`buf.rs:15` + `link/mdvcore.h:48` claim null-on-empty, but `from_vec` of an unallocated empty Vec (reachable: `mdvcore_hex_render` of 0 bytes → empty String → `lib.rs:287`) stores the aligned-dangling pointer (0x1), len=0, cap=0 — non-null. A Swift caller branching on `data != nil` mis-classifies an empty result (no UB, len=0, but a wrong ABI statement). Separately `free_in_place` (`buf.rs:59`) rebuilds `Vec::from_raw_parts(data, **buf.len**, cap)`; only `cap` is documented do-not-modify, so a Swift-side len corruption (len>cap) becomes library UB at free time — an unnecessary trust edge.
**Fix:** normalize `cap==0 → data=null` in `from_vec`; reconstruct with len **0** in `free_in_place` (u8 has no per-element Drop — identical free, immune to len tampering); document `len` as read-only.

### F6 — S4 — `hex_search_frame` silently clamps offsets >u32::MAX
`hex.rs:219-222` maps each match offset with `u32::try_from(o).unwrap_or(u32::MAX)`. The FFI takes a `usize data_len` (`lib.rs:307-314`), so >4 GiB input yields confidently wrong offsets (all 0xFFFFFFFF) instead of an error. Doc relies on an unenforced caller cap (`hex.rs:210`).
**Fix:** error when `data.len() > u32::MAX`, or widen the wire schema to u64 offsets now, while the protocol is young.

### F7 — S4 — `mdvcore_force_panic` ships in the production staticlib
`lib.rs:84-97`, exported in `mdvcore.h:68`. Safe under the guarded `dist` profile, but a deliberate panic trigger in the shipped symbol table; under any future panic=abort slip it's a one-call process killer.
**Fix:** gate behind a `ffi-test-hooks` cargo feature enabled only by the Swift test-harness build.

### F8 — S4 — highlight crate: no no-panic lint wall, direct indexing/slicing on grammar-provided offsets, no parse timeout
`crates/highlight/Cargo.toml` has no `[lints]` table (deliberate, per its comment). `highlight_lines` (`lib.rs:341-363`) uses `spans[si]`/`src[cursor..s]` with byte offsets sourced from 12 third-party C grammars; a buggy grammar emitting a mid-UTF-8 offset panics (TUI/web only — not FFI-reachable). `Highlighter::highlight` (`lib.rs:277`) sets no timeout/cancellation, so pathological input wedges a render thread for unbounded CPU.
**Fix:** `get()`-based slicing with graceful unstyled fallback; local lint denies; tree-sitter timeout for large inputs.

## Verified sound (audited, no finding)

- **Slice construction**: every `from_raw_parts` site (lib.rs:138, 184, 229, 281, 329/335, 389, 448, 529) is preceded by a paired null/len check and a `len==0 → &[]` branch; u8 alignment trivially satisfied. (A caller passing `len > isize::MAX` with a tiny buffer already violates the validity contract — subsumed.)
- **catch_unwind correctness**: `AssertUnwindSafe` is justified and documented (`guard.rs:17-21` — the catch exists precisely to stop the unwind; state-suspicion is handled by contract + F4 suggestion). Since Rust 1.81 an escaped unwind at `extern \"C\"` is a defined abort, and the guard exists for *host survival*, correctly stated (`guard.rs:1-15`). All 14 exports are wrapped (the two `void` frees use bare `catch_unwind`, also fine — raw pointers are `UnwindSafe`).
- **panic=abort vs dist profile**: `Cargo.toml` `[profile.release] panic=\"abort\"` is size-figure-only; the app-link path is `dist` (`panic=\"unwind\"`, opt-level 3), and `scripts/build-rust-core.sh:30-48` hard-rejects non-unwind profiles (`dist|dev|test` allowlist). Good, load-bearing guard.
- **MdvStatus / cbindgen contract today**: `#[repr(C)]` with explicit pinned discriminants; header matches source exactly (checked field-by-field, enum value-by-value); opaque `SessionHandle` correctly forward-declared; `bool`/`u64`/`uintptr_t` ABI mappings correct.
- **Send/Sync on SessionHandle**: justified — all access is Mutex-mediated (`handle.rs:41-48`); `CsvSession` is plain owned data; the contention test (`tests.rs concurrent_calls_are_serialized_or_rejected_never_ub`) hammers 8 threads × 200 ops and pins Ok|Busy-only outcomes. Double-free of `MdvBuf` is genuinely idempotent (fields nulled, `tests.rs buf_double_free_in_place_is_safe`).
- **wire.rs hostile-bytes decode**: `MAX_FRAME_LEN` (16 MiB) enforced on encode (wire.rs:163) and decode (wire.rs:198), declared-vs-actual length must match exactly (wire.rs:203), and `decode` rejects trailing bytes via cursor-position check (wire.rs:118-134) — kills padded/smuggled payloads. **Preallocation-bomb check done at the dependency level**: rmp-serde 1.3.0 reads str/bin via `take(len).read_to_end` into an incrementally-grown buffer (registry `rmp-serde-1.3.0/src/decode.rs:1042,1051`), so a header declaring 4 GiB cannot allocate more than the actual ≤16 MiB input; serde seq visitors use cautious size hints. Decode targets (`ApplyRequest`, `ParseRequest`, …) are flat structs — no unbounded recursion. `cm_edit::apply` validates bounds/overlap/ordering in i64 before any slicing and uses validating UTF-16 decode (no U+FFFD divergence).
- **Session open**: `CsvSession::open` errors only on UTF-8 (`session.rs:52-56`), so the FFI's `Err(_) → BadUtf8` mapping is exact (today; would rot if OpenError grows variants). CSV parse is cap-limited (`csv::Limits`) — truncates with markers rather than ballooning.
- **trace globals**: `static SINK: RwLock<Option<Box<dyn Sink>>>` (`trace.rs:88`) — poisoning treated as no-sink (`trace.rs:108-114`), no unwrap, `Sink: Send+Sync` required; in the Swift app no sink is installed so FFI-path tracing is a cheap no-op. (Residual exotic case: a sink that panics inside a `Span` Drop *during* an unwind would double-panic-abort; the Sink trait documents must-not-panic, and no sink exists in the app context.)
- **highlight crate unsafe**: zero `unsafe` tokens in its own source; the grammar FFI lives in the pinned grammar crates (`tree-sitter-* = \"=x.y.z\"`, exact-pinned per the minimal-deps posture).

## Notes for the production hardening pass

1. F1 + F3 are the two structural items to fix before this graduates from PoC: F1 closes the only realistic path to cross-language memory corruption; F3 (registry/generation handles) removes the last raw-pointer trust edge and would let the threading docs' \"misuse is rejected\" claim be literally true.
2. Consider a boundary-wide input-validation convention: every scalar param that sizes an allocation (hex `width`, future ones) gets an explicit envelope check at the FFI edge, not in core. F2 is the only instance today.
3. The status enum has room (`Internal = 99` reserved): a `Tainted`/`InvalidArg` variant is additive and non-breaking per the documented discipline.
