## 1. JetBrains MPS (Meta Programming System)

**What it is.** A projectional (a.k.a. structure) editor and language workbench: you edit the AST directly through one or more *projections* (notations) rather than typing free text that a parser turns into a tree. Because there's no parser, notations that plain text cannot express — tables, math, diagrams — become first-class alongside textual ones (https://www.jetbrains.com/help/mps/mps-faq.html).

**How it stores the artifact (concrete data structure).** Per JetBrains' own FAQ:
- "Every program element is stored as a node with a unique ID (UID) in the AST. References are based on actual pointers (references to UIDs)."
- "The AST is actually an Abstract Syntax Graph (AGT) because cross-references are first-class rather than being resolved after parsing." (i.e., it's a graph, not a tree — references are stored resolved.)
- "The program is then persisted to disk as XML, but this process is transparent to the user." (https://www.jetbrains.com/help/mps/mps-faq.html)
- Persistence is per-model and pluggable — "the persistence type in MPS is set on the per-model level," with a custom-persistence API (https://www.jetbrains.com/help/mps/custom-persistence-cookbook.html) **[search-indexed]**.

The load-bearing design choice: **stable node UUIDs are the identity of a program element**, and cross-references are stored as pointers to UUIDs, not as names to be re-resolved.

**Why it matters for an AI-authored-model → render-target system.** MPS is the closest existing production system to "one semantic model, many projections, the canvas is just one projection." Two properties transfer directly:
- Multiple simultaneous, editable notations over the *same* model — the exact "canvas is a projection of the model" architecture.
- Stable UUIDs give you *move-vs-delete* discrimination in diff/merge: "since every program element has a UUID, a move can be distinguished from delete/create, which provides more usable semantics for diff and merge" (https://www.jetbrains.com/help/mps/mps-faq.html). For an AI agent that restructures a document, structural identity survives reordering — a text-diff would show a huge churn where a structural diff shows "moved."

**What breaks / documented pain points.** MPS is the best-documented cautionary case *because it succeeded technically yet the ergonomic tax is real*:
- **No plain-text source ⇒ bespoke VCS tooling.** JetBrains FAQ: "Since the concrete syntax is not pure text, a generic persistence format must be used. Therefore, special tools need to be provided for diff and merge features." (https://www.jetbrains.com/help/mps/mps-faq.html) You cannot use ordinary `git diff`/`git merge` meaningfully on the XML; you need MPS's own merge driver.
- **The text-feel problem.** FAQ: "Using the MPS projectional editor for the first time can feel odd because it is different from a textual editor," though "it takes a few days for most users to become accustomed" (https://www.jetbrains.com/help/mps/mps-faq.html).
- **Voelter's SLE 2014 paper** *Towards User-Friendly Projectional Editors* enumerates the honest drawbacks: the unfamiliar editing experience; difficulty integrating with existing infrastructure such as VCS and diff/merge tools; and that for notations that *look* textual, users expect classic text-editing behavior that projectional editors historically did not deliver. It specifically notes "MPS provides no generic support for (temporarily) commenting out code" as an example of a mundane text operation that becomes hard (https://mbeddr.com/files/projectionalEditing-sle2014.pdf; also https://link.springer.com/chapter/10.1007/978-3-319-11245-9_3) **[search-indexed, PDF not directly parseable]**.
- **Controlled experiment (Berger, Völter, Jensen, Dangprasert, Siegmund, FSE 2016), *Efficiency of Projectional Editing*.** 19 participants (graduate CS students + industrial developers). Findings: projectional editing is efficient for *basic* editing tasks, but editing strategies and typical errors differ from text; more *complex* tasks require substantial experience and a good mental model of the AST before projectional editing becomes efficient; there is an explicit tradeoff of "fewer typing mistakes" against "increased complexity of code editing"; and more experience significantly improved *advanced* editing but not basic editing (https://voelter.de/data/pub/fse2016-projEditing.pdf; https://dl.acm.org/doi/10.1145/2950290.2950315) **[search-indexed; PDF unparseable and ACM page 403'd — numbers are from the paper's indexed abstract]**.

Net: MPS proves the model works and ships in industry (mbeddr, healthcare/automotive DSLs), but every non-obvious cost the user asked about — VCS, copy-paste/comment-out, text-editing muscle memory — shows up as a documented, named problem, mitigated but not eliminated.

## 2. Intentional Software / Intentional Programming (Charles Simonyi)

**What it is.** Simonyi's paradigm where "programmers focus on capturing the intent of users and designers, and spend as little time as possible interacting with machines and compilers" (https://en.wikipedia.org/wiki/Intentional_Software). Born at Microsoft Research in the 1990s; "By March 1995 [Simonyi] had built an integrated development environment demonstrating it," and in September 1995 he published *The Death Of Computer Languages, The Birth of Intentional Programming* (https://en.wikipedia.org/wiki/Intentional_Software). He left Microsoft in 2002 to found Intentional Software, which built the **Intentional Domain Workbench (IDW)**.

**How it stores the artifact (concrete data structure).** The **intentional tree**: programs are "written in a general purpose language with the working name of CL1, which was represented as a tree or database rather than text. This information could be projected or viewed in several ways, such as circuit diagrams or a C#-like language" (https://en.wikipedia.org/wiki/Intentional_Software). Fowler, who saw a private demo, describes the same core: "The fact that editing is done on an intentional tree rather than text also changes some other things," and the projections are *reversible* — "All three of these projections are reversible, meaning that you can edit through them, updating the semantic model and other projections" (across XML, a custom syntax, Ruby, diagrams, and C#) (https://martinfowler.com/bliki/IntentionalSoftware.html). Automatic rewriting of the tree was possible "as expert knowledge of implementation options changed" (https://en.wikipedia.org/wiki/Intentional_Software).

**Why it matters for an AI-authored-model → render-target system.** This is the *purest statement* of the architecture the user is describing: a single semantic model (intent), decoupled from notation, projected into many editable views — one of which could be a canvas. Fowler was genuinely impressed: "there was a realness and maturity that I hadn't seen before," citing live execution woven into specs (circuit-impedance results shown during editing; red/green test feedback updating as formulas change) (https://martinfowler.com/bliki/IntentionalSoftware.html). Boersma highlights an ability that AI-model systems would kill for — total provenance: "when running a domain in the IDW you can point to a pixel on the screen and ask the IDW why that pixel has that colour, at which point you're presented with trace information about the chain of transformations that turns domain data into its visualisation" (https://medium.com/@dslmeinte/intentional-software-bought-by-microsoft-2606e6eb1106).

**What breaks / why it's a cautionary tale.**
- **It never shipped a live system.** Fowler's decisive caveat (2007): "No system designed using the Intentional Domain Workbench has yet gone live," and "you never really understand something till you deploy it into production every week" (https://martinfowler.com/bliki/IntentionalSoftware.html).
- **Unusable by mortals.** Boersma, who actually used the IDW and *is* a language-engineering expert: "a couple of weeks is not enough to get a working (albeit basic) knowledge of the IDW at all"; he compares the learning curve to "a sane LISP ... times a non-trivial factor because you're mentally operating in several domains at the same time," and concludes bluntly on "The IDW being unusable for normal folks," compounded by sparse documentation. He attributes it partly to a founder-genius trap: "smart people rarely develop the skill to explain their smarts in a clear way that's understandable for people not already operating on or near their level" (https://medium.com/@dslmeinte/intentional-software-bought-by-microsoft-2606e6eb1106).
- **~15 years in stealth, then a quiet acquihire.** Fowler noted for years it "has been hiding under some deep rocks" (https://martinfowler.com/bliki/IntentionalSoftware.html). On April 18, 2017 Microsoft acquired it and "many of its employees join[ed] the Microsoft Office team" (https://en.wikipedia.org/wiki/Intentional_Software). Boersma was surprised the company "pivoted quite a bit since they effectively went underground, and in a direction that seems to cater mostly for being integration in Microsoft Office," and openly worried "will it go the way of Oslo, i.e.: nowhere…" (a reference to a prior failed Microsoft language-workbench effort) (https://medium.com/@dslmeinte/intentional-software-bought-by-microsoft-2606e6eb1106). The original intentional-programming vision was effectively shelved into productivity tooling.
- **Structural VCS + lock-in are unsolved.** In his language-workbench survey Fowler names the two systemic blockers this whole class shares: "High on my list is that of version control. We know how to do effective version control for textual sources with good diff and merge capabilities … language workbenches will need to be able to provide diff and merge of the semantic model itself"; and lock-in — "Once you define a language in a language workbench you are tied to that language workbench. There's no standard for interchange between the different language workbenches" (https://martinfowler.com/articles/languageWorkbench.html). He also flagged the maturity gap as the near-term killer: "The biggest short term limitation of these tools is maturity" (same URL).

The cautionary read: the technology was arguably the most advanced of its kind, and it still died — not on capability but on **learnability, the absence of a shipping proof point, and the lack of an ecosystem** (VCS, interchange, a user base that could learn it).

## 3. Hazel

**What it is.** "A live functional programming environment organized around typed holes" — a web-based editor for an "Elm/ML-like functional programming language" (https://hazel.org/). The foundational paper is *Hazelnut: A Bidirectionally Typed Structure Editor Calculus* (Omar, Voysey, Hilton, Aldrich, Hammer; POPL 2017) (https://arxiv.org/abs/1607.04180).

**How it represents the artifact (concrete data structure).** From the Hazelnut abstract: it is "a structure editor based on a small bidirectionally typed lambda calculus extended with *holes* and a *cursor*." Editing is not free-text; it's a calculus of **edit actions** that "operate over statically meaningful incomplete terms." The key mechanism: "the action semantics automatically places terms assigned a type that is inconsistent with the expected type inside a hole," which "safely defers the type consistency check until the term inside the hole is finished." The metatheory is mechanized in Agda, with "connections with gradual typing and contextual modal type theory," and the reference implementation is a functional-reactive program in js_of_ocaml (https://arxiv.org/abs/1607.04180). Concretely this is a *zipper* term (an expression tree plus a cursor position) over which typed edit actions preserve a well-typedness invariant — I could not extract the exact `ZExp` grammar (the CMU page and the arXiv PDF didn't yield the formal figures), so I'm describing the model from the abstract, not the formal rules.

**Typed holes — the problem they solve.** hazel.org states the invariant plainly: Hazel can "typecheck, manipulate, and even run incomplete programs, i.e. programs with holes. **There are no meaningless editor states**," and "every incomplete program that you can construct using Hazel's language of edit actions is both *statically* and *dynamically* well-defined" (https://hazel.org/). Holes play two roles: "(1) stand for parts of the program that are missing; and (2) serve as membranes around parts of the program that are erroneous" (https://hazel.org/). The follow-up, *Live Functional Programming with Typed Holes* (arXiv 1805.00155), gives a *dynamic* semantics so incomplete programs can actually **run**: empty holes stand for missing expressions/types, and non-empty holes act as "membranes around static and dynamic type inconsistencies" (https://arxiv.org/abs/1805.00155) **[abstract via search]**.

**Why it matters for an AI-authored-model → render-target system.** This is the most directly relevant idea for *agent authoring*. An AI that emits a partial program/document can leave **typed holes** where it is unsure, and the artifact remains a well-typed, *runnable* object the rest of the system can typecheck, render, and even evaluate around the gaps. The "membrane around errors" property means one bad subtree does not invalidate the whole model — exactly what you want when an agent produces an 80%-correct structure and a human (or another agent, or a canvas) fills the rest. "No meaningless editor states" generalizes to "no meaningless *intermediate model states*," which is the safety property that makes incremental machine authoring against an AST tractable.

**What breaks / maturity.** Honest status: it is a **research prototype**, not production software. hazel.org positions it as "an elegant platform for research on the future of programming (and programming education)" rather than as a shippable tool, and the work lives at POPL/OOPSLA/PLDI (https://hazel.org/). It's a small ML-like language, browser-hosted; there's no ecosystem, no library story, and the structure-editing ergonomics problem (see MPS/Dark) applies to human users the same way. Its value here is the *idea* (typed holes + always-meaningful states), which is portable, more than the tool.

## 4. Dark / Darklang

**What it is.** A "holistic" backend platform: "it combines an editor with a language and infrastructure … each piece is designed specifically to work with the other pieces" (https://medium.com/darklang/the-design-of-dark-59f5d38e52d2). Its editor, **Fluid**, was a structured/projectional editor; the language was deployless ("As soon as you write code in the Dark editor, it's immediately deployed to production … There is no long build process, no tarballs, no containers") (same URL).

**How it stored the artifact.** The AST was the source of truth. Per Darklang's own retrospective, in Darklang-classic "your source of truth was an AST," every keystroke "made direct structural edits to the AST," and the FluidEditor was "a sort of 'reverse parser'" — instead of parsing text into a tree, "it took the AST and pretty-printed it into a set of FluidTokens" (https://blog.darklang.com/an-overdue-status-update/). The design rationale was the classic no-syntax-errors pitch: "Syntax errors exist because we write code as text, and then ask the compiler to read it, which sometimes it cannot," so Dark built "an editor that doesn't allow them to be added — one that speaks the language, not just plain text," yielding whole-program autocomplete and "syntax errors aren't possible" (https://medium.com/darklang/the-design-of-dark-59f5d38e52d2).

**Why it matters — and the honest failure story (this is the retrospective you were after).** Darklang is the cleanest real-world data point that **structured editing is hard specifically as a human UX**, and it's unusually candid:
- The editor was buggy and users couldn't type what they meant: the concrete example — "What should happen if a user hits the `|` key at the end of `let x = true` – are they trying to pipe (`|>`) that `true` into some following code, or are they starting a Bool 'or' (`||`)?" (https://blog.darklang.com/an-overdue-status-update/).
- Users rated it "somewhere between 'Ok I guess' and 'probably the worst part of Darklang'" (https://blog.darklang.com/an-overdue-status-update/).
- It was a massive engineering drag: the editor was "~50% of our codebase," "pretty costly to develop – the code was poorly organized, and changes needed to be carefully coordinated between our backend and client," and "a major distraction from more important work. The point of Darklang isn't to reinvent a development environment" (https://blog.darklang.com/an-overdue-status-update/).
- The fix was to **abandon structured editing and write a normal text parser + language server** so people could use VS Code (https://blog.darklang.com/an-overdue-status-update/). Note the irony directly relevant to your project: they *added a parser* to escape the structured editor — the opposite direction from "store as AST, project a view."

**The AI-changes-the-calculus evidence (strongest primary source in this whole report).** Darklang's "going all-in on AI" post makes the argument explicitly, and it cuts *against* human structured editing while cutting *for* structural language properties:
- "As well as no longer being important in a world of generated code, the old editor's code was pretty awful" (https://blog.darklang.com/gpt/).
- "Do we expect that in 3-5 years time developers will still be typing out artisanal code at a keyboard? I struggle to see it." (https://blog.darklang.com/gpt/).
- Structure still helps the *machine*: "static typing can provide excellent feedback that generated code will work, and the better the static typing, the better the feedback," and immutability helps because "AIs do much better on code directly in front of them than on far-away state being modified indirectly" (https://blog.darklang.com/gpt/).
- In the restructuring post: "Our online structured editor didn't make sense when the LLM is generating the code," while "Immutability was the secret sauce of Darklang v1" is retained (https://blog.darklang.com/goodbye-dark-inc-welcome-darklang-inc/).

**Company fate.** Dark Inc "burned cash too quickly between 2017 and 2020," "The product wasn't quite good enough back then to raise a Series A," and by 2025 "an 8 year old product with no traction was not going to attract new investment"; the company shut down and the language was sold to employees (new Darklang Inc, open-sourced, "designed to safely run anywhere") (https://blog.darklang.com/goodbye-dark-inc-welcome-darklang-inc/). Simon Willison preserves the founder quote confirming the June 16, 2025 shutdown: Dark Inc "ran out of money," and the board "believed that the best way forward was to shut down the company … an 8 year old product with no traction was not going to attract new investment" (https://simonwillison.net/2025/Jun/16/paul-biggar/).

The takeaway the user should weight heavily: **the one company that built exactly "AST source of truth + structured editor + no text files + deployless," in production, with real users, concluded the structured *editing* was its worst part and that LLM code-gen removed its remaining rationale** — but it kept the structural language *properties* (types, immutability) as the thing that helps AI.

## 5. Unison

**What it is.** A language "built around one big idea: let's identify a definition by its actual contents, not just by the human-friendly name" (https://www.unison-lang.org/docs/the-big-idea/). Reached 1.0 in production (https://www.unison-lang.org/unison-1-0/).

**How it stores the artifact (concrete data structure).** Content-addressed by hash of the syntax tree:
- "Each Unison definition is identified by a **hash of its syntax tree**." Before hashing, the code is normalized: "all named arguments are replaced by positionally-numbered variable references, and all dependencies … are replaced by their hashes" (https://www.unison-lang.org/docs/the-big-idea/). So identity = structure + transitive dependency hashes, independent of names and formatting. (The hash is SHA3-512 per secondary sources — https://byteiota.com/unison-1-0-content-addressed-code-hits-production/ **[search-indexed]**.)
- Names are decoupled: "names are just separately stored metadata that don't affect the function's hash" (https://www.unison-lang.org/docs/the-big-idea/).
- The codebase is a **database, not text files**: "a proper database which knows the type of everything it stores, has a perfect compilation cache, perfect knowledge of dependencies, indices for type-based search" (https://www.unison-lang.org/docs/the-big-idea/). Concretely it's **SQLite** in `~/.unison` — the SoftwareMill walkthrough: "Looking at the extension of the file in `~/.unison`, it's using SQLite," storing "abstract syntax trees, or rather some representation of them … keyed by their hashes" (https://softwaremill.com/trying-out-unison-part-1-code-as-hashes/). In April 2021 Unison "switched from git-style, filesystem-based database to new SQLite format for 100x codebase size reduction" (https://www.unison-lang.org/unison-1-0/). LWN frames it neutrally: code lives in "an append-only, content-addressed database" and the hash "encodes not just the code itself but its exact dependencies" (https://lwn.net/Articles/978955/).

**The editing workflow (important — this is where the plain-text loss bites).** You do *not* edit the database directly. You use `ucm` (Unison Codebase Manager), which "monitor[s] all `*.u` files in the current directory. Whenever you save … it will be parsed and the `ucm` will either report syntax errors or suggest adding new or modified definitions to the codebase." To change existing code you run `edit [name]`, which "render[s] a textual representation of the function, using the names that are currently associated with the function's hash, into the scratch file" (https://softwaremill.com/trying-out-unison-part-1-code-as-hashes/). LWN: on save the system "reads the code, and then presents any problems with it, or offers to update the database," and "code is always formatted when the programmer goes to read or edit it" (https://lwn.net/Articles/978955/). So text is a *transient projection materialized on demand* — precisely the "canvas is a projection" model, but for code.

**What content-addressing buys (why it matters for AI-authored models).**
- **No builds / perfect caching**: "Once anyone has parsed and typechecked a definition and added it to the codebase, no one has to do that ever again" (https://www.unison-lang.org/docs/the-big-idea/). For an agent regenerating large models, unchanged subtrees keep their hash and never recompile/re-render.
- **Non-breaking rename & no dependency hell**: because references are by hash and names are metadata, "dependency conflicts and the diamond dependency problem are just not a thing" (https://www.unison-lang.org/docs/the-big-idea/).
- **Never-broken codebase**: "A Unison codebase is never in a broken state, even midway through a refactoring" (https://www.unison-lang.org/docs/the-big-idea/) — the Hazel "no meaningless states" property at the codebase level. Very attractive when an agent is mid-edit.
- **Structural diff/merge for free**: merge conflicts "only happen when two people actually modify the same definition; not because you moved some stuff around in your files" (https://www.unison-lang.org/unison-1-0/) — the same move-vs-edit win MPS gets from UUIDs, here from content hashes.

**What breaks / honest maturity.**
- **The 40-years-of-text-tooling loss is real and named.** "Developers have spent 40 years perfecting text-based workflows: grep, diff, Git. Unison throws that out for a database-first approach" (https://byteiota.com/unison-1-0-content-addressed-code-hits-production/ **[search-indexed]**). Because code lives in SQLite, ordinary `grep`/`git` don't apply to the codebase; Unison had to **build its own VCS** — "a native version control system: with projects, branches, clone, push, pull, merge" plus Unison Share for "code contributions (pull requests), code review" (https://www.unison-lang.org/unison-1-0/). You trade the entire git/grep/PR ecosystem for a bespoke reimplementation.
- **DX friction with hashes.** During refactors "you'll get the hashes in the scratch file," cryptic references that complicate editing — "one of the areas of the 'developer experience' that they are working on" (https://softwaremill.com/trying-out-unison-part-1-code-as-hashes/).
- **All-or-nothing + ecosystem gaps.** LWN: "Unison's greatest benefits only come when an entire program is written in it," "Unison doesn't even have a stable foreign-function interface (FFI)," you must "reimplement a lot of functionality that is already present in other languages," and dependency updates rely "on all of the affected code being locally available for development." It "remains pre-1.0" in maturity terms with "performance problems, occasional bugs in the runtime, unstable interfaces" (https://lwn.net/Articles/978955/). The 1.0 page confirms C FFI was still "underway" and records/library-management/sync-speed were roadmap items (https://www.unison-lang.org/unison-1-0/).

## Cross-cutting: the non-obvious tradeoffs

### The loss of plain-text tooling is the deepest, least-reversible cost
Every system pays it and every system has to *rebuild* the ecosystem it discarded:

| System | Storage | VCS story | Grep/diff |
|---|---|---|---|
| MPS | Node graph w/ UUIDs → XML | Custom diff/merge tools required (https://www.jetbrains.com/help/mps/mps-faq.html) | UUID-based structural diff; no meaningful text grep |
| Intentional IDW | Intentional tree / DB | Unsolved; Fowler names it the #1 blocker (https://martinfowler.com/articles/languageWorkbench.html) | N/A |
| Hazel | Typed AST + holes (zipper) | None (research) | N/A |
| Dark | AST + FluidTokens | — (abandoned; then adopted text + LSP) (https://blog.darklang.com/an-overdue-status-update/) | none → *why they reverted to text* |
| Unison | Content-hashed AST in SQLite | Bespoke native VCS + Unison Share (https://www.unison-lang.org/unison-1-0/) | no git/grep on codebase (https://byteiota.com/... **[search-indexed]**) |

The pattern: you don't just "lose grep/diff/git," you inherit the obligation to *reimplement* diff, merge, code review, and search — and Fowler's lock-in warning ("tied to that language workbench … no standard for interchange," https://martinfowler.com/articles/languageWorkbench.html) means that reimplementation is non-portable.

### The editing-ergonomics problem is a *human* problem
- Dark: users called the structured editor "probably the worst part of Darklang" and couldn't "just type their code" (https://blog.darklang.com/an-overdue-status-update/).
- MPS: "can feel odd," needs days to acclimate, and text-like notations frustrate text expectations (https://www.jetbrains.com/help/mps/mps-faq.html; SLE 2014 **[search-indexed]**).
- IDW: "unusable for normal folks," LISP-squared learning curve (https://medium.com/@dslmeinte/intentional-software-bought-by-microsoft-2606e6eb1106).
- FSE 2016: only efficient for basics without training; complex editing needs real AST fluency (https://voelter.de/... **[search-indexed]**).

This is the single most important insight for your use case: **the ergonomic objection is almost entirely about a human driving the structured editor by hand.** If the *author is an AI agent* emitting structure against the model, and the *human sees a projection (the canvas)*, the ergonomic tax largely evaporates — the agent doesn't get frustrated by the `|` vs `||` ambiguity, and the human never touches the raw tree. What does *not* evaporate is the tooling-ecosystem cost (diff/merge/review/grep/version-control of structured data) and the lock-in.

### Why the companies failed/pivoted (distinct causes, not one story)
- **Intentional**: not capability — *learnability + no shipped proof point + no ecosystem*; folded into MS Office productivity, vision shelved (https://martinfowler.com/bliki/IntentionalSoftware.html; https://medium.com/@dslmeinte/...; https://en.wikipedia.org/wiki/Intentional_Software).
- **Dark**: the structured editor was 50% of the codebase, buggy, a distraction from the actual product, and users hated it; separately, the *company* ran out of money with no traction (https://blog.darklang.com/an-overdue-status-update/; https://blog.darklang.com/goodbye-dark-inc-welcome-darklang-inc/).
- **Unison**: hasn't failed — it shipped 1.0 — but its adoption ceiling is the all-or-nothing ecosystem gap and the cost of living outside git/grep (https://lwn.net/Articles/978955/).
- **MPS**: didn't fail; it's the existence proof that the model *can* work in industry if you accept the tooling investment.

### Does AI/LLM authorship change the text-vs-structure calculus? (mixed, sourced)
- **Against structure (human-editor sense):** Darklang's explicit conclusion — the structured editor "didn't make sense when the LLM is generating the code," and they *added a text parser + LSP* to move onto VS Code (https://blog.darklang.com/goodbye-dark-inc-welcome-darklang-inc/; https://blog.darklang.com/an-overdue-status-update/). LLMs are trained overwhelmingly on text and are fluent producing it; a structured editor is friction for both the human and, arguably, the harness around the model.
- **For structure (machine-consumed properties):** the *same* Darklang argues structural language properties help AI — better static typing gives "excellent feedback that generated code will work," and immutability helps because "AIs do much better on code directly in front of them than on far-away state" (https://blog.darklang.com/gpt/). Hazel's typed holes and Unison's never-broken/perfectly-cached codebase are exactly the invariants that make *incremental machine editing* safe (https://hazel.org/; https://www.unison-lang.org/docs/the-big-idea/).

**Synthesis for your architecture (my analysis, flagged as such):** the honest reading of these five is that the winning combination for an AI-authored-model → render-target system is *not* "make humans edit structure" (that's what killed Dark's UX and Intentional's adoption) but "**let the agent author against a structured/typed model with hole-tolerance and content-stable identity, materialize text/canvas as an on-demand projection, and — critically — budget up front for the reimplementation of diff/merge/review/search that you forfeit by leaving plain text.**" MPS (UUID move-vs-delete diff), Unison (hash-stable identity, never-broken codebase, structural merge), and Hazel (typed holes = no meaningless intermediate states) each contribute a proven-useful piece; the graveyard (Intentional, Dark's editor) is where teams made *humans* pay the structured-editing tax without a compensating ecosystem.
