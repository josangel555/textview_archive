# Higher-level UI description languages, visual-builder internal models, declarative frameworks, tokens, and machine-authored IRs

## 0. The one structural insight that cuts across everything

Nearly every serious system in this space — hand-authored or machine-authored, 2005 or 2026 — converges on the **same shape**: a *recursive tree of typed nodes*, where each node is `{ type, props/attrs, style, children }`, styling is factored out into a *referenced* token/style layer rather than inlined, and dynamic behavior (data binding, conditionals, loops, events) is expressed as *first-class node/field types* rather than embedded code strings. HTML/CSS/JS is treated as a **compile target**, not the authoring surface. The interesting differences are all in *where the expressiveness ceiling sits* and *how the dynamic/behavioral layer is modeled* — that's where these systems succeed or break. I'll return to this in the closing section because it's the load-bearing conclusion for the design problem.

## 1. Visual-builder / no-code internal document models

### 1.1 TeleportHQ UIDL — the purest "JSON IR for UI" in the wild

**What it is.** A framework-agnostic JSON "User Interface Definition Language" explicitly designed as an *intermediary format between creation tools and code generators*, so the same UI can be emitted to React/Vue/HTML and migrated between them ([docs.teleporthq.io/uidl](https://docs.teleporthq.io/uidl/)).

**How it models the document (concrete).** A component is `{ name, node, propDefinitions, stateDefinitions, styleSetDefinitions }`. The `node` is a recursively-nested discriminated union of `{ type, content }` where `type` ∈ ([docs.teleporthq.io/uidl/structure.html](https://docs.teleporthq.io/uidl/structure.html)):
- `static` — literal text/number passed through unchanged (`{"type":"static","content":"100px"}`)
- `dynamic` — a runtime reference: `{"type":"dynamic","content":{"referenceType":"prop|state|local|attr|children|token","id":"fieldName"}}`
- `element` — the visual node: `{"elementType":"container","style":{},"attrs":{},"children":[],"events":{}}`
- `conditional` — `{node, reference, value}`
- `repeat` — `{node, dataSource, meta:{iteratorName,useIndex}}`
- `slot`, `nested-style`

Styles are per-property objects that are themselves `static` or `dynamic`, and media queries are modeled as `nested-style` nodes (`"@media(max-width: 320px)": {"type":"nested-style", ...}`). The full spec ships as a JSON Schema *and* TypeScript interfaces.

**Why it matters.** This is almost a spec-sheet answer to the design problem: a machine-friendly, human-readable JSON that (a) separates static vs dynamic vs styling concerns, (b) makes control flow (`conditional`/`repeat`) explicit rather than code, and (c) has an authoritative schema an LLM can be constrained against. It is one of the very few formats *explicitly designed to be generated by tools rather than typed*.

**What breaks / maturity.** The docs themselves flag `events` as **"an experimental feature with limited capabilities."** That is the tell: the *structural/visual* layer is mature and clean, but the *interactive/behavioral* layer (the hard 20%) is where the abstraction thins out. Project Teleport / teleportHQ has also lost commercial momentum over the years (UNVERIFIED as to current maintenance intensity — the docs and repo are live but activity is modest).

### 1.2 Plasmic — a rich, production internal model exposed as a Model API

**What it is.** A visual builder whose *internal* project representation is exposed via a "Project Model API" returning JSON — the tree of elements that make up any page/component ([docs.plasmic.app/learn/model-quickstart](https://docs.plasmic.app/learn/model-quickstart/)).

**How it models the document (concrete).** Root is a `site` object holding `styleTokens`, style presets, `globalVariants`, `userManagedFonts`, `globalContexts`, `activeTheme`, `splits`, and `components`. Each component has `{type (page|component), metadata, pageMeta, variants, tplTree}`. The `tplTree` is a tree of **TplNodes**:
- `TplTag` — a normal HTML element (`tag`, `children`, `text`)
- `TplComponent` — an instance of a Plasmic *or code* component
- `TplSlot` — slot definitions

Styling/props live in **variant settings (`vsettings`)** on each node: `rs` (the CSS rulesets), `attrs` (element props), `args` (component props incl. slot args). Every object carries `__type` (e.g. `Component`, `StyleToken`) and an internal id `__iid`; cross-project references add a `__uuid`.

**Why it matters.** Plasmic is the strongest example of the pattern taken to production maturity: **variants as a first-class dimension of the model** (a node's styles are keyed by which variant combination is active), tokens at the root, and a clean escape hatch — arbitrary React **"code components"** register into the same tree, so the model never fully boxes you in. That escape hatch is exactly how it survives the 20% ceiling (§6.2).

**What breaks / maturity.** Mature and code-first (it has real codegen and two-way integration with a real repo), but the model is *proprietary and large* — `rs` stores CSS rulesets, so the "abstraction over CSS" is thin (it stores CSS, it doesn't replace it). The complexity of `vsettings`×variants is real: the model is not something a human hand-writes, which is fine for the problem here but signals how much machinery correct variant/state handling actually requires.

### 1.3 Builder.io + Mitosis — the "LLVM for front-end" and a WYSIWYG-canvas-to-JSON pipeline

This is two coupled things, and together they're the closest existing analogue to the stated design problem.

**Builder.io visual editor (the canvas → JSON half).** The drag-and-drop editor stores content as a tree of **blocks** (text/image/button/custom-code-component). The editor and app communicate by **messaging down JSON and then sending patches** on edit; custom components register a *name→reference map* plus their input schema so the editor knows what exists and what inputs each takes; at render time the SDK **iterates the blocks and renders components in the target framework** ([builder.io/c/docs/how-builder-works-technical](https://www.builder.io/c/docs/how-builder-works-technical), [builder.io/c/docs/visual-editor](https://www.builder.io/c/docs/visual-editor)). Note the **registration-of-a-component-vocabulary** move — the canvas can only place components the host app has declared. That's the SDUI pattern (§5.4) reappearing in a design tool.

**Mitosis (the JSON-IR → many-frameworks half).** Explicitly framed as *"a compiler for the frontend, analogous to LLVM"* — one common IR, many code generators ([builder.io/blog/mitosis-a-quick-guide](https://www.builder.io/blog/mitosis-a-quick-guide), [github.com/BuilderIO/mitosis](https://github.com/BuilderIO/mitosis)). The IR is **`MitosisComponent`**, described as "the single source of truth," containing `name`, `imports`, `exports`, state (`useState`/`useStore`), lifecycle hooks (`onInit`/`onMount`/`onUpdate`/`onUnMount`), `useContext`, `useRef`, and a JSX tree of **`MitosisNode`** = `{ name, properties, bindings, children, meta }` ([deepwiki.com/BuilderIO/mitosis](https://deepwiki.com/BuilderIO/mitosis)). Crucially the pipeline is symmetric: **parsers** (`parseJsx`, `parseSvelte`, `parseAngular`, `parseBuilder`) all normalize *into* the IR, and **generators** (`componentToReact`, `componentToVue`, …) consume it — including `parseBuilder`, which turns **Builder.io's visual-editor JSON directly into the IR**.

**Why it matters.** This is the exact architecture the design problem is reaching for: *WYSIWYG canvas → structured JSON → IR → compile to HTML/CSS/JS (and React/Vue/etc.)*. The `bindings`-vs-`properties` split on each node (reactive expressions vs static attributes) is the clean way to model "some props are literal, some are data-driven" without embedding code. And the LLVM framing is the right mental model: define the IR once, write N backends.

**What breaks / maturity.** Mitosis deliberately accepts only a **static subset of JSX** (inspired by Solid) so it can be statically parsed — the price of "compile to everything" is that you *cannot* author in the full expressiveness of any one framework. That's the impedance mismatch in its most honest form: the IR is the *intersection* of what all targets can do, not the union. Complex framework-idiomatic code doesn't round-trip. (Maturity: actively developed, used inside Builder, but historically has had rough edges on advanced components — treat as "solid core, sharp corners.")

### 1.4 Webflow — hierarchical node tree with a *shared class* styling model

**What it is.** A commercial visual web builder. Two relevant representations: the **Data API** resource model ([developers.webflow.com/data/reference/structure-1](https://developers.webflow.com/data/reference/structure-1)) and, more revealingly, the **clipboard/copy-paste format** `@webflow/XscpData`.

**How it models the document (concrete).** The `XscpData` payload is `{ type:"@webflow/XscpData", payload:{ nodes:[...] } }` where each node has `_id`, `tag`, `classes` (an array of **class IDs**, not inline styles), `children`, `type` (Webflow component type e.g. `"Image"`), and `data` (attributes like `src`) ([discourse.webflow.com XscpData thread](https://discourse.webflow.com/t/how-to-convert-html-sections-to-webflow-xscpdata-type-json-format/203987)). **NOTE: this comes from community/forum reverse-engineering, not official spec docs — treat the exact field list as reliable-but-unofficial (UNVERIFIED as canonical).**

**Why it matters.** The key modeling decision is **styling via referenced classes, not inline style objects** — Webflow's whole value prop is that it authors *reusable CSS classes* the way a hand-coder would, which is why its output is comparatively clean vs old WYSIWYG tools. That's a direct lesson: model style as *named, referenced, reusable* units, never as per-node inline blobs.

**What breaks / maturity.** Mature and popular, but the canonical no-code lock-in case (§6.4): the design lives in Webflow's model, export is a snapshot, and there's no real round-trip back from edited code.

### 1.5 Framer — React-native canvas, weak public IR

**What it is.** A design/site builder that is *itself built on React* and renders the canvas, preview, and published site through React + a Virtual DOM; "code components" are literally React components that render on the canvas ([framer.com/blog/why-framer-uses-react-to-build-sites](https://www.framer.com/blog/why-framer-uses-react-to-build-sites/), [framer.com/developers/components-introduction](https://www.framer.com/developers/components-introduction)).

**How it models the document.** Search surfaced a claim that Framer's project structure is an **"XML representation of pages, components, and code files."** **UNVERIFIED — weak source; Framer's internal document model is not publicly documented.** What *is* verifiable is that the render substrate is React and that it can export components as React code.

**Why it matters / breaks.** Framer is the cleanest case of "the tool's substrate == the target technology" (React all the way down), which minimizes impedance mismatch but maximizes lock-in to that one target. Worth noting as a design axis: *should the canvas render through the same engine it compiles to?* Framer says yes; TeleportHQ/Mitosis say no (neutral IR).

### 1.6 Penpot — "designs as open code," W3C-token-native

**What it is.** Open-source Figma alternative whose pitch is that designs *are* real code — it renders SVG-native and exposes SVG/CSS/HTML directly in the inspect panel, storing layout as real CSS (`flex`, `gap: 16px`, `border-radius: 8px`) rather than proprietary units ([github.com/penpot/penpot](https://github.com/penpot/penpot); the "designs as code" framing per multiple secondary sources — treat the marketing gloss with mild caution, the *internal* store is a structured model, not literally SVG-on-disk).

**Why it matters (the standout).** Penpot is **the first design tool to implement design tokens natively against the W3C DTCG draft** ([Smashing Magazine, May 2025](https://www.smashingmagazine.com/2025/05/integrating-design-code-native-design-tokens-penpot/); [help.penpot.app/user-guide/design-tokens](https://help.penpot.app/user-guide/design-tokens/); [penpot.app/blog/design-tokens-with-penpot](https://penpot.app/blog/design-tokens-with-penpot/)). It exposes tokens via API *in the standardized format, no conversion*. For the design problem, Penpot is the proof that a visual canvas can author *directly against the token/component vocabulary* and emit standards-based output.

**What breaks / maturity.** Token *plugin* API is still in-flight ([penpot#7916](https://github.com/penpot/penpot/issues/7916)). And "layout as real CSS" is honest only up to what the tool exposes — the same impedance ceiling applies (advanced CSS the editor doesn't surface isn't authorable).

## 2. Declarative UI frameworks as "a model that compiles/reconciles to a render target"

These aren't authoring formats for documents, but each embodies a design pattern the problem must solve. The recurring lesson: **the thing you write is a lightweight description; a heavier runtime tree does the actual work, and reconciliation between them is the hard part.**

| Framework | Authored surface | Intermediate/runtime model | Render target | Lesson for the problem |
|---|---|---|---|---|
| **React / JSX** | JSX (sugar for `createElement`) | Virtual DOM tree, diffed/reconciled | Real DOM | Description is cheap & disposable; a persistent tree + diff is what makes edits fast |
| **Flutter** | Widget tree (immutable) | **Element tree** (mutable, persistent) → **RenderObject tree** | Skia/Impeller pixels | **Three trees**, not one |
| **Jetpack Compose** | `@Composable` functions | **SlotTable** (gap-buffer flat array) + Snapshot system | Android canvas | The model can be a *linear buffer*, not a pointer tree |
| **SwiftUI** | `@ViewBuilder` result-builder DSL | View value tree encoded *in the type system* | UIKit/AppKit | The tree can live in *types*, compiled away |
| **Elm / elm-ui** | Pure functions, `Model→view` | Virtual DOM; elm-ui's own layout algebra | HTML/CSS (as *output target*) | A *constrained* model can delete whole bug classes |
| **Qt QML** | Declarative object-tree markup | Object tree + property-binding graph | Qt Quick scene graph | Reactive **property bindings** as the data-flow model |

**Flutter's three trees** ([docs.flutter.dev/resources/inside-flutter](https://docs.flutter.dev/resources/inside-flutter); [ente.io/blog/tech/flutter-keys-elements-and-renderobjects](https://ente.io/blog/tech/flutter-keys-elements-and-renderobjects/)): the *Widget* tree is the immutable declarative blueprint you author; because widgets can't remember parent/child relationships, a persistent *Element* tree holds identity and does reconciliation on `setState`; the *RenderObject* tree does layout/paint/hit-test. **Direct relevance:** your authored document ≠ your live editing tree ≠ your render output. Treating them as one thing is a classic mistake; keeping a stable identity/element layer is what makes incremental edits and animation tractable.

**Jetpack Compose's SlotTable** ([Leland Richardson, "Under the hood of Compose"](https://medium.com/androiddevelopers/under-the-hood-of-jetpack-compose-part-2-of-2-37b2c20c6cdd); [ProAndroidDev gap-buffer](https://proandroiddev.com/understanding-gap-buffers-in-jetpack-compose-the-60-year-old-algorithm-powering-modern-android-ui-a07ca2013e64)): the entire composition — every group, remembered value, identity — is stored in a **flat array with a movable gap buffer** (the same 60-year-old algorithm text editors use), holding the tree in *depth-first execution order*. Insert/delete/skip are near-constant-time by moving the gap. **Non-obvious lesson:** the "UI tree" doesn't have to be a tree of heap objects; a cache-friendly linear buffer with positional memoization can be dramatically faster for the update-heavy workload a live canvas generates.

**SwiftUI result builders** ([SwiftLee on @ViewBuilder](https://www.avanderlee.com/swiftui/viewbuilder/)): `@ViewBuilder` is a Swift *result builder* — a compiler feature for building DSLs — that turns a block of child views into a single value: multiple children become a `TupleView`, `if/else` becomes `_ConditionalContent` via `buildEither`, and `some View` (opaque return) keeps the concrete type fixed at compile time. The view hierarchy is **encoded in the type system**, not just at runtime. **Lesson:** control flow (conditionals, lists) can be modeled as *typed structural nodes* (`_ConditionalContent`) — precisely mirroring UIDL's `conditional`/`repeat` node types. Two independent designs reached the same factoring.

**Elm / elm-ui** ([github.com/mdgriffith/elm-ui](https://github.com/mdgriffith/elm-ui); [korban.net elm-ui intro](https://korban.net/posts/elm/2018-11-17-elm-ui-introduction/)): elm-ui is a *replacement* for HTML+CSS "which it treats as an output target," built on two ideas — (1) get the compiler to verify layout/styling by expressing it in typed Elm code, and (2) keep styles **local to each element** so there's a single place representing layout, rather than bouncing between HTML and remote CSS files. **This is the most important framework lesson for the problem:** a *deliberately constrained* styling model eliminates entire classes of CSS bugs (specificity wars, cascade surprises, action-at-a-distance) — at the cost of not being able to express everything CSS can. That trade is the whole game (§6.3).

**QML** ([en.wikipedia.org/wiki/QML](https://en.wikipedia.org/wiki/QML); [doc.qt.io/qt-6/qtqml-syntax-propertybinding](https://doc.qt.io/qt-6/qtqml-syntax-propertybinding.html)): a QML document *is* a hierarchical object tree with properties, and its defining feature is **property bindings** — assign a property a JS expression and the engine tracks dependencies and auto-re-evaluates on change. **Lesson:** model data-flow as declarative reactive bindings between properties rather than imperative event handlers — this is exactly UIDL's `dynamic` reference and Mitosis's `bindings`, generalized.

## 3. Design tokens as the *authoring vocabulary* (compose against tokens + components, not raw CSS)

### 3.1 W3C DTCG Design Tokens Format Module

**What it is.** A community-group JSON interchange format for design tokens; JSON chosen for broad language support and low barrier to entry ([designtokens.org/tr/drafts/format](https://www.designtokens.org/tr/drafts/format/); [designtokens.org](https://www.designtokens.org/)).

**How it models a token (concrete).** A token is a name→object with `$value` (mandatory), plus optional `$type`, `$description`, `$extensions` (vendor namespace, reverse-DNS keys), `$deprecated`. **Groups** are objects *without* `$value` and can set a default `$type` that children inherit. Types include primitives (`color` as `{colorSpace, components[], hex}`, `dimension` as `{value, unit}`, `duration`, `fontFamily`, `fontWeight`, `cubicBezier`, `number`) and **composites** (`shadow`, `border`, `transition`, `typography`, `gradient`) built from sub-values. **Aliases** use curly-brace refs (`"{colors.blue}"`) resolving to another token's `$value`; property-level refs use RFC-6901 JSON Pointer via `$ref` (e.g. `"#/colors/blue/$value/components/0"`); groups can inherit via `$extends`. Circular refs forbidden. ([Style Dictionary DTCG notes](https://styledictionary.com/info/dtcg/) corroborate the format.)

**Why it matters.** This is the standard way to give a machine authoring-time a *semantic vocabulary* — "spacing.md," "color.primary" — that resolves to concrete CSS at compile time. An LLM emitting `"$value":"{color.primary}"` is both more constrainable *and* more maintainable than one emitting `#0066cc`. Aliasing + composite types mean the token layer can carry most of what `style` objects otherwise inline.

**What breaks / maturity — read the warning.** The draft literally says: *"Do not attempt to implement this version… Do not reference this version as authoritative."* It is **not a W3C standard and not on the standards track**, still under active churn (the `color` object form and `$extends` are relatively recent and contested). Tooling (Tokens Studio, Style Dictionary, Penpot) tracks *different draft snapshots*, so "DTCG-compatible" files don't always interoperate today. Build against it, but pin a version and expect drift.

### 3.2 Airbnb Lona — tokens + components as JSON, compiled cross-platform (the cautionary predecessor)

**What it is.** A toolchain where a **design system is defined in JSON** — components, colors, text styles, gradients, shadows, data types — and the **Lona Compiler** emits UI code for Web (React), iOS (Swift), Android (Kotlin), React Native, plus Sketch files ([github.com/Lona/Lona](https://github.com/Lona/Lona); [FlatTokens example](https://github.com/Lona/Lona/blob/master/examples/FlatTokens/README.md)). It predates and prefigures DTCG: `.component` files as JSON, a "flat tokens" exchange representation, and Lona Studio as the GUI over the JSON.

**Why it matters.** It's a full realization of "author against tokens + components → compile to multiple native targets," from a team (Airbnb DLS) that had the cross-platform-consistency problem for real.

**What breaks — the honest maturity flag.** Airbnb itself states it **does not support the project and its code/tests are *not* at the rigor of other Airbnb projects.** It's effectively dormant. The lesson isn't "the idea failed" — Airbnb pivoted the *same* idea into server-driven UI (§5.4) — it's that **a bespoke multi-target compiler is a large, ongoing maintenance liability**, and the org chose a runtime-interpreted approach over a compile-time one.

## 4. Machine/LLM-generated IRs — representations *meant to be produced by machines*

This is the richest and least-obvious part of the assignment.

### 4.1 pix2code (2017) — the origin of "learn a UI DSL, don't emit pixels"

Beltramelli's pix2code ([arxiv.org/pdf/1705.07962](https://arxiv.org/pdf/1705.07962); [github.com/tonybeltramelli/pix2code](https://github.com/tonybeltramelli/pix2code)) generated code from a single GUI screenshot via CNN(vision)+LSTM(language) → a **domain-specific language**, not raw code. Key finding: the model learns *layout and hierarchical structure* well but **struggles with color/style specifics and long lists**. **Non-obvious takeaway that keeps recurring:** machines are good at getting the *structural tree* right and bad at the *fine visual/style detail* — which argues for a representation that pins structure crisply and delegates precise styling to a token/reference layer the model doesn't have to hallucinate.

### 4.2 RICO (2017) — UI as a DOM-like semantic tree, at dataset scale

RICO ([interactionmining.org/rico](https://interactionmining.org/rico); [ACM PDF](https://dl.acm.org/doi/pdf/10.1145/3126594.3126651)) captured 66k+ screens from 9.3k apps, each as screenshot + **view hierarchy JSON structurally similar to a DOM tree**: per node, the component class, text content, bounding box, and interactive flags (clickable/focused/scrollable). Follow-ons (Screen2Vec, Screen2Words) learn embeddings over this. **Takeaway:** the field's consensus machine-readable UI representation is *exactly* the `{class, bounds, text, flags, children}` tree — reinforcing that a typed node tree is the natural target for ML both to consume and to produce.

### 4.3 DesignAsCode (2026 preprint) — the direct, recent answer: generate HTML/CSS as the IR, with a render-in-the-loop reflection stage

This paper ([arxiv.org/html/2602.17690](https://arxiv.org/html/2602.17690)) is almost purpose-built commentary on the design problem. **NOTE: recent preprint; treat findings as promising-but-not-yet-replicated.**

- It frames the exact tension you named: T2I models give **visual fidelity but zero editability** (fused raster); layout-generation gives **editability but weak visuals**; hybrids fail from *rigid primitive representations*, *fixed-schema composition*, and *open-loop workflows*.
- Its thesis: **use executable HTML/CSS as the design representation**, because code natively supports `backdrop-filter`, `mix-blend-mode`, complex gradients — "professional-grade styling impossible in primitive representations like JSON coordinate lists."
- **Ablation, quantified:** replacing HTML/CSS with JSON *"severely impacts subjective metrics"* (Layout subjective score dropped 63.67 → 58.07). Removing the render-in-the-loop reflection caused *"significant degradation across most metrics."*
- Pipeline: **Semantic Planner** (fine-tuned LLM builds *variable-depth* hierarchies from content semantics — explicitly *not* a fixed schema) → **HTML Composer** → **Visual-Aware Reflection** that *renders the HTML to pixels, compares to target, and edits the code*, because "code generation is inherently an open-loop system blind to rendering artifacts."

**Two non-obvious, directly-actionable findings:** (1) a *too-constrained* IR (bare JSON coordinate lists) measurably *hurts* visual quality vs code — the expressiveness ceiling is not free; (2) you cannot trust generated structure without **rendering it and closing the loop** — the model is blind to its own visual output. Any WYSIWYG-from-agents system needs a render-and-inspect feedback stage, not just generate-and-ship. (This also independently validates your own project's "confirm on the real UI" directive.)

### 4.4 Server-Driven UI (Airbnb Ghost Platform, Lyft Canvas) — the production pattern for "backend/agent emits UI data, client renders"

The most battle-tested realization of "an authority emits a UI *document*, a renderer interprets it against a fixed component vocabulary" ([Airbnb deep dive](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5); [InfoQ summary](https://www.infoq.com/news/2021/07/airbnb-server-driven-ui/); [SDUI overview](https://medium.com/@aubreyhaskett/server-driven-ui-what-airbnb-netflix-and-lyft-learned-building-dynamic-mobile-experiences-20e346265305)).

**Airbnb Ghost Platform model (concrete):** one shared GraphQL schema across web/iOS/Android. A screen response = a **`sections` array** (self-contained, pre-formatted, pre-localized data models, each with a `SectionComponentType` like `TITLE`/`PLUS_TITLE`) + a **`screens` array** defining layouts and where sections go + presentation metadata (modal/bottom-sheet/full-screen). Clients hold native **Section Components** (Kotlin/Swift/TS) that map *one section data model → one rendering*, and **ILayout** implementations that place sections. Interactions are **`IAction` objects** in the response; generic actions (navigate/scroll) are handled universally, custom ones per-feature.

**The load-bearing design constraint (and why):** sections are *"entirely independent of other sections and the screen on which they are displayed."* That independence — plus a **deliberately limited, reusable component vocabulary** — is what makes the whole thing tractable and cross-platform. The article is explicit that the cost is up-front generalization work: you must *"generalize the shared aspects… and account for each page's idiosyncrasies in a consistent, thoughtful way."*

**Lyft Canvas:** same idea, **Protocol Buffers instead of GraphQL/JSON**; primitives = buttons/layouts/action-callbacks in protobuf; claimed **40–60% smaller payloads and faster serialization**, cutting experiment delivery from ~2 weeks to ~2 days ([same SDUI overview](https://medium.com/@aubreyhaskett/server-driven-ui-what-airbnb-netflix-and-lyft-learned-building-dynamic-mobile-experiences-20e346265305)) — **the payload-size numbers are from a secondary summary, UNVERIFIED against Lyft primary sources.**

**Why it matters most:** SDUI *is* the "agent authors a UI document that compiles/renders" problem, solved in production, and its hard-won lesson is unambiguous — **constrain to a curated component/section vocabulary with independent, self-contained nodes and a small closed set of actions.** Open-ended expressiveness is the enemy of a renderable, cross-target, machine-emitted UI document.

### 4.5 Generative UI (Vercel v0 / AI SDK 3.0) — LLM emits component *invocations*, not markup

v0 generates React/Tailwind/shad-ui components from prompts, iteratively refinable ([vercel.com/blog/announcing-v0-generative-ui](https://vercel.com/blog/announcing-v0-generative-ui)). More architecturally interesting is **AI SDK 3.0 "Generative UI"**: instead of returning text, the model's **tool calls stream React Server Components** — the LLM chooses *which registered component to render with which props*, and the framework streams the actual UI ([vercel.com/blog/ai-sdk-3-generative-ui](https://vercel.com/blog/ai-sdk-3-generative-ui)). **Takeaway:** the productionized LLM-UI pattern is *not* "LLM writes HTML"; it's "LLM selects from a registered component vocabulary and supplies props" — the SDUI insight again, arrived at from the LLM side. v0's iterate-don't-one-shot workflow also echoes DesignAsCode's reflection loop.

### 4.6 Constrained decoding / structured output — and the crucial counter-evidence

You can *force* an LLM to emit only schema-valid JSON via a logit processor that masks invalid tokens to −∞ during sampling, giving **100% schema adherence by construction**, and it can be **faster** than free generation because the grammar prunes dead-end tokens ([mbrenndoerfer.com constrained decoding](https://mbrenndoerfer.com/writing/constrained-decoding-structured-llm-output); [letsdatascience.com](https://letsdatascience.com/blog/structured-outputs-making-llms-return-reliable-json)). This is the mechanism that makes "author against a UIDL/DTCG schema, guaranteed valid" real.

**The non-obvious counterpoint you should not skip** — *"Let Me Speak Freely?"* ([arxiv.org/pdf/2408.02442](https://arxiv.org/pdf/2408.02442)): forcing structured/JSON output **degrades reasoning/task performance** versus free-form, with the gap widening on complex tasks; the mitigation is to **let the model reason freely first, then format** (severity of constraint matters more than structure per se). **NOTE: the verbatim phrasings above are the fetcher's paraphrase; the directional finding — format restriction hurts, free-reason-then-format recovers much of it — is the paper's established result.** **Design implication:** don't make the agent *think* in the constrained IR. Let it reason/plan in natural language, then emit the schema-constrained document as a final, separate step. Grammar-constrain the *output*, not the *cognition*.

## 5. Cautionary tales & pitfalls (the part to internalize)

### 5.1 The Dreamweaver/FrontPage bloat lesson — *and* its non-obvious mitigation

WYSIWYG tools historically produced **unmaintainable, bloated, poorly-semantic, browser-fragile HTML**; FrontPage's code bloat was "aggravating and required constant fixing," especially when pasting content (it emitted piles of `<style>`/`<font>` tags to reproduce a look) ([dev.to "end of front-end"](https://dev.to/diegoeis/the-probable-end-of-the-front-end-profession-as-you-know-it); [acscreative.com](https://www.acscreative.com/insights/why-wysiwyg-editors-are-just-plain-awful/)). Root cause: the tools generated **presentational markup per-element** with no shared style abstraction — the exact opposite of Webflow's shared-class model.

**The under-appreciated mitigation history — Dreamweaver "Roundtrip HTML":** Macromedia's answer was a feature that **preserved hand-written code and never rewrote it unless explicitly asked**, letting devs move between Design and Code view non-destructively ([flylib Roundtrip HTML](https://flylib.com/books/en/2.836.1.80/1/); [Adobe coding docs](https://helpx.adobe.com/dreamweaver/using/general-information-coding-dreamweaver.html)). **Lesson for your problem:** the historical fix for "generated code is garbage" was *respect for a source of truth* — and note that Roundtrip only worked because *HTML was the source of truth*. If your source of truth is a higher-level IR, you *avoid* the bloat problem by construction (you regenerate clean output every time), but you *inherit* the round-trip problem instead (§5.2) — you can't let anyone edit the generated HTML.

### 5.2 The round-trip / two-way-sync problem — the deepest structural trap

If both the visual model *and* the generated code are editable, keeping them in sync is genuinely hard: it causes **"model–code drift"** turning models into "shelfware" ([Visual Paradigm round-trip engineering](https://guides.visual-paradigm.com/docs/mastering-uml-visual-modeling-in-the-visual-paradigm-ai-ecosystem/module-8-professional-engineering-and-global-collaboration/round-trip-engineering/)), and — critically — **two one-way pipelines do NOT compose into two-way sync**: a real bidirectional engine must *track the origin of every change (to ignore its own writes), diff at field level, and apply one shared conflict policy*, else it's "two one-way pipes wearing a trench coat" ([stacksync.com](https://www.stacksync.com/blog/the-engineering-challenges-of-bi-directional-sync-why-two-one-way-pipelines-fail)). Practitioners note true 2-way sync between code and a drag-drop editor is the holy grail precisely because it's so rarely achieved ([HN discussion](https://news.ycombinator.com/item?id=45610224)).

**Design implication (strong):** decide *one* source of truth and make code generation **one-directional** (IR → HTML/CSS/JS, regenerated, never hand-edited). Plasmic/Mitosis/SDUI all sidestep round-trip by making the model authoritative and codegen disposable. If you *must* allow code edits, you're signing up for the hardest problem in the space — budget accordingly or don't.

### 5.3 Impedance mismatch: a constrained model vs CSS's full expressiveness (the "leaky abstraction")

CSS is a global, cascading, near-Turing-expressive styling system; any higher-level model is a *lossy projection* of it. Visual tooling is called *"the ultimate leaky abstraction — the user always receives CSS no matter what tricks are used to avoid thinking about it"* ([rangle.io on CSS](https://rangle.io/blog/why-judging-css-for-being-global-misses-the-point); [Wikipedia: Leaky abstraction](https://en.wikipedia.org/wiki/Leaky_abstraction) / Spolsky's Law of Leaky Abstractions). DesignAsCode *quantified* the cost of over-constraining (§4.3): JSON coordinate lists can't express `backdrop-filter`/`mix-blend-mode`/complex gradients, and visual quality drops measurably.

**The unavoidable tension:** the *tighter* your IR (easier for agents, fewer bugs, cross-target — cf. elm-ui, Mitosis's JSX subset), the *lower* your expressiveness ceiling. The *looser* (raw HTML/CSS), the more you inherit bloat, round-trip pain, and un-constrainable output. There is no free lunch; there's only *where you put the ceiling and how you provide an escape hatch* (Plasmic's "code components," SDUI's "custom actions," DTCG's `$extensions`).

### 5.4 The no-code 80/20 ceiling and lock-in

Visual builders "accelerate the first 80% dramatically; the last 20% requires different tooling entirely," and that 20% *"often takes longer than the first 80% because it requires workarounds that create maintenance problems undetectable until something breaks"* ([channel.tel no-code ceiling](https://www.channel.tel/blog/no-code-ceiling-visual-agent-builders-production); [lowcode.agency limitations](https://www.lowcode.agency/blog/capabilities-and-limitations-of-no-code); [okoone.com](https://www.okoone.com/spark/technology-innovation/inherent-limitations-where-low-code-platforms-fall-short/)). Reported consequence: a meaningful fraction of no-code projects get **rewritten in custom code within ~2 years** (the specific "25–30% / $50k–$250k rebuild" figures are from a single secondary source — **UNVERIFIED**, cite the *pattern* not the numbers).

**Design implication:** plan the escape hatch *from day one*. The systems that survive the ceiling (Plasmic, Builder) do so by letting real code components drop into the model as first-class nodes. A closed vocabulary with no escape hatch guarantees you hit the wall; the question is only when.

### 5.5 Format-restriction can dumb the model down (§4.6, repeated because it's the sleeper)

The instinct "constrain the LLM to my UI schema" is right for *validity* and wrong for *quality if applied to the reasoning step*. Separate **plan (free-form)** from **emit (schema-constrained)**.

## 6. Distilled, non-obvious takeaways for the design problem

1. **Adopt the convergent shape deliberately:** typed-node tree + referenced token/style layer + explicit control-flow node types (`conditional`/`repeat`/`slot`) + declarative data **bindings** (not embedded code). TeleportHQ UIDL, Mitosis, Plasmic, SwiftUI's `_ConditionalContent`, and QML bindings all independently landed here. UIDL is the closest off-the-shelf schema to copy.
2. **Model = single source of truth; codegen = one-way and disposable.** This is how everyone avoids the round-trip trap (§5.2). Do not let generated HTML be hand-edited unless you're prepared to build a real bidirectional-diff engine.
3. **Separate three trees** (authored doc / stable editing-identity tree / render output), Flutter-style — don't conflate the document you store with the thing you diff or the pixels you paint.
4. **Author against tokens + a registered component vocabulary**, DTCG-style and SDUI-style — semantic references (`{color.primary}`), never inline literals. This is simultaneously the maintainability win (kills Dreamweaver bloat), the constrainability win (LLM emits valid refs), and the cross-target win.
5. **Put the expressiveness ceiling consciously, and build the escape hatch first** (Plasmic code-components / SDUI custom-actions / DTCG `$extensions`). Over-constraining measurably hurts visual quality (DesignAsCode); under-constraining reintroduces every WYSIWYG pathology.
6. **Constrain the *output*, not the *cognition*:** let the agent reason free-form, then grammar-constrain the final IR emission (`Let Me Speak Freely` + structured-output tooling).
7. **Close the render loop:** generate → render → visually inspect → correct. DesignAsCode proves code-gen is "open-loop and blind to rendering artifacts," and your own project's hard-won "confirm on the real UI" rule is the same lesson from the other direction.
8. **Steal the LLVM framing (Mitosis):** define the IR once; write independent backends per target (HTML/CSS/JS now, others later). The neutral IR is what buys you multi-target and agent-authorability at once — at the known cost that your IR is the *intersection* of target capabilities, not the union.
