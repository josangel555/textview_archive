## Era Narrative

The markdown_viewer project launched with a **rapid skeleton-first strategy**: SPM structure (May 14 morning), AppKit window, CI, and bundle assembly landed within hours, followed immediately by feature phases (markdown rendering, tabs, sidebar, file watcher, git integration). By end-of-day May 14, the team had published a functioning macOS app that could open files and render markdown.

The **second wave (May 14–15 afternoon) exposed early instability**: vanishing tabs, compositor-layer conflicts between AppKit and SwiftUI where sibling views would stop rendering, and source-view wrapping failures that made text disappear. These bugs were not corner cases — they hit on everyday interactions (mode-toggle, sidebar-expand). The team diagnosed and **reworked the source-view rendering stack twice in 24 hours**, finally landing on a pure-SwiftUI approach with a pixel-regression test to prevent future compositor pathologies.

**By May 15 afternoon**, the app was stable enough to integrate TreeSitter syntax highlighting (phase 5b) as a full feature branch, bringing 8 languages and 5 MB of grammar code. Parallel to that, a **6-agent code review** began, seeding a batch-fix wave.

**May 17–18 consolidated gains**: a multi-wave production audit (4 agents in parallel) identified baseline memory bloat (76 MB empty window), correctness bugs (deadlocks, UAF, schema downgrades), and O(N) hot paths in cursor movement and search highlighting. The team shipped **40+ perf and correctness fixes** in a single commit, followed by targeted follow-ups. Simultaneously, infrastructure work (MCP stdio server, TreeSitter lazy-load scaffolding, walkthrough engine) was shipped in parallel, keeping the mainline unblocked.

| ad030f30 | 2026-05-15 | **REVERT**: NSTextView source view — compositor bug regressed | Root cause identified: NSRulerView re-entrant glyph-range walks |
| 810da1e4 | 2026-05-15 | **fix**: source-view multi-line select + nail the compositor bug | **Proper diagnosis**: NSViewControllerRepresentable + visual regression test (`screencapture` pixel variance) |
| 00cd7118 | 2026-05-14 (date anomaly; logically after 810da1e4) | **fix**: pure-SwiftUI source view eliminates AppKit/SwiftUI compositor bug | Consolidates Batch 2 fixes; confirms pure-SwiftUI as stable path |

**Pattern**: Three re-attempts to get the source-view rendering right. First two tried to keep NSTextView (for native find, drag-select) despite visual regressions. Third succeeded by **abandoning AppKit containment entirely** — pure SwiftUI rendered correctly, and missing features (scroll-to-match, multi-line drag-select) were deferred as separate tickets.

**Teeth**: Commit 810da1e4 introduced `SourceViewVisualRegressionTests` — spawns the .app, captures via `screencapture -l<windowid>`, samples pixel variance in UI regions (TabBar, ModeBar, StatusBar, etc.), asserts ≥3 distinct color quantizations. **Plus a meta-test** that flips a broken-ruler env var and confirms the test FAILS on the broken build — proving the regression test has teeth (this is a production standard in the owner's CLAUDE.md).

**Cost**: 4–5 commits on the same problem. The fix didn't "stick" until root cause was diagnosed via in-process snapshot (cacheDisplay) failure + direct WindowServer capture (screencapture). Lesson: visual rendering bugs **require pixel-level validation at WindowServer tier**, not in-process headless tests.

## Learnings for the Rebuild

1. **Lead with comprehensive design, not incremental discovery.** Commit 0.1 included DESIGN.md spanning Phases 0–8 with clear rationales. This gave the team a shared roadmap and reduced churn from "what should we build next?" Later phases discovered issues but didn't pivot the overall direction.

2. **Rework loops on visual rendering require pixel-level regression tests (screencapture at WindowServer tier).** The compositor bug took 3 attempts partly because `cacheDisplay` and in-process snapshots hid the pathology. Commit 810da1e4's `SourceViewVisualRegressionTests` + meta-test (deliberate break with teeth) became the gold standard. Invest in T5-tier visual regression infrastructure from the start.

3. **Ship big features complete (including tests, docs, theme) before lazy optimization.** Phase 5b TreeSitter landed as a feature-complete commit (35 files, 8 languages, queries, tests), then lazy loading was added separately. This avoided "we need to optimize, but the feature is half-done" churn.

4. **Coordinate multi-subsystem fixes via parallel commits, not mega-commits.** The May 18 perf/correctness sweep split 40+ fixes across individual commits (one per subsystem win). Each is reviewable, testable, and can land independently. Yet they represent a coordinated effort, not random fixes. This scales better than either "one giant PR" or "ship things ad-hoc."

5. **Docs-to-code ratio of 25% is sustainable if docs are bundled with code.** Rather than standalone doc commits, PHASE_*.md, DESIGN.md, LESSONS.md, CODE_REVIEW.md were all part of feature or audit commits. No "update docs" churn. The high ratio reflects *discipline*, not bloat.

6. **Parallel worktree lanes (6 agents on TreeSitter lazy loading, 4 agents on audits) unblock the mainline if fixes are coordinated at the commit level.** Worktree branches landing via rebase + fast-forward kept main linear. No merge-commit bubbles, even with heavy parallelism. This requires discipline on coordination but scales to large teams.
