# Greenfield Analysis: Commits 1380-1576 (08 of 19)

## Era narrative

**Date span: 2026-06-10 to 2026-06-12 (3 days, 197 commits)**

This slice captures the **rust-core engine-port acceleration and remote-core infrastructure sprint**. After ~6 weeks of foundational work, the team had cleared validation backlogs and pivoted to a major architectural milestone: decoupling the Rust engine surface from the Swift shell via a machine API.

The era is dominated by **staged rollout of engine ports** (fuzzy, find, markdown, transcript) being wired into adapters and gradually flipped to default-ON via a "soak" strategy (stages A, A0, round 2, round 3). In parallel, a **remote-core daemon (mdv-serve)** was built from scratch, coupled with a local transport layer that proved byte-equality between in-process and loopback execution. By day 3, 9 of 10 engines were shipping Rust-first. LSP features (rename, goto, formatting) were being plumbed in parallel, and high-impact security work (egress audit, supply-chain gates, audit logging) landed alongside routine perf optimizations that were immediately validated.

**The documentation discipline was extraordinary.** Of 197 commits, 112 (57%) are "docs: log" entries — a tide-marking pattern where every validated task + minor work cascade gets logged in real time. This hyper-active logging enabled immediate owner visibility and created a clear artifact of the validation workflow. The codebase reached a mature state: FFI misuse guards, health checksums, feature gates, and careful staged rollouts were the default behavior.

3. **Continuous handoff hygiene** — logs stay current, so session-to-session context is fresh.

This pattern is **intentional process compliance**, not overhead. It created a 112-entry log of validation events that survived compaction.

## Learnings for the rebuild

### 1. **Staged rollout beats big-bang for distributed systems**

The soak stages (A, A0, round 2, round 3) for the Rust engine ports showed that a phased, validated rollout de-risks architectural changes. Each stage had explicit validation gates. This pattern should be baked into the rebuild's design from the start: feature gates, capability discovery, and a deliberate go-live sequence for each tier.

### 2. **Responsive perf work and blocker-unblocking**

The grammar cache fix (TSK-545) was identified as a blocker on the highlight flip, fixed on-path, and validated same-day. This was not deferred to a "performance pass" later. **Blocking perf issues should be solved immediately when discovered**, not queued. A rebuild should prioritize identification of blocking perf issues early (via profiling) and solve them in-place.

### 3. **Documentation logging is process infrastructure, not overhead**

The 112 "docs: log" entries represent a **structured compliance artifact**. Each log entry is a dated proof that work was validated. This enabled the owner to see total progress and understand what was in-flight vs. complete. A rebuild should establish similar logging discipline early (perhaps per-ticket boards + a live log), not as an afterthought.

### 4. **Endpoint testing (fake-server e2e, pixel validation) catches gaps that headless tests miss**

LSP formatting was discovered as "never built" mid-work and plumbed in completely with a fake-server e2e test. Pixel suites for tabs were calibrated against real VM captures. These endpoint tests caught integration gaps that unit tests would have missed. A rebuild should **plan for endpoint/UAT tests as a first-class testing tier**, not as a final validation layer.

### 5. **Cross-layer feature spans require careful commit hygiene**

Theming (engine → import → UI → consumer surface) spanned multiple commits but stayed coherent. Highlight (core → adapter → default-ON flip) similarly. The rebuild should establish **clear architectural boundaries at commit boundaries**: each commit should represent a meaningful integration step, and complex features should document their shape (stages, ordered commits, composition) in tickets before implementation.

### 6. **Security work should not be an afterthought; audit coverage should scale with capability**

The egress audit (TSK-635), supply-chain lane (TSK-554), audit logging (TSK-636), and advisory watch (TSK-628) all landed in this slice *alongside* feature work, not afterward. The rebuild should establish security gates as part of the definition-of-done for each feature tier: "does this pull data from untrusted sources?" → audit logging. "Does this use a new library?" → supply-chain gate. "Does this open a network socket?" → egress audit.
