## Learnings for the rebuild

1. **Autonomous progress logging is load-bearing infrastructure, not process overhead.**
   The 100 log entries (56% of commits) are not noise; they are the artifact that enables session continuity after context compaction. Every item ships with a log entry capturing scope, status, evidence class, and cross-links. A rebuild must **codify this discipline upfront** — treat AUTONOMOUS_PROGRESS.md + HANDOFF + BACKLOG as the system of record alongside git, not afterthoughts. Make logging easy (a CLI scaffold per task → append entry → one git commit folding log + code).

2. **Validation ladder (model → UI → full suite → UAT) is the real gate, not host-green alone.**
   The distinction between "model-tested" and "validated via validation-drain" appears ~40+ times. This signals that a feature is not "done" until the full suite runs and no regression appears. A rebuild should **make the validation ladder explicit and opt-in-free** — define what each tier is (unit, integration, headless, VM live, pixel), require the ladder on commit, and make VM reachability a first-class CI concern (not a nice-to-have).

3. **VM testing is the new lint.**
   4,942 tests run on the VM as a routine step, not an afterthought. The "VM sweep clean" entry marks a milestone. A rebuild must **make the VM suite run as easily as `swift test`** (current blocker: Swift 6.1.2 vs 6.3 toolchain mismatch, fixed here). Invest in the VM infra before shipping features; the tests run there, the pixels render there, and no amount of host-green proves on-screen behavior.

4. **Render-path gaps close via harness, not feature-by-feature UAT.**
   The slice shows 10+ new UI scenes added (metadata-checksum, lsp-rename, code-actions, folder-only, theme-dark, etc.) specifically to enable pixel-lane validation. These are not features; they are test scaffolding. A rebuild should **architect the UI harness from day one** with per-scene entry points and per-tier assertion mechanisms (a11y IDs, pixel comparison, model state inspection). Close render gaps systematically; don't accumulate "owner needs to manually click this" tasks.

5. **Slice work cleanly; avoid micro-tickets.**
   TSK-282, TSK-311, TSK-259 each span 2 commits (impl + log); TSK-284 is one commit. Features are not atomized into 10-step micro-commits. A rebuild should **think in slices** (mode A/B, surface 1/2, core/UI) and allow a reasonable engineer to ship each slice in one go. File tickets for slices, not steps; a 197-commit era should not have 197 tickets (it has ~60–80 distinct TSK-ids).

6. **Teeth testing must be demonstrated (not assumed) at commit time.**
   The "behavior-preserving mutants" LESSONS entry and the scene-harness UAT lanes show that tests are actively proven to fail when code breaks. A rebuild should **codify teeth-demo as a pre-commit gate**: for every UAT test, revert the code, confirm the test fails, restore, confirm green. Ship that proof (e.g., via a negative-control env var + test) so audits can see the guard was real, not theoretical.
