## Learnings for the Rebuild

### 1. **Canvas Epic: Rust-First, Design-Before-Build, Multi-Tier Validation Is Non-Negotiable**
   The Canvas epic succeeded through **ruthless planning (M0–M4 docs, board decomposition, kill-criteria) BEFORE a line of code**, tight Rust-core ownership (no Swift-side engine), and **multi-layer validation (rust-core tests + proptest/fuzz, FFI boundary tests, host model tests, WebView suites on VM, real-runtime mount tests)**. The earlier subagent research runaway nearly destroyed the quota; the disciplined rebuild recovered by treating design as a spike artifact, not ongoing deliberation.
   
   **Lesson:** Mega-epics REQUIRE pre-committed design docs + board tickets + kill-criteria before implementation. No "we'll design as we go." Reserve research for spikes (bounded); lock decisions before the build-loop starts.

### 2. **Slice-Based Decomposition Is Load-Critical for Parallelism**
   This slice pushed **50+ concurrent features across a team** (via agent-driven work). Slice-based split (model + render-tail) enabled:
   - Host-green work to land WHILE render is VM-blocked (e.g., all of TSK-698 script-console except the SwiftUI panel)
   - Staggered validation (host gate for model, separate VM gate for render, owner final)
   - Parallel work on model while other features render (no serialization)
   
   **Lesson:** For a rebuild, enforce slice-based delivery FROM DAY ONE. No feature is "done" if only one tier is validated. The discipline scales better than heroic endpoint validation.

### 3. **VM Tier Discovers Real Bugs That In-Process Suites Miss**
   Canvas M3.S1 revealed: window-hosting breaks boot, eval-return-values drop, whole-channel death under specific conditions. None surfaced in in-process WebView suite validation (the fallback contingency). The M3.S1b fixes were **architectural changes**, not cosmetic.
   
   **Lesson:** In-process WebView suites are valuable for fast iteration, but they are NOT a substitute for VM real-runtime validation. Plan for VM validation as a separate tier, not a "nice-to-have." Real WebKit ≠ in-process hosted WebView.

### 4. **Test Infrastructure Drift Is Silent and Kills Coverage**
   SpreadsheetViewHostingTests was literally un-laned and ran nowhere (self-skipped on host, never in VM lanes). The gate was blind. This would have been caught MUCH earlier with a drift-detector.
   
   **Lesson:** Add infrastructure-guard tests that VERIFY the test laneing (e.g., WebViewLaneCoverageTests) is synchronized across ALL lanes. Gate it so future un-laned tests turn the main gate RED immediately.

### 5. **Flake Hardening Requires Root-Cause Understanding, Not Just Symptom Patches**
   TSK-1328's first fix (2-pump settle) worked in isolation but failed under load. The second fix (retry-with-varying-action) addressed the REAL issue (settle-then-measure is racy when async residuals land mid-window). This took 2 commits because the first didn't fully diagnose the mechanism.
   
   **Lesson:** When a flake re-emerges, re-diagnose the root before patching again. Ask "what changed in the test environment / system load profile that broke my earlier fix?" Don't layer patches on patches.

### 6. **Lesson Recording Must Be Systematic (Not Scattered)**
   This slice added 6 LESSONS entries (settle precision, uncovered-test heuristics, VM toolchain poisoning, in-process-hosting AX gaps, subagent runaway, render-lane framing). They're in one LESSONS.md file, date-stamped, with concrete examples and playbooks. Future sessions reference them and extend them.
   
   **Lesson:** Maintain a SINGLE, dated, searchable lessons file. Every session that discovered a hard-won pattern (a tier-mismatch, a flake-recovery technique, a tool poisoning) adds an entry SAME DAY. Do NOT scatter lessons across scattered doc comments or commit messages.
