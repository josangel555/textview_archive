## Process Signals

### Commit Hygiene — Strong Discipline

1. **Paired docs commits.** Every feat/fix/perf lands with a `docs: log +NNN` entry capturing it into `AUTONOMOUS_PROGRESS.md`. This pairs the code change with its tracking narrative in a single atomic record. Example: feat(sessions)→docs log; feat(archive) slice 1→docs log; feat(archive) slice 2→docs log (not bundled into one). This is the owner's "fold docs into the item's code commit" made operational.

2. **Zero merge commits.** All 197 commits form a linear spine (`git log --oneline` never branches). Work happens on agent branches; it lands via rebase + fast-forward onto main. Indicates strict adherence to the linear trunk rule.

3. **Bundled-docs-vs-standalone.** All doc commits are anchored to a code change (a `docs: log +NNN` follows a feat/fix/perf within 1–2 commits). No standalone doc churn. HANDOFF refresh commits (e.g., commit #8: `00bac0f1 docs: refresh HANDOFF at 87354ef…`) appear once per ~20–30 commits as session checkpoints, which is appropriate.

4. **Revert cluster: ZERO.** No reverts, no "I was wrong" commits. Contrast this with typical development (which often shows 3–5% revert rate). The discipline here is **high confidence in root-cause diagnosis before implementing** (per CLAUDE.md directive: "DIAGNOSE before you fix").

## Learnings for the Rebuild

1. **Docs-as-process, not afterthought.** The 1.21:1 ratio works because each feature is *immediately* shadowed by a tracking log entry. This isn't waste; it's the **live artifact of the process itself**. In a rebuild, make logging-on-landing a first-class step (e.g., task close → auto-log). Without it, the board + code tell a fragmented story.

2. **Multi-stage features need per-slice validation gates, not end-to-end gatekeeping.** TSK-580 (envelope) spans 12 commits, but each slice (1, 2, 4, 5, 3, 3-output) is individually testable and can land. The owner sees progress checkpoints, not a black-box "landing" event. **Slice-first planning** (e.g., "envelope: dispatch seam → method routing → consumers") makes the backlog tractable.

3. **Render validation is not a tail — it's the lock gate.** Commits 152–197 show that render work ships in two waves: (1) model + host-testable wiring, (2) render scenes + VM pixel guards. Neither wave is optional; both are owner-gated. The discipline catches **invisible on-screen bugs** that host tests cannot see (e.g., occluded views, z-index mishaps, color blending). A rebuild **must budget for the VM layer** as a first-class lane, not a nice-to-have.

4. **Root-cause diagnosis before fix = zero rework.** This slice has **zero reverts**, zero "fix X again" patterns. The 19 fix commits are surgical — each cites its root cause (race condition, missing gate, wrong field order, off-by-one in DCH handling). Contrast with typical codebases at ~3% revert rate. **Enforce the DIAGNOSE directive:** before implementing a fix, answer "is this a class of bugs" and "what is the mechanism" in the ticket. Hand-waving "let me try X" leads to thrash.

5. **Lean on the Rust core for efficiency gains; don't sprinkle them in Swift.** This slice has 2 major perf commits: CSV arena (rust-core table storage) and wire format (cross-language protocol). Both are **foundational shifts** that affect many call sites. The reverse mistake: tweaking every Swift hotspot independently. A rebuild should **identify the O(N) loops and push them to the core early**, then let the Swift layer compose.

6. **Wire versioning + round-trip testing = confidence in cross-language changes.** TSK-563 (wire v2) lands with: (a) wire-version guard, (b) Rust tuple-twin round-trip test, (c) cross-language diff A/B corpus referee. This is the **template for any protocol change**. It catches decode mishaps (commit-time, not prod-time) and makes remote debugging possible. A rebuild should adopt this in week one.
