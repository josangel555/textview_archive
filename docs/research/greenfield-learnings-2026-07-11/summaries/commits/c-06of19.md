## Process signals

**Doc-logging discipline:**
- 123 logging commits in 197 total (62%) is NOT noise; each `docs: log +N` is a **boundary marker** tracking when a task transitioned from code→fixed→review→validated (or parked/held). The board state is recorded in-tree, per owner's CLAUDE.md directive. This provides **full auditability** — you can track *when* a decision was made and what the work state was at that moment.
- Example: `84cef457` logs "+87 — TSK-135 security sibling-bypass validated w/ new teeth" immediately after `40c01450` added the test. No gap between work and record.

**Teeth-demonstration culture:**
- Multiple commits explicitly call out that a guard was broken and the fix makes it red again (commit `903c27f3`, `dd902649`, `b5baea03`). A test that's never been shown to fail is treated as suspect. This is **quality discipline at the code level**.
- Example `903c27f3`: "the buggy scale made the main test red, so the fix has teeth" — proving the guard works.

**Bundled-docs discipline:**
- LESSONS entries and AUTONOMOUS_PROGRESS updates land **in the same commit as the code** (e.g., `1c8874a1` lands doc updates with TSK-501 validation). No separate doc commits for logging. Hydrates institutional memory without inflating commit count.

**No multi-day gaps between code and validation:**
- Feature lands (e.g., `88909409` on 2026-06-08 13:00 UTC), validation lands same day (`a141d03e` on 2026-06-08 18:00 UTC). Board state is live and in-sync.

**VM infrastructure as first-class work:**
- TCC/ulimit/launchctl fixes are tracked as board tasks (TSK-500–TSK-502), not hidden in "test infra maintenance". This surfaces blockers and prevents silent test-lane lossage.

## Learnings for the rebuild

1. **Validation is a first-class citizen, not an afterthought.** 62% of commits tracking closure signals that the team spends *half their time* documenting and proving what's done, not just building. This overhead should be baked into the schedule from day one. Without it, you ship "code-green, screen-broken" regressions.

2. **Multi-slice epics with planned stages prevent rework.** TSK-342 (image editor) and TSK-257 (syntax highlighting) landed in 8 planned commits each — core layer, then per-tier wiring, then teeth demo. No reverting. Design the epic to *surface* a testable phase boundary; tests at each phase catch design mistakes early.

3. **SPI-level problem-solving is a strength, not a workaround.** Commit `cc44c814` (TCC disclaiming via private SPI) solved a fundamental "xctest can't capture pixels" blocker that would have delayed or killed the VM pixel-test lane. A smaller team might have declared it "too risky" and delayed the feature. The discipline was: prove it works on the host (links and compiles), gate it to tests only (not shipping), then validate on the VM. Risk is managed, not avoided.

4. **Tooling unblocks entire categories of work.** TSK-500 (ulimit) and TSK-501 (launchctl) are ~40 lines total, but they unblock 150+ VM test runs and the entire visual-regression lane. Infrastructure work that seems "cosmetic" (raising a kernel limit, spawning a process differently) is actually **critical path**. Budget tooling/infra work as liberally as feature work.

5. **Security validation needs teeth, not just code review.** Commit `b5baea03` extracts a redaction kernel and writes tests that *prove* removing the kernel surfaces the breach. The model: "(1) extract the logic to a pure testable function; (2) write tests that check the happy path; (3) write a teeth-demo test that swaps to the broken path and expects red asserts." Codify this pattern for every security boundary.

6. **Staging work across ecosystem tiers (core → web → TUI → UI) amortizes testing.** TSK-257 lands the tree-sitter engine in rust-core, then wires it into TUI (raw TestBackend pixel checks), then web (HTML span checks), then UI (visual regression). Each tier tests independently and incrementally. When you land a 6-tier feature as one monolithic commit, you either test everything or test nothing; staged commits let you test as you go.
