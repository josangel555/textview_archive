## Rework arcs

**TSK-1046 (scroll-restore):** 13 commits spanning render-layer diagnosis through test-harness validation. Sequence: (1) session-switch restore attempt (TSK-1046 first fix), (2) model-layer read-fallback for async timing race, (3) render-layer warm-reattach timing fix, (4–13) extensive test-infra debugging (async-await continuation bridge, probe timeout scaling, wait-rendered-scroll poll fallthrough). **Root cause pattern**: a multi-stage async handoff (WebView didFinish → SwiftUI re-eval → Task hop → render) where each stage MUST read state in the correct order, but no single stage owns the state. The fix strategy evolved from "patch the restore order" → "insert fallback reads" → "restructure the test probe itself to match the render VM's actual timing constraints." Final validation required building a live CM6 in-process WebView test, proving the harness itself was the bottleneck.

**TSK-1243 (UAT harness env-delivery):** 11 commits representing a 10+ VM round-trip diagnostic cycle. Sequence: (1) initial discovery (HOME=/var/root under sudo), (2) attempted ProcessInfo snapshot fix, (3) getenv lead (also failed), (4–5) didFinishLaunching timing investigation + viaOpen fallback, (6–11) config-file workaround (write ~/.mdv-launch-config.env in AppLauncher, read FIRST in main.swift). **Root cause**: LaunchServices 'open --env' silently drops env vars when launched via 'sudo -u' (the VM GUI lane), and didFinishLaunching may not fire on viaOpen re-attachment. **Rework signal**: the agent re-diagnosed from scratch multiple times despite the owner's existing ticket analysis, resulting in three separate "fix" commits before landing the SOP-recommended side-channel (config file). Added SOP step 0 post-facto: "READ the ticket's existing understanding BEFORE re-diagnosing."

**TSK-1254 (AX automation):** 17 commits all on 2026-06-26, shipping as vertical slices (driver brain, real AXUIElement adapter, command grammar, catalog expansion, verb/surface discovery). This was NOT a rework arc but a disciplined slice landing — each commit is one conceptual unit (e.g. "AXIdentifierCatalog promotes 5 secondary surfaces") with tests + docs, validated end-to-end on the host (AXDriverCore unit tests prove the brain; live adapters deferred to VM/owner). This is the **exemplar of healthy epic slice structure** vs. TSK-1046/1243 rework.

**TSK-345 (PM store):** 14 commits, all 2026-06-27, landing the event-sourcing core in one day. Slices: (1) crate setup + sqlite, (2–3) event log + persistence, (4–8) lifecycle state-machine + identity guards + dependency edges + cascading, (9–11) inverse queries + ripple logic, (12) event-sourced edges, (13) wire protocol. Each commit is ~60–300 lines (feature-complete within its scope), with supporting LESSONS/CHANGELOG updates folded in. No rework; the design was solid and the landing disciplined.

## Process signals

**Docs-only commits are heavy (45%).** Breakdown: HANDOFF updates (reconciliation snapshots), BACKLOG consolidation ("ONE backlog" directive landing), CHANGELOG owner-visibility updates, CLAUDE.md SOP codification (root-cause SOP, render-confirm SOP). This reflects the owner's late-May directive that process and discipline were being systematized post-facto. Not inherently bad (the codification is valuable), but the high ratio suggests the team was doing work, discovering gotchas, and then documenting them as separate commits rather than embedding process lessons in the code changes that triggered them.

**Handoff-driven updates.** Multiple handoffs every 1–2 days (611472f2, 23ee245f, 413bf792, 616b3fd8, HANDOFF.md micro-updates). Suggests real-time context-passing and mid-flight discovery.

**Test-infrastructure work consumed substantial effort.** TSK-1243 and TSK-1046 together account for 24 commits out of 197 (12%), all focused on UAT harness fixes (env delivery, scroll probes, async-await bridges, WebContent IPC timeouts). This is the cost of building agent-driven UAT on top of production code that wasn't designed for in-process introspection.

**Rework vs. slice discipline.** TSK-1046/1243 (rework) contrasts sharply with TSK-1254/345 (slices). The slice pattern (vertical, self-contained, incremental, validated at landing) shipped faster and with fewer revisions. Rework emerges when root causes are hidden (timing races, env quirks, harness-level assumptions).

**Teeth-demonstration is inconsistent.** Some commits (a28a5a35: "flipped test_restoreScroll… its old XCTAssertNil was FALSE GREEN") explicitly show how tests were wrong and how the fix proves the guard now works. Others land code without documenting what made prior versions fail.

**Zero reverts in this span.** No git-revert commits, suggesting either discipline or that bugs were fixed incrementally in-place rather than reverted and re-landed.

## Learnings for the rebuild

1. **Invest in UA/RT early, but expect 15–20% of velocity burned on harness fixes.** The scroll-restore and env-delivery bugs were fundamentally app-level issues (timing race, env delivery), but surfacing them required 24 commits of harness work (probes, async bridges, config-file side-channels). A greenfield rebuild should: (a) design the app's internal state and async boundaries to be observable SYNCHRONOUSLY (e.g., scroll offset always readable without waiting for didFinish), and (b) separate UAT harness concerns into a dedicated test-infrastructure project, tested and stabilized BEFORE being used to validate production code.

2. **Single source of truth beats patching async boundaries.** The model-layer fix to scroll (a28a5a35 — read from tab.renderedScrollY, not from an async-seeded dict) was ~5 lines and immediately correct. The prior attempt (restore-order patches) kept failing because it tried to order side effects across an uncontrollable async chain. Lesson: when an async boundary creates a race, collapse the layers if possible rather than adding more instrumentation or retries.

3. **Root-cause discipline is not negotiable when a fix resurfaces.** TSK-1046 and TSK-1243 both went through multiple "fixes" that didn't stick because the diagnosis was incomplete. The owner's SOP (CLAUDE.md step 0: "READ the ticket's existing understanding FIRST") exists because this happened. A rebuild should codify root-cause investigation (identify whether the bug is sync-sequencing, async-timing, or data-level, then verify end-to-end) into the ticket-acceptance flow, not just documentation.

4. **Fold process lessons into code commits.** The 90 docs-only commits represent process-capture work. Many should have been folded into the code commits that triggered them (e.g., the root-cause SOP should ship with a28a5a35's commit, not in a separate CLAUDE.md update). This keeps git log readable and ensures future developers see the *why* in the same place as the *how*.

5. **Slice-based landing outperforms rework-driven iteration.** TSK-1254 (17 commits, zero rework) and TSK-345 (14 commits, zero rework) landed faster and cleaner than TSK-1046 (13 commits + extensive test-harness fixes) and TSK-1243 (11 commits + round-trip diagnostics). The pattern: design → vertical slices, each self-contained and validated → commit → move on. Avoids the cost of discovery-and-re-diagnosis when preconditions are hidden.

6. **Test infrastructure should be stability-gated before production use.** The UAT harness (viaOpen launch, scroll probes, async continuations) required more debugging than the features it was testing. A rebuild should: (a) land a minimal harness first, (b) gate it heavily (prove it's not the false-green culprit), (c) THEN use it to validate production behavior. This inverts the current flow where production features and harness maturity co-evolve.
