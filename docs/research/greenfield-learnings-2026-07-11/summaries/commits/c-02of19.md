## Learnings for the Rebuild

### 1. **Convergence Rhythm: Land → Audit → Fix → Refactor → Handoff**
The healthy cycle shown here is **not linear feature-by-feature**, but rather **parallel feature branches converging into a quality checkpoint**. A rebuild should budget for this: don't expect pure velocity; expect convergence moments where you merge branches, run an audit, fix bugs, extract coordinators, and re-document architecture. The time cost is high (~3–4 days in an 11-day slice) but the quality payoff is substantial (20 fixes + 11 security hardening + 2 major refactorings in one cycle).

### 2. **Audit as a Deliberate Gate, Not Accidental**
The CORRECTNESS_2026-05-25 cluster is **not reactive bug-fixing**; it's a scheduled formal audit. Build this into the process: after major feature branches converge, do a comprehensive code review (security, correctness, perf), file findings, and fix them as a single commit. This avoids dribbling fixes into the history and makes the quality bar explicit. Pair each fix with a test.

### 3. **Refactoring After Features Is the Healthiest Time**
TabCoordinator and EditorCoordinator extractions happened **after** the features that stressed DocumentModel landed. Wait for the real load to surface the architecture problems, then refactor with comprehensive tests that prove behavior is maintained. This is better than speculative refactoring; the tests are grounded in actual usage patterns. Budget for this: roughly 1 large extraction per 3–5 feature landings.

### 4. **Tests Are Immediate, Not Backfilled**
38 test commits (19% of total) are interleaved with features, not added later. This is not just unit tests; it includes coordinator state-machine tests, invariant tests, VM UI tests, and scenario tests. A rebuild should **make test-writing part of the feature-landing flow**, not a separate phase. When a feature merges, tests merge with it.

### 5. **Security and Perf Audits Deserve Dedicated Merge Commits**
Instead of sprinkling security + perf fixes across multiple commits, consolidate them: `Merge security + concurrency fixes: 11 fixed, 75 new tests` makes it explicit that this is a quality checkpoint, not incidental work. This also makes the diff reviewable as a unit. A rebuild should treat security/perf audits as **first-class deliverables**, not afterthoughts.

### 6. **Handoff Documentation Is a Structural Checkpoint, Not Optional**
The LESSONS.md / DESIGN.md / BACKLOG.md / HANDOFF_2026-05-29 bundle (984 lines) represents **institutional knowledge consolidation at a natural boundary**. A rebuild should budget explicit time for this: after each convergence cycle, update the LESSONS (gotchas, anti-patterns), DESIGN (architecture), BACKLOG (next steps), and produce a handoff (state of the codebase + decisions made). This is not a "nice to have"; it's **structural continuity** that survives context switches and onboarding.
