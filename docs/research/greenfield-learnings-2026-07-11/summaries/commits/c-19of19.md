### TSK-1566: P0 Launch-Wedge — App Un-Openable (LS -600) (1 commit, but indicates systemic issue)

| Commit | Date | Subject | Root |
|--------|------|---------|------|
| 87dda3c5 | 2026-07-07 | `fix(launch)`: P0 — app un-openable (LS -600): bridges must never touch AppKit; zombie bridges self-reap | **Root**: main.swift ran `NSApplication.shared` BEFORE the --mcp-connect branch, so every MCP bridge process (same bundle executable) initialized AppKit and registered as a running TextView.app instance. Finder tried to ACTIVATE the bridge instead of launching the app. Four zombie bridges present, holding pipe write-ends open. |

**Fix**:
1. Hoist --mcp-connect branch above NSApplication.shared (bridge is pure POSIX)
2. MCPSocketBridge.exitWhenOrphaned() — PPID-poll watchdog; exits within ~5s if spawning client dies
3. Drop stale swift-folds.scm resource-check entry (Queries bundle deleted with Swift fold twin)

**Guard**: MCPBridgeLaunchOrderTests parses the LIVE main.swift; reorder goes RED.

**Evidence**: Empirically verified on installed build (TSK-1566 closed).

**Significance**: This is a **pre-launch discovery** (July 7, days before audit). The owner's app was literally un-openable. This class of issue — "side effects of background processes colliding with the user's app" — is notoriously hard to catch without real-world testing and typically surfaces AFTER shipping.

## Process Learnings for the Rebuild

### 1. **Adopt Structured Batch Discipline from Day 1**

The 25-batch progression (B1–B25, each with a closure checkpoint) forced hard decisions ("ship now or defer") and prevented feature sprawl. The rebuild should **start with a batch roadmap** (30–40 batches, ~10 days of work per batch at 8-week velocity) and enforce closure gates:
- Every batch has a `docs: B# closed (...)` commit that names what shipped, what's deferred to render tails, and what's blocked
- No batch enters the next without resolving *all* open items (shipped, parked with reason, or blocked with blocker noted)

This eliminates "I thought that was done" and "wait, where does feature X live?"

### 2. **Reserve 3+ Weeks for the Drain Phase and Don't Skip It**

The 37-tick drain discovered:
- 3 production crash classes (MCP reader/writer, launch-wedge)
- 22+ subsystems (models, infrastructure, APIs) that were built but not shipped
- Integration gaps (features built but unreachable to users, e.g., TSK-1438 outline)
- Daemon/transport architecture (6-slice design, not a last-minute bolt-on)

**The rebuild should schedule drain as a 3-week mandatory phase AFTER features are modeled**, not treat it as "cleanup if we have time." File drain tickets upfront; track them on the board.

### 3. **Decouple Model from Render Tier; Track Both Explicitly**

The project's "model now, render later" pattern (40+ tickets moved to render tails in this slice alone) is powerful but **requires explicit tracking**:
- Every feature ticket must name its **required test evidence classes at grooming** (e.g., "WV model + T5 pixel")
- Model = host-testable, shipped to review
- Render tail = VM-validated later, NOT left orphaned
- Block render-tail validation from reaching "done" until pixel-proof is attached

The rebuild should formalize this in the ticket template: model tier, render tier, split acceptance criteria.

### 4. **Establish VM-First UI Testing by Week 2; Never Run T4/T5 on the Host**

By 2026-07-09, the team had operationalized pixel-capture UAT on the VM:
- Scene code in UISceneRegistry (committed, repeatable)
- vm-uitest.sh with window-id capture via `screencapture`
- Headless gate re-run after every UAT commit (verifies the core model still works)

The rebuild should **not wait until week 8 to discover the VM lane**. Operationalize it in week 2 (while building a few early features), run one end-to-end UAT, then leverage it for all subsequent render work.

### 5. **Crash-Class Audit Deserves Its Own Sprint**

The MCP reader/writer crashes (TSK-1559, TSK-1566) were production-critical and discovered during final merge gate. The rebuild should have **one dedicated week (week 4–5) for a crash-class audit**:
- Instrument all teardown/edge-case paths (app quit, connection loss, resource exhaustion, concurrent cancellation)
- Run the headless suite under load (18-worker gate, stress memory)
- Capture OS crash signals (SIGABRT, SIGSEGV) in a dedicated test; replay against release build
- Pair with security-review for exploit-class issues

This is **not** optional cleanup — it's foundational reliability work.

### 6. **Pixel-Proof Over Hand-to-Owner for Render Validation**

The discipline shown in commits 140–150 (8e976c3a onwards) — **scene code + pixel evidence + command to reproduce** — accelerated the final phase significantly. The rebuild should:
- Make pixel-proof the DEFAULT for "I verified this renders"
- Never move a render ticket to "done" on model-test evidence alone
- Attach the scene code (UISceneRegistry entry) and pixel proof to every render-tail validation
- Automate the scene-launching and screen-capture so proof is a 30-second operation, not a 10-minute manual walkthrough
