# Commits 1971–2167 (Slice 11 of 19): Feature Velocity + Infrastructure Maturation

## Era Narrative

**Dates:** 2026-06-14 to 2026-06-19 (6 days)

This slice captures a critical **feature-velocity sprint** interspersed with infrastructure consolidation. The work divides into two distinct phases:

**Phase 1 (June 14–17):** A high-velocity feature burn of the curated intake work, driven by the owner's triaged backlog (TSK-887…945). Small to medium CSV features (Copy as Markdown Table, Sort, Summary), editor improvements (Vim mode, Edit Lines operations, Preview focus), UI refinements (breadcrumb, mode shortcuts, focus management), and file/session operations dominate. Each feature typically lands in 1–2 commits. A parallel docs-tracking overhead emerged: each feature commit was immediately followed by a "docs: log X" commit, creating churn—**nearly half of all commits (87/197 = 44%) were documentation check-offs**, not feature code. This pattern inflated the commit count but provided strong visibility into work progression.

**Phase 2 (June 18–19):** The focus shifted to **infrastructure + security**. Large, complex features were integrated (Tmux control-mode terminal integration, LSP completion, Audio/MIDI host-testable models, Feed reader, Goto-Anything symbols), while test infrastructure underwent a refactor wave (VM harness UAT fixes, git-fixture consolidation, timing-report instrumentation). A security hardening cluster appeared at the slice's tail: three back-to-back commits (TSK-963, TSK-967, TSK-966) addressing LSP args gating, HTML sanitizer event-handler bypasses, and XSS escaping—suggestive of a design-review audit pass. Performance work (doc mirror stateful apply, predicate caching, search result capping) was interleaved with refactors (dead FFI removal, internal rust-core visibility tightening).

**Key observation:** The repo had reached a feature-complete / user-facing-value plateau by day 4 ("clean high-value pool tapped," commit 6f69cfff); subsequent work pivoted to backlog intake, infrastructure hardening, and quality/perf polish. The volume (197 commits in 6 days) reflects rapid iteration cadence supported by a well-instrumented async validation loop (VM harness UAT, heap of small tests per feature).

## Process Signals

### Commit Hygiene: Bundled Docs vs Standalone Doc Commits

**The pattern:** 87 docs commits out of 197 total (44%). Most follow the structure:
```
<feature commit>  (e.g., feat(csv): Copy as Markdown Table)
docs: log X       (e.g., docs: log CSV Copy as Markdown Table/JSON (TSK-870) + CHANGELOG)
```

**Example chain (TSK-870):**
1. 6ca616f5 feat(csv): Copy as Markdown Table + Copy as JSON
2. f57f812c docs: log CSV Copy as Markdown Table/JSON + CHANGELOG

**Assessment:**
- **Pro:** Visibility. Every feature has an immediate commit log; the board can audit what was done in a day.
- **Con:** Churn. Doubles commit count without substance. A 197-commit day is really ~110 code commits + ~87 doc commits.
- **Per owner guidance:** FOLD docs into the code commit, not standalone. This slice violated that—it created a "paired doc" pattern that inflated the log.

### Revert Clusters & Teeth

**Observation:** Zero reverts. This is noteworthy given 197 commits in 6 days. Possible explanations:
1. **Tight scoping:** Each TSK was well-understood before implementation.
2. **Strong test gates:** Host headless + VM validation caught issues before landing.
3. **Integrated validation:** Some fixes happened within the same feature window (e.g., if a test failed, the fix was added before committing the feature).

**Teeth demonstration:** A few commits show deliberate negative controls or diagnostic markers (e.g., commit 9f6fddb7 "test(diag): TSK-1243 viaOpen marker instrumentation — TEMP — remove after"), indicating the team was instrumenting to prove fixes worked. However, these are outside the slice boundary. Within the slice, no explicit "revert to verify the test fails" pattern.

## Learnings for the Rebuild

1. **Unbundle docs from code commits.** This slice created a "feat + immediate-log" pattern that is process-heavy. The owner's guidance (fold logs into code commits, not standalone) should be enforced from day 1. A 197-commit day should be ~130 code + tests, not 110 + 87 docs. Use the board (`tasked` MCP) as the single record, not per-commit logs.

2. **Rework arcs should be rare.** The slice shows only one genuine rework loop (TSK-947, split across two "halves"). Most work was sequential and validated immediately. The rebuild should maintain this hygiene: each ticket is scoped complete before landing; if mid-flight feedback requires a split, that's a new ticket, not a re-land of the same ticket. The no-revert pattern here was strong.

3. **Feature velocity + infrastructure is sustainable, but requires discipline.** This slice landed 93 features + 7 perf + 2 refactor in 6 days, *while also* maintaining test harness health + security hardening. The key: **async validation loop** (VM harness, headless gate) meant features didn't block on test infrastructure. The rebuild should prioritize the harness (test-in-vm.sh, CI gates, T4/T5 pixel tests) as load-bearing **before** feature velocity ramps.

4. **Perf work should be interleaved, not batched.** TSK-887 (palette memoization), TSK-888 (search cap), TSK-961 (profiling tools) landed *during* the feature push, not after. The rebuild should make perf measurements routine (commit 36e66ece adds ~87 lines for memoization; commit 21171a82 adds ~80 lines for search capping—small, high-ROI changes). Don't defer perf to a "polish pass."

5. **Complex features can land in one commit if the design is solid.** TSK-727 (Goto-Anything, 434 insertions), TSK-956 (Audio/MIDI, 631 insertions), TSK-955 (Feed reader, 706 insertions)—all landed in single commits with comprehensive tests. This suggests deep pre-flight design + scoping. The rebuild should invest in design docs + spikes *before* implementation, so features don't land as "I'll finish it next commit."

6. **Security audits should be explicit gate events, not tail work.** The TSK-963/TSK-967/TSK-966 cluster (LSP args, HTML sanitizer, XSS escaping) at the slice tail suggests a design-review audit pass happened ~day 6. The rebuild should schedule **security review as a mandatory gate event** (e.g., every 10–15 features, or before public release), not discover hardening needs reactively.
