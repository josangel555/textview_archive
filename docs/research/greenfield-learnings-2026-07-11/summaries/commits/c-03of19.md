# Commits 395–591 of 3733: Pre-Launch Audit & UAT Campaign (2026-05-29 to 2026-06-03)

## Era Narrative

This five-day window captured the **post-feature-complete hardening sprint** leading into the pre-launch UAT phase. After ~8 weeks of agent-driven feature development, the project entered a structured **47-agent audit** on 2026-05-30, targeting 172 security/reliability/correctness findings across 14 subsystems (G1–G14, plus signing phases). The audit wasn't sequential—it was fanned out across a large multi-worktree fleet, with each agent tackling a dedicated slice (LSP pool leaks, parser hardening, file watcher resilience, cache-key folding, session persistence, etc.). By 2026-05-31, those findings landed via 29 merge commits back to a `integration/next-steps-fanout-2026-05-29` branch. This window also saw the **debut of Rust-core integration** for CSV parsing (a monumental FFI/static-link scaffold), **observability infrastructure** for logging/tracing, **major feature lands** (image zoom, HTML rendering, code review Stage 1–3, git file-history tab, diagnostic windows), and a **testing-pyramid audit** that reframed the project's UI-testing strategy. The sprint closed with a 22-commit UAT campaign harvesting fixes from parallel validation branches, then a session-ending handoff and backlog reconstruction on 2026-06-03.

The interval shows the project transitioning from **feature velocity** (building user-visible capabilities) to **production hardening** (audit-driven bulk fixes + test-infra overhaul). It also demonstrates a mature **workflow automation pattern**: large audit investigations spun up 47+ agents in parallel, each given a narrowly-scoped subsystem, forcing the team to choreograph merge-back and reconciliation at the end—a pattern that recurs throughout the 3733-commit history for scaling coordination.

- **Bundled:** Most code commits included relevant docs (commit messages, inline comments). Example: `035369fb` ties security findings to audit codes (SEC-001/002); `bd4e74e5` explains the root cause; `b3b06bcc` names the test class + scenario.

### Merge Commit Discipline

29 merges from the multi-worktree audit + UAT workflows. **No merge commits on main—all are onto intermediate branches** (`integration/next-steps-fanout-2026-05-29`, `audit/pre-launch`). This preserves the linear-trunk invariant: the main line stays a single thread. Worktree branches fan out and are reconciled via intermediate integration branches, then squashed back to main.

### Revert as a Signal: The "Surface-Only" Trap

The single revert (`663c6a1a`) is instructive. A change labeled "Phase-9 surface-only" broke runtime .bundle codesign validation. The revert message calls this out: "surface-only was wrong; deferred to Phase 9 w/ VM re-test." **This is a high-confidence catch—a mistaken risk categorization led to a pre-emptive revert after only ~hours in main.** Indicates: (a) good observational discipline (tested post-commit), (b) willingness to revert fast, (c) learned lesson about surface-only claims.

### Rework Clustering vs. Systematic Phases

Rework is NOT clustered chaotically; it follows audit phases. G1 cache-key folding, then G9 cache LRU rebasing—separate audit agents, separate commits, each fixing what they found. When rework appears (G4 repeats 4 times), it's because the subsystem warranted multiple passes. **This is healthy: rework is phased and bounded.**

## Learnings for the Rebuild

1. **Bulk-fix campaigns via audit phases are viable at scale:** 47-agent parallel audit → 32 G-phase commits shows that coordinating large-scale hardening is feasible if you (a) partition by subsystem, (b) give each agent a narrow scope, (c) merge back to an integration branch, then (d) land one squashed commit per phase to main. Reduces merge-commit clutter and keeps the log readable. **For rebuild: invest in audit instrumentation from day one; parallel audits catch rework-prone subsystems early.**

2. **"Surface-only" is a high-risk categorization:** The one revert proves that build-time surface changes can break runtime behavior in non-obvious ways. Don't trust risk assessments that assume a change is isolated. **For rebuild: any build-script or signing-related change needs VM validation before landing, not "if we have time."**

3. **UAT should run on parallel worktrees, then batch-land fixes:** The 22 `uat-fix` harvested commits show disciplined UAT: let parallel branches accumulate corrections, don't interrupt main, then integrate when UAT phase ends. Avoids the "UAT never ends" trap. **For rebuild: separate UAT validation from main-branch development; give UAT branches time to stabilize before integrating.**

4. **Observability/instrumentation landing must precede diagnostics features:** The `ObservabilitySink` landing (`a23e8812`) on 2026-05-31 unlocks diagnostic windows + instrumentation UI commits on 2026-06-02. Logging infrastructure is a prerequisite, not an afterthought. **For rebuild: scaffold observability scaffolding (ring buffers, event routing) early, before shipping per-feature logging; it pays dividends in post-launch debugging.**

5. **Testing-pyramid reframing is a heavyweight commitment:** The `testing-strategy-2026-05-31` research (1610 lines) outlined a multi-month migration (T1–T5 tier separation, UITestCase→LiveAppTestCase→PixelTestCase). This wasn't a quick fix; it required design upfront and multiple followup commits (`test(pyramid): keystone`, etc.). **For rebuild: get testing tiers right from the outset; retrofitting tier discipline costs more than building it in. Consider enforcing tier-based skip guards early (e.g., host-safe headless-only by default).**

6. **Performance wins tied to root-cause clarity are real and shippable:** The launch-memory fix (`bd4e74e5`, 998MB→55MB) was a 30-line change addressing a specific root cause (appendLazyTab idempotence). These are the wins users feel. **For rebuild: measure first (profile launch, identify the leak), trace it to root cause (not blame a subsystem), then ship the single targeted fix. Batch performance wins by impact, not subsystem.**
