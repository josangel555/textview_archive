## Learnings for the Rebuild

### 1. **Board ≠ Code. Validate Code-First, Not Tickets.**
The single largest finding: the tracking board had become a **stale liability**, listing "missing UI" for features that were actually wired but undiscovered. A greenfield rebuild must **make code the source of truth from day 1**. Periodic audits (even informal) that read code and cross-check tickets catch this drift early. *Cost: 1 audit pass per week during active development; benefit: never surprise-ship vaporware and never burn cycles chasing phantom features.*

### 2. **Real-App UAT Beats Model-Green. Prioritize Test Vehicles.**
Host-only tests (model-green, headless DOM assertions) cannot catch:
- Compositor occlusion (a SwiftUI view blanked by a layer-backed NSViewRepresentable)
- Empty-state rendering (a view tree node is present but alpha/size/z-order renders it invisible)
- Keyboard/gesture routing (AXUIElement vs synthetic events)

The shift to VM UI-driven validation (T4 LiveAppTestCase, WebView hosting lane, T5 pixel capture) was transformative. **Establish the T4/T5 vehicle early**—it is the friction-reducing enabler for safe refactors and correctness fixes. The cost (VM rsync + test-in-vm.sh) is negligible; the benefit (confidence in pixel behavior) is immense.

### 3. **Epic Slicing: Milestones → Slices → UAT.**
Canvas (M0→M6) succeeded because:
- 7 independent milestones (each a 2–4 week sprint)
- 5–7 slices per milestone (each a coherent feature: S1=infra, S2=chrome, S3=export, etc.)
- 1 UAT slice per milestone (M5.S5, M6.S7) that exercises the full journey

A greenfield rebuild should **encode this three-level hierarchy into the task board**: Epic → Milestone → Slice, with UAT always the last slice. It forces discipline (slices must be shippable) and makes progress visible (owners see "5 of 6 slices done" not vague percentages).

### 4. **Planned Consolidation, Not Thrashing.**
The Stage-B deletions (Swift fuzzy → Rust fuzzy, Swift CSV → Rust CSV, etc.) had **zero rework**—zero reverts, zero "it didn't stick" cycles. Why? Because the deletion was *planned*, not reactive:
- Bridge was built first (rust-core was ready).
- Fallback degradation pattern was in place (fault → unranked output + log).
- Swift twin was deleted wholesale, not piecemeal (no stale hybrid lingering).

A greenfield should **plan the Rust-only endpoint from day 1**: build the bridge upfront, use it in shadowing mode (parallel Rust + Swift, compare), then delete the Swift twin. This costs a few weeks of dual-maintenance but eliminates years of "should we port this?" questions.

### 5. **Test Guards Are Discipline Enforcement.**
The ContextBudgetTests (AUTONOMOUS_PROGRESS rotation), WebViewAllowlistTests (chrome stays native), and HardCodedColorRatchetTests (shrink-only colors) have **one job: prevent regression into anti-patterns**. They are not optional polish; they are **load-bearing operational rules**.

A greenfield should **preemptively instrument guards for known risk zones**: budget caps (no context bloat), architectural boundaries (WebView only in content hosts), and quality ratchets (colors, font sizes, hardcoded strings shrink-only). The guards cost 30 lines of test code; the regression they prevent costs days of investigation.

### 6. **Backlog Curation Scales Autonomy.**
The 25-batch re-curation of ~200 items enabled batch-loop runs (owner cron directive). Without it, an autonomous agent faces an undifferentiated queue and can't make prioritization decisions.

A greenfield should **maintain ONE curated backlog** (owner priority-ordered, not auto-generated) and treat the task board as the *implementation state record* (what's in progress, what's done), not the planning tool. The curation is owner work, but the discipline (one backlog, board-as-record) scales the agent loop.
