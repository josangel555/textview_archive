## Learnings for the rebuild

1. **Autonomous runs need heavyweight progress tracking.** The 93 docs commits (47% of total) are not noise — they're the owner's visibility mechanism for what shipped, blockers encountered, and decisions needing escalation. A rebuild running autonomous loops should log systematically (per wave, per ticket, per tier when handling audits/migrations). The docs/progress pair-commit pattern is load-bearing.

2. **Phased architecture work (Rust slices, front-end convergence) prevents rework.** The core::view consolidation didn't require TUI or web to be rewritten three times; it was designed once, built once, consumed twice. A rebuild should plan multi-frontend/multi-consumer abstractions upfront and slice the work to build-once-use-twice, not build-thrice-converge-later.

3. **Security audits uncover real bugs when triaged by severity.** Deep-audit found 80 items; S1/S2 (18 findings) had actual exploits (DNS-rebinding, path confinement, symlink escape). S3/S4 were polish/hardening. Prioritizing S1/S2 first prevented thrashing and kept emergency fixes separate from routine hardening. A rebuild's security gate should triage findings and land fixes in severity order, not a chaotic batch.

4. **Test backfill after feature surge is a legitimate pass, not rework.** The 16+ test commits were systematic coverage of untested methods, not repeated fixes to the same code. This prevented silent regressions in the long term and is a defensible tactical investment after a velocity spike. A rebuild should budget for a "test sweep" pass after major feature shipments.

5. **Bundled docs with code (not standalone doc commits) keeps the story coherent.** The owner's directive to fold docs into code commits meant ~1:1 ratio of doc lines to code lines, but no separate churn. This avoids a split "oh, there's code history AND a parallel doc history" problem. A rebuild should enforce paired commits or explicit "this doc change stands alone" justification.

6. **Zero reverts and forward momentum come from validated spikes before implementation.** No rework loops in this slice indicates designs (UX overhaul decisions, Rust slice plans, audit response priorities) were validated before shipping. A rebuild should invest in spike/design validation and resist the urge to ship-first-validate-later, especially for complex subsystems like the terminal or docking layout.
