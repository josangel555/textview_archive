## Learnings for the rebuild

1. **Refactor mid-project, not at the end.** DocumentModel's 40-slice SRP extraction (TSK-1110, 57 commits) was done *while shipping features*, not deferred. The technique is: extract incrementally, validate after each slice (test gate green), fold extracted slices into their dependencies as they land. This keeps the monolith from ever becoming unmaintainable and catches refactor-induced bugs immediately. The greenfield rebuild should establish this discipline on day 1: if a class reaches 800 lines, carve it (don't wait for 7500). The discipline paid off: zero render regression, 100% test suite passed throughout.

2. **Build the model, add teeth, *then* wire the UI.** Every feature in this slice follows this pattern: (a) pure-logic core (NavHistory, RichTextHTMLParser, RenderedBlockDiff, dirty-rect bounds), (b) host tests that prove the model works (differential, invariants, round-trips, XSS gates), (c) render wiring deferred ("at review" / "on VM"). This separates the model-confidence problem (solvable off the render path) from the integration-and-feel problem (needs live validation). The rebuild should enforce this: a feature is not ready for render validation until the core is 100% tested and documented.

3. **Systematize test coverage in veins, not ad-hoc.** TSK-585 (19 proptest commits) shows a systematic sweep: every parser got fuzz, every engine got differential or invariant tests. This wasn't "randomly add tests"; it was "systematically close gaps in every subsystem". The rebuild should adopt this vein approach: identify the major test categories (unit, integration, property, fuzz, performance, security), then *clear them methodically* as a team rather than accumulating "test debt".

4. **Validate the test suite's isolation and speed.** TSK-1288 (test-hermeticity) and TSK-836 (test-speed) are rarely the "glamorous" work, but they *unblocked* everything else. Test pollution (writing to ~/Library) made results unreliable. Slow tests (2.0s drift-guard) made the gate-log unreadable (couldn't see the real outliers). The rebuild's day-1 checklist: (a) every test's isolation properties documented (what state does it touch? is it tmp-isolated?), (b) the gate-log analyzed weekly for slow tests (36x wins are *always* available if you look). These are cheaper than shipping bugs.

5. **Slice major work to validate incrementally.** TSK-1110 (40 slices), TSK-1288 (6 fix slices + guard), TSK-1183 (7 capability slices) all show the same pattern: don't land a 1000-line change in one commit. Slice it so that each slice is independently meaningful, the gate runs after each slice, and you can point to "slice N works because tests Y/Z green". This catches integration bugs early (as soon as a dependency interaction breaks, the slice *after* it will fail the gate) and makes code review tractable.

6. **Document the checkpoints, not the journey.** 9 periodic handoff commits vs. 188 working commits shows disciplined state-capture. The rebuild should adopt this: every 3–5 hours of work, capture "where are we?" (HANDOFF.md, AUTONOMOUS_PROGRESS.md), not "here's my thought process step-by-step" (that's token-waste). Handoffs should answer: *What shipped? What's blocked? What's next?* Only that. The rebuild's template: date + shipped count + blocker list + next-action + new tickets filed.
