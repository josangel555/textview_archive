## 2026-06-23 to 2026-06-26 — CM6/WebKit test-vehicle cluster (jetsam kill, async eval flake, mtime staleness, lane-registration) · status: current, dense and highly reusable
**[P]/[T]** domain: WebKit/testing/VM
- learnings: a heavy WKWebView's WebContent XPC process can be idle-killed (jetsam) by the OS under a headless/background GUI session — proven via unified-log evidence, NOT memory or JIT related; a spawned-app UAT that drives a heavy embedded webview through the OS is close to unwinnable for that reason. The RIGHT vehicle for such content is an IN-PROCESS test that mounts the webview inside the test process itself (no spawned app → no jetsam exposure). The async `try await webView.evaluateJavaScript` throws WKError-5 both deterministically (undefined/object results) and INTERMITTENTLY even for primitive results — the completion-handler variant does not have this bug; bridge it to async via `withCheckedContinuation`, extracting the Sendable primitive INSIDE the handler. `rsync -az` mtime-preservation defeats SwiftPM's incremental build on a remote/mirrored machine — the tell is "a code path that's impossible for the source on disk is still exercised"; fix by touching changed files before build and watching for the `Compiling <file>` line in the build log to confirm recompilation actually happened. A new in-process test suite that isn't added to the runner's hardcoded filter list runs literally NOWHERE (instant "skipped", false green) — any harness with an env-var-gated suite list needs that list checked whenever a suite is added.
- carry-forward: PORT — the in-process-webview-test-vehicle pattern and the completion-handler-not-async-eval pattern are both concrete, load-bearing fixes worth carrying verbatim into any future embedded-webview architecture.

## 2026-06-22 — `swift test --filter` does NOT relink an external static lib after rebuild · status: current
**[P]** domain: build/FFI
- learnings: SwiftPM does not treat a linked-in `.a` (added via a raw `-L` flag) as a tracked build input — after rebuilding the native lib, even a `swift test --filter` that touches Swift sources can keep testing the STALE binary. To verify an FFI/native-core behavior change from the higher-level language, you generally need a FULL clean rebuild (not a filtered slice) to force the relink — and even that can FALSE-PASS on the very next run if the change was native-only with no Swift source touched (SwiftPM only relinks when a Swift compile unit changes). Mitigation: force a relink explicitly (touch a Swift test-target file, or `rm -rf .build`) after any native-core rebuild, or run the full gate twice, or confirm a known native-dependent test flips red→green as expected before trusting a "pass."
- carry-forward: PORT — this exact FFI-staleness class (external static lib not tracked by the higher-level build system's incremental cache) will very likely recur in a Rust-core-over-FFI architecture; encode the "force relink after native rebuild" step as a standing CI/gate rule from day one.

## 2026-06-21 — "Engine tested ≠ feature shipped"; gated-zero-risk render pattern; FormulaEngine port · status: current, dense
**[U]/[P]** domain: architecture/testing/FFI
- learnings: a fully-tested engine (dense unit tests + cross-language A/B parity) can have ZERO view consumers and ship as a totally inert dead path — "a passing test suite proves the MODEL, never that a view consumes it"; before claiming/changelogging a feature, grep for a non-test CONSUMER of the engine. A grep-based "consumption guard" cannot distinguish real call-graph-reachable consumption from a dead reference that's textually identical to a live one — a real guard needs call-graph reachability, not string presence. Pattern for building a render-path change safely and autonomously: gate the NEW behavior behind a default-OFF flag so the off-branch is provably byte-identical to today, pair it with a pure host-tested decision-logic helper, and treat the gate-ON behavior as the VM/owner review surface. For a spreadsheet-like ported engine: diff the LIVE function sets between the old and new engine (a function library can have grown since the last "parity" claim) rather than trusting a stale corpus; verify a port via cross-language A/B parity tests (same input through both engines, assert equal) rather than only per-engine unit tests; a `#NAME!`-style fallback from new-engine to old-engine is sound specifically because the new engine's function set is a strict subset of the old's.
- carry-forward: DISTILL — "tested model ≠ shipped feature, grep for a live consumer" and the "default-OFF gate + pure decision-helper" render-safety pattern are both high-value, broadly applicable practices for the next project, especially given it will again have a Rust-core-with-multiple-UI-frontends shape where "ported but unwired" is a structurally likely failure mode.

## 2026-06-20 (PM) — Memory metrics, runaway diff algorithm, worktree overlap, agent rate-limits · status: current, dense
**[U]** domain: perf/process
- learnings: VSZ is meaningless (address space); RSS undercounts (misses compressed/swapped pages); the number that actually matters for real memory pressure is `phys_footprint` (macOS-specific, but the general lesson — "measure the right memory metric, not whatever's easiest to print" — is universal). A naive O(n×m) LCS diff algorithm caused a 77GB memory spike and swap-thrashed the whole host; the fix chain was: common-prefix/suffix trim → line interning to ints → Myers O(N·D) linear-space diff (the diffutils/git-standard algorithm) → a hard size-guard that refuses to invoke the differ above a threshold and falls back to a snapshot. Tests have no memory ceiling by default — a runaway algorithm under test can take down the whole host, not just fail the test; consider resource-bounded test execution. Git worktrees isolate the FILESYSTEM, not semantic overlap — three agents working in separate worktrees each independently solved the same overlapping problem, and the duplication only surfaced at merge; the mitigation is orchestration (knowing overlapping scopes before dispatch), not the worktree mechanism itself. Sub-agents can die on transient server-side rate-limits mid-work with substantial uncommitted work — the work is generally NOT lost (recoverable from the worktree), so recovery is "WIP-commit and continue from the main loop," not "start over."
- carry-forward: PORT the diff-algorithm chain (prefix/suffix trim → interning → Myers linear-space → size-guard) verbatim if any large-text-diffing feature is needed again — it's the textbook-correct approach and was learned the hard way here. DISTILL the phys_footprint-not-RSS lesson and the worktree-isolation≠scope-isolation lesson.

## 2026-06-20 — Render-path bugs, VM verification, multi-agent VM ops · status: current
**[U]/[P]** domain: testing/architecture
- learnings: a host-tested MODEL fix is not a fix for a RENDER bug, and reporting it as fixed anyway (twice, in this project's history) burns real trust — for user-facing render behavior, never call it fixed until proven on real UI. - carry-forward: DISTILL — the "render bug root cause is often view-rebuild-drops-restored-state" pattern and the "don't delegate long-running waits to sub-agents" operational rule are both broadly reusable.

## The SwiftUI/NSTextView compositor bug — full writeup · status: current, THE signature bug of this codebase
**[P]** domain: SwiftUI/AppKit/testing (but the META-lesson is universal)
- learnings: this is the project's most-referenced structural bug (echoed by name in many later entries above — "TSK-488", "compositor occlusion"). Root cause: attaching an `NSRulerView` subclass to a hosted `NSTextView`'s scroll view forces synchronous text layout DURING SwiftUI's own commit phase (the ruler's draw call happens inside `NSScrollView.tile()`, itself called mid-SwiftUI-commit) — this triggers a "laid out reentrantly" warning and SwiftUI SKIPS that frame's layer-content commit for SIBLING views laid out earlier in the same stack, leaving them blank on screen with NO trace in the view hierarchy (the views exist, have correct data, just never composited). Multiple plausible-looking fixes do NOT work (layer-backing flags, container wrapping, switching representable flavors, forcing redisplay) — the only real fix is structural: never attach an `NSRulerView`/subclass a `NSLayoutManager` for a text view hosted this way; render line-number gutters as a SEPARATE SwiftUI view synced via scroll-bounds notifications instead. CRITICALLY: this bug class is invisible to EVERY headless testing technique — view-tree walks pass (the views exist), `cacheDisplay`/`dataWithPDF`-style off-screen redraws pass (they bypass the compositor and draw fresh, lying about actual composition state) — the ONLY thing that observes it is `screencapture(1)` (or an equivalent OS-level capture API) against a genuinely live, composited window. The project's primary defense is NOT the test — it's a STRUCTURAL PROHIBITION (a one-line, statically-greppable code-review rule: never attach NSRulerView / never subclass NSLayoutManager for this view) — because the rule is cheap, has zero false-greens, and prevents the bug from being introduced at all, whereas the pixel test is expensive, VM-gated, and only belt-and-suspenders. The project also encodes a meta-test that deliberately re-introduces the bug behind an env-gated flag and asserts the pixel-variance detector actually goes RED — proving the detector has real teeth rather than being a test that can never fail.
- carry-forward: PORT the META-lesson verbatim into the next project's own methodology, independent of AppKit specifics: **for any bug class that is fundamentally "invisible pixels only, not tree-structure" (compositor bugs, occlusion, z-order, blend-into-background colors), the primary defense should be a structural/static prohibition documented and grep-able, with a pixel-capture test as belt-and-suspenders — and any pixel-detector test must be proven to have teeth via a deliberate, reproducible negative control.** This generalizes far beyond AppKit/SwiftUI to any UI stack with a compositor (web CSS z-index/occlusion, game-engine UI layers, etc). The specific NSRulerView/NSLayoutManager avoidance is [P] and moot if not reusing AppKit/TextKit, but SKIP the mechanism, PORT the meta-lesson.

- learnings: `xctest`/`cacheDisplay`/`dataWithPDF` all "lie" about composition for the same reason — they don't go through the real window-server compositor; if a bug class is visible-pixels-only, the test must be pixel-level too (live-window screencapture, or an equivalent). ## File-path cache keys vs content-hash; `@Published` publish-loop; ForEach-materializes-array leak · status: current
**[U]** domain: perf/SwiftUI
- learnings: keying a cache on a full-content hash is O(N) per call and gets called on every UI re-render — key on `(identity, cheap-length-or-metadata)` instead, using length as a coarse but automatic change detector. A `@Published` setter fires its change signal unconditionally regardless of whether the value actually changed — if a view's render path writes back to the same published property (even indirectly, via a controller class), this can create an infinite render→republish→render loop that manifests as steady memory growth (looks exactly like a leak but is actually per-cycle transient allocation churn outpacing GC/ARC reclaim); the fix is to DEDUPE AT THE PUBLISH SITE (compare new-vs-last before invoking the published setter), and the dedupe state must live on a long-lived object, not transient view-local state. A helper function that materializes a full array from a range/stride inside a UI body function reallocates that array on EVERY re-render — for a large collection this creates steady RSS growth and visible stutter under scroll; use a lazy `Range` directly instead of calling `.map` to eagerly build an array, when the UI framework's iteration primitive accepts a lazy collection.
- carry-forward: DISTILL — all three (cache on cheap-metadata not full-content-hash; dedupe-at-publish-site to prevent republish loops; prefer lazy ranges over eagerly-materialized arrays in hot render paths) are universal perf-engineering patterns for any reactive/observable UI framework, not SwiftUI-specific in spirit.

## `swift build` lock contention piles up silently · status: current
**[P]** domain: build/process
- learnings: multiple overlapping build invocations (e.g. from an impatient retry when an earlier one hadn't printed output yet) leave zombie processes holding the build-system's lock, serializing all subsequent builds behind them — symptom is builds/tests taking wildly longer than expected with no obvious cause; "no output" from a background build task usually means it's blocked on a lock, not actually compiling. Don't fire a new build until the previous one has genuinely finished; investigate before broadly killing build processes (a narrow, deliberate kill of identified PIDs is safer than a broad pattern-kill, which can also be blocked by a safety classifier anyway).
- carry-forward: DISTILL (a generic "don't retry a slow build by launching a second one; check for lock-holding zombies first" operational habit).

## Things to NOT do — the codebase's own postscript list · status: current
**[P]/[U]** domain: mixed (SwiftUI/shell/packaging/security)
- learnings: this is a curated "don't re-break this" list distilled from real incidents, restated compactly: don't subclass NSLayoutManager or attach NSRulerView (compositor bug, see above); don't `cd && command` in shell (use `-C`/absolute paths, since compound commands defeat permission allowlists); don't bulk-strip a signed bundle without properly clearing extended attributes afterward (`strip(1)` can re-apply metadata that then fails runtime-hardened codesign, and naive `xargs`-based attribute-clearing can silently fail on the bundle root due to quoting — use a recursive form directly); don't change a stable bundle identifier (breaks all TCC grants); don't iterate a string by user-perceived "Character" when scanning for line-ending bytes (a CRLF sequence is a single grapheme cluster to a Character iterator, so a naive scan for a line-feed byte never matches — iterate unicode scalars/bytes instead); don't re-encode already-optimized image assets through a lossy high-level packing tool when a byte-preserving low-level tool exists; don't let a "core/logic" module import a "UI framework" module even transitively (the module-boundary discipline is what keeps the fast unit-test tier UI-free); don't write to well-known user-data directories from automated/restore code paths (permission-prompting + grants that don't survive ad-hoc rebuilds); don't bypass a failing pre-commit/security hook.
- carry-forward: DISTILL the shape (a codebase should maintain exactly this kind of curated "postscript of real incidents" list); the individual bullets are mostly [P]/platform-specific but a few are [U] (module-boundary discipline, don't bypass failing hooks, compound-command shell rule).

## VM smoke testing without Xcode / with Xcode addendum; macOS 15 Screen Capture Privacy; launchctl-asuser env stripping · status: current
**[T]** domain: VM/macOS
- learnings: a swift.org toolchain install (no Xcode) can compile and run the app but CANNOT run XCTest at all on macOS (XCTest.framework ships exclusively with Xcode) — plan for a real Xcode install on any macOS CI/VM box that needs to run tests, not just build. Launching a GUI app over SSH into a VM's actual GUI session requires `launchctl asuser <uid>` (a bare SSH-spawned process won't attach to the WindowServer session) — and remote screen-capture requires the SAME trick plus its own Screen Recording TCC grant. Separately, macOS 15+ added a "Screen Capture Privacy" feature that redacts window CONTENT from `screencapture -l<windowID>` specifically for processes whose TCC ownership is ambiguous (e.g. spawned via `sudo launchctl asuser`, where the launching UID is root but the session UID differs) — full-screen capture still shows the desktop/menu bar but the target window's content is blanked, even with every relevant TCC grant nominally in place; this has no clean automated fix (installing the app as a real per-user LaunchAgent so ownership is unambiguous is one option; manual visual inspection of the VM's actual display is the fallback with no automation cost). `launchctl asuser` resets env to the target user's clean session env — the common `/usr/bin/env VAR=x cmd` trick for passing one-off env vars does NOT survive this boundary; wrap the whole invocation in `sh -c '...'` with the vars set INSIDE that shell string instead, and fully detach stdio (`>/dev/null 2>&1 </dev/null &`) or the calling SSH session will hang waiting for the child's fds to close.
- carry-forward: PORT the macOS-VM-remote-GUI-automation recipe wholesale (Xcode-needed-for-XCTest, launchctl-asuser-for-GUI-attach, the sh-c-env-wrapping trick, stdio-detachment) if the next project again uses a UTM/VM-based macOS test lane — these are all concrete, reusable operational recipes. The Screen Capture Privacy limitation is a real, unavoidable macOS 15+ platform constraint worth flagging early in any pixel-capture test strategy.

## Swift 6.1+ concurrency tightening: `super.setUp()`/`super.tearDown()` and `NSEvent` Sendable drift · status: current
**[P]** domain: Swift concurrency
- learnings: a `@MainActor`-isolated test class calling `super.setUp()`/`super.tearDown()` on a non-Sendable, non-isolated base class trips a strict-concurrency "sending self across an actor boundary" error under newer Swift — the fix is simply to drop the super calls (the base implementations are no-ops anyway). A type that becomes `Sendable` in a newer language-version toolchain but wasn't in an older one used on a different build machine causes cross-toolchain build divergence for code that returns that type from an actor-isolated closure — extract only the specific PRIMITIVE fields you need before entering an isolated scope, and return only Sendable primitives across the actor boundary, rather than passing the whole non-Sendable object across.
- carry-forward: DISTILL — both are concrete Swift-concurrency migration patterns (drop no-op super calls under strict concurrency; extract-primitives-before-crossing-actor-boundary) directly relevant if the next project again targets multiple Swift toolchain versions across host/CI/VM.

## Foundation URL parser + relative-path resolution drift across OS/Foundation versions · status: current
**[P]** domain: Foundation/cross-version
- learnings: `URL` parsing/fragment-extraction and relative-path standardization behavior both DIFFER across Foundation versions on the same API call with the same input (a `URL(string:)` fragment accessor changed for `about:` URLs; `URL(fileURLWithPath:relativeTo:)` standardization gave a genuinely different resolved path across two Foundation versions) — this class of bug is invisible on a single dev machine and only surfaces when a secondary build environment (here, the VM) uses a different OS/Foundation version, acting as an unplanned "canary." Prefer field-by-field comparison over round-tripping through a URL-components abstraction (reserialization can differ across versions), and prefer manual string concatenation (`appendingPathComponent`) over relative-URL construction when you need a specific, version-stable resolution behavior. Pin any such platform behavior with a unit test and run it on every distinct OS/Foundation version available (a second real machine is a genuine asset here, not just redundant CI).
- carry-forward: DISTILL — the general principle ("standard-library URL/path APIs can silently change semantics across OS versions; test on every real target OS version, prefer explicit string-level path handling for anything load-bearing") is directly reusable, independent of Foundation specifically.

## Memory + perf audit (2026-05-18 multi-agent sweep) — cluster of ~15 concrete perf entries · status: current
**[P]/[U]** domain: perf/SwiftUI/AppKit/FFI/C-interop
- learnings (each is a standalone, verbatim-portable pattern):
  - a non-lazy vertical stack inside a scroll view instantiates EVERY child up-front (a 1MB CSV file ballooned process memory to ~1GB this way) — always use the framework's lazy/virtualizing container for any collection that can grow past a few dozen rows; verify the "still lazy inside a two-axis scroll view" claim empirically, don't assume from docs.
  - a multi-process rendering engine (WebKit-style) shows up as several persistent helper processes in system memory tools once ANY instance of it has ever been created in the app's lifetime — don't misattribute that baseline to the app's own code; use the OS's actual per-process physical-footprint tool, not a naive RSS sum, when investigating a memory complaint.
  - wrapping a platform dynamic-color type in a UI-framework color wrapper allocates a fresh wrapper object on every access with NO caching — hoist repeatedly-used ones into a small `static let` palette; the dynamic (light/dark-mode-aware) resolution still works correctly because it resolves at DRAW time, not at wrapper-construction time.
  - synthesized structural equality on a type that (transitively) holds a large String/Data payload performs a full O(N) content compare on every diff-equality check that a UI-diffing framework performs — for a type used in a large observed collection, implement equality manually on cheap identity/discriminator fields instead (URL + byte-count + encoding, not full content); this generalizes to any type holding a big payload that will be equality-compared frequently by a reactive framework's diffing.
  - `Process()` + `waitUntilExit()` followed by a synchronous full-buffer read of stdout/stderr DEADLOCKS once output exceeds the OS pipe kernel buffer size (~64KB on macOS) — the child blocks writing into a full pipe while the parent is blocked waiting for exit; drain both pipes CONCURRENTLY (on separate threads/queues) while/before waiting, never sequentially after.
  - a C-callback-based context pointer (any FFI/C-API pattern that stores a raw pointer as long-lived "user data," e.g. filesystem-event streams, display-link callbacks, C-array callbacks) needs explicit retain/release callback functions wired into the C API's context struct — passing an unretained pointer with a manual owner and no retain/release lets ARC free the Swift object while the C API still has an in-flight callback against it (a use-after-free).
  - a regex/pattern cache with a "last compiled" slot must have a SEPARATE negative-cache slot for "this pattern failed to compile" — collapsing success and failure into the same nilable slot means an invalid pattern gets recompiled (and re-fails) on every single call site invocation instead of being remembered as invalid.
  - a symlink-resolving path-canonicalization call is a real syscall (`realpath()`-class) — cache it with a bounded LRU keyed on input path when called per-row/per-redraw in a UI body.
  - a "does this set contain X" check backed by a plain array/list is O(N) — maintain a parallel Set-backed index for any membership check performed inside a UI body/render loop, especially when it's called in a nested loop (N rows × M redraws).
  - a text-layout engine's "lay out everything up front on any string assignment" default is the single biggest UI-thread win to disable for large documents — enable non-contiguous/incremental layout so only visible glyph ranges are laid out; this is only safe when the line-number gutter (or equivalent) is NOT itself forcing full layout via a synchronous ruler-style callback (ties back to the compositor bug above).
  - batch multiple attribute-mutation calls on a mutable rich-text storage inside explicit begin/end-editing brackets — without it, an internal attribute-storage indexer re-fixes-up after every single mutation call, which is measurably costly for thousands of runs (e.g. syntax highlighting) in one pass.
  - a "paint runs over a base string with overlapping ranges, later wins" algorithm should use a SWEEP-LINE approach (sort start/end events, maintain an active-set ranked by input order) rather than allocating a per-CHARACTER auxiliary array — O(K log K) in run count with zero per-character memory, vs O(N) memory in document length for the naive canvas approach; validate a sweep-line rewrite with a DIFFERENTIAL test against the old naive implementation on randomized overlap-heavy inputs, not just example cases.
  - bridging a native string to the platform's legacy 16-bit-code-unit string type just to read its `.length` materializes the FULL UTF-16 representation — for large strings that's tens of milliseconds per call; use the native (UTF-8-backed, O(1)) byte-count accessor for any cache-key/change-detection purpose, reserving the legacy-type length only for APIs that genuinely need UTF-16 offsets.
  - a large top-level app-icon image representation decodes to a multi-megabyte in-memory bitmap that stays resident while any window is showing, even though it's visible to virtually nobody (Finder's extreme-zoom Get Info view) — dropping the largest unnecessary representation from an icon asset is a cheap, safe memory win.
  - a lock-free-looking "release outer lock between cache-miss and expensive-compile, then take a per-key lock" pattern can still race if two threads both first-touch the SAME key concurrently and both proceed to compile before either writes the cache — the fix is a lazily-allocated PER-KEY lock (allocated under the outer lock) plus a double-checked cache read after acquiring the per-key lock, so different keys still parallelize but same-key races are eliminated.
- carry-forward: PORT the whole cluster as a checklist for the next project's own perf-hardening pass — nearly every item here ([P] framework-specific in mechanism but [U] in shape) will recur in some form in any reactive-UI + native-text-editing + FFI-bridged-native-core architecture, which is exactly what's being rebuilt.

## Schema-version guard is mandatory for any Codable/JSON persistence store · status: current
**[U]** domain: persistence
- learnings: a persistence layer that decodes Optional fields gracefully will silently accept a NEWER schema version's file (extra additive fields just get dropped on decode), and if the reader then re-writes that file at some later point (e.g. on quit), it DESTROYS the newer fields it never understood — any persisted-schema store with a `currentSchema` constant needs an explicit "refuse to read (and definitely refuse to re-write) a file whose declared schema version exceeds what this build understands" guard.
- carry-forward: PORT — a concrete, easily-missed data-safety rule (schema-version refusal, not just graceful-optional-decoding) worth baking into the next project's persistence layer design from the start, especially given multiple UI frontends (TUI/WebUI/native) will likely share persisted state formats.

## Lazy workspace/session restore — don't materialize every item eagerly on launch · status: current
**[U]** domain: perf/architecture
- learnings: a multi-tab/multi-document session-restore feature should restore each item as a lightweight PLACEHOLDER (knows its identity/URL, hasn't loaded content) and materialize (actually read/parse) only the item that's immediately visible/focused — with materialization idempotent so re-selecting an already-materialized item is a no-op. Noted caveat even in the "done" version: if materialization runs synchronously on the main/UI thread, selecting a lazy placeholder for a very large item still freezes the UI briefly — the fully correct fix needs an explicit async "loading" state + a UI placeholder for it, which was left as a deferred follow-up here.
- carry-forward: DISTILL — the lazy-placeholder-then-materialize-on-focus pattern for session restore is a strong architectural default to adopt from day one in the next project (rather than retrofitting it, as happened here), including going straight to the async-loading-state version rather than the synchronous-materialize version that was later flagged as still-imperfect.

## Close/cleanup paths must purge ALL URL-keyed / id-keyed caches, with a sibling-still-open guard · status: current
**[U]** domain: architecture
- learnings: any cache keyed on a file URL or a tab/document id will leak entries on close unless explicitly pruned at every close path — and a URL-keyed cache specifically needs a "is any OTHER open tab still using this URL" guard before evicting (so "open the same file in two tabs, close one" doesn't blow away the other's cache). Multiple close paths (single close, close-others, close-to-the-right, etc.) each independently enumerating every per-item cache/dict to clean up is itself an anti-pattern — this was later fixed with a registerable close-hook mechanism (see the coordinator-pattern entry below) specifically because per-tab dicts kept silently leaking when a new one was added and someone forgot to add it to all N close paths.
- carry-forward: DISTILL (both halves: the sibling-still-open eviction guard, and the close-hook-registration fix for the "N close paths each need to know about every cache" problem — see the TabCoordinator entry below for the actual mechanism).

## Mermaid runtime attached to a WKWebView on demand — CSP/attack-surface hygiene, not just perf · status: current
**[P]** domain: WebKit/security
- learnings: an initial fix that gated a large injected script (`WKUserScript`) behind "install once per webview instance, on first document that needs it" was later revisited for a SECURITY reason, not just perf: a `WKUserScript` bypasses CSP entirely, so leaving a large third-party JS runtime attached to a webview that has since navigated to a document that doesn't need it is unnecessary attack surface — the fix evolved to actively EVICT the script (`removeAllUserScripts()`) when the current document no longer needs it, computed per-document-load rather than once-per-webview-lifetime. Noted structural caveat: `removeAllUserScripts()` is only safe to use for a single-script-at-a-time scheme; if a second unrelated user script is ever added to the same webview, this eviction approach needs to move the removable script to its own isolated content world first.
- carry-forward: PORT — the general rule ("a user-script/content-script injection mechanism bypasses CSP; treat conditional script attachment as a SECURITY control surface, not just a perf optimization, and actively evict when no longer needed") is directly relevant to any future embedded-webview architecture with optional heavy JS runtimes (mermaid, katex, etc. — both named as likely reused).

## Shared process-pool for multiple WebView instances of the same kind · status: current
**[P]** domain: WebKit/perf
- learnings: without an explicit shared process-pool object, every new webview configuration (created fresh, e.g. on every tab-switch-triggered view recreation) spawns a brand-new heavy content-rendering helper process — share one process-pool instance across all same-kind webviews in the app (a `static let`) so tab switches that recreate the SwiftUI-side view don't also respawn the underlying OS-level content process.

## Equality-guard `@Published`-style setters at every WHOLESALE assignment site · status: current
**[U]** domain: perf/reactive-architecture
- learnings: reiterates and generalizes the earlier `@Published`-republish-loop lesson to every assignment site (not just the ones that caused an infinite loop): any place that assigns a whole new value to an observed/published property should guard with an equality check first, or expose a setter method that does so and route all callers through it consistently — otherwise semantically-identical repeated updates (e.g. an idle poll returning the same result, a callback re-firing the same computed summary) cause needless full re-renders of every observer.

## `static let` of a non-Sendable-but-actually-thread-safe type needs an explicit, documented unsafe opt-out · status: current
**[P]** domain: Swift concurrency
- learnings: several standard-library-adjacent types (date formatters, encoders, etc.) are thread-safe for read-only use in practice but aren't formally marked Sendable, so a strict-concurrency compiler rejects a shared static instance of them — the fix is an explicit unsafe opt-out annotation, paired with a comment documenting WHY it's actually safe (the type's real-world thread-safety guarantee), rather than working around the compiler with some other indirection that hides the actual reasoning.
- carry-forward: DISTILL (the pattern "explicit, documented unsafe opt-out with a stated reason, not a workaround that obscures the reasoning" is a good general concurrency-migration discipline for any strict-concurrency Swift codebase).

## Render size caps for expensive, multi-stage content pipelines · status: current
**[P]/[U]** domain: perf/architecture
- learnings: a multi-stage rendering pipeline (parse → AST → generate output → load output into a separate rendering process) can allocate several MULTIPLES of the input size transiently across its stages — a moderately-sized input file (tens of MB) can spike memory by hundreds of MB when pushed through such a pipeline. The mitigation is an explicit, conservative size cap above which the expensive pipeline is skipped entirely in favor of a lightweight placeholder/fallback view — with a SEPARATE, larger cap for a cheaper degraded mode (e.g. plain-text display) that doesn't invoke the expensive stages at all.
- carry-forward: DISTILL — the general pattern (explicit size-based circuit-breaker for any multi-stage content pipeline with multiplicative memory cost, with a cheaper fallback tier below the hard cutoff) is directly applicable to markdown/HTML rendering in the next project too.

## DocumentModel god-object split — coordinator-extraction pattern with invariant tests · status: current, architecturally significant
**[U]** domain: architecture/SwiftUI
- learnings: a single giant observable model (thousands of LOC, dozens of published properties, 100+ public methods spanning many unrelated domains) causes a severe, hard-to-see performance problem in any observer-pattern UI framework: EVERY published-property write on the god-object republishes to EVERY observer of the whole object, so a keystroke in one unrelated UI area (e.g. a search field) re-renders totally unrelated views (e.g. a tab strip) — the first symptom seen in this codebase was a proliferation of manual "if x != newX" republish-suppression guards scattered through setters, which is itself a smell that the object is doing too much. The fix pattern: extract a separate `ObservableObject`/equivalent PER DOMAIN, store it as a child property on the god-object, and preserve existing call sites via thin forwarding get/set properties so the refactor doesn't ripple through calling code. CRITICALLY, this pattern needs an explicit REGRESSION-GUARD TEST per extracted coordinator — a test that mutates only that coordinator's own state and asserts the PARENT's change-notification fires ZERO times — because the whole benefit of the split can be silently undone by a future re-forwarding of the child's notification up to the parent (which happened multiple times here before the invariant tests existed), and a companion NEGATIVE-CONTROL test is needed to catch the opposite failure mode (the notification chain is broken so badly that even legitimate parent-level observers never fire).
- carry-forward: PORT — this entire pattern (per-domain ObservableObject extraction + thin forwarders for compatibility + a "child mutation causes zero parent republishes" invariant test with a negative control) is one of the highest-value architectural lessons in this whole file and should be the DEFAULT starting shape for the next project's own central document/app model, rather than discovering the need for it after the model has already grown into a god-object.

## `addCloseHook`-style registration for per-item cleanup subsystems · status: current
**[U]** domain: architecture
- learnings: when N different "close" code paths (close-one, close-others, close-to-the-right, etc.) each need to run cleanup for every per-item subsystem (per-tab caches, per-tab cursor state, per-tab diagnostics, etc.), enumerating them by hand in each close path is a silent-leak generator — every time a new per-item subsystem is added, someone has to remember to add its cleanup to all N close paths, and this project found subsystems that had been leaking forever because nothing ever cleaned them up. The fix: a single registration mechanism (`addCloseHook { id in ... }`) that each subsystem calls once at its own init time, and a single `cleanupAfterClose(id:)` entry point that runs every registered hook — so adding a new per-item subsystem in the future requires touching exactly one place (its own init), not N close paths.
- carry-forward: PORT — the close-hook-registration pattern (inversion of control: subsystems register their own cleanup rather than close-paths enumerating subsystems) is a directly reusable, high-value architectural pattern for any app with multiple per-item subsystems and multiple ways to remove an item.

## SwiftUI republish forwarding amplifies every tick — the "don't forward, observe directly" correction · status: current
**[U]** domain: architecture/perf
- learnings: this is the explicit SELF-CORRECTION of the earlier (2026-05-?? "SwiftUI child-ObservableObject changes don't propagate") entry — the original fix (pipe every child's `objectWillChange` up into the parent's `objectWillChange`) is "seductive" (matches the mental model of "I want my parent to update when my child changes") but in practice reproduces the SAME god-object republish-cascade problem the coordinator-extraction was meant to solve: every child tick (even unrelated ones — a background poll, a hover event) republishes the ENTIRE parent, re-evaluating every observer of the parent. The corrected pattern: don't forward child-to-parent notifications at all; instead, every view that needs the CHILD's state observes the CHILD object directly (not through the parent). This requires updating every call site that previously relied on the parent's notification to also fire for child changes — treated as a one-time migration cost, verified by an invariant test pinning the new (severed) contract, with a negative-control test guarding against "the chain is broken AND the legitimate parent-level observers were never reconnected."
- carry-forward: PORT — this self-correction is itself a valuable meta-lesson: **the natural first fix for "my parent doesn't see my child's changes" (blanket propagation) is very often WRONG at scale in an observer-pattern UI framework; the correct fix is almost always "observe the child directly, don't propagate."** Worth stating as an explicit architectural rule from the start of the next project rather than rediscovering it after the propagation anti-pattern has already shipped and needs walking back.

## Key learnings from this batch

- **The compositor-occlusion bug class (WKWebView/opaque-native-view siblings blanking out) is this project's single most expensive, most-referenced lesson.** It recurs by name across many later dated entries and has its own dedicated section with a full root-cause writeup. Its meta-lesson — **structural/static prohibition first, pixel-capture test as belt-and-suspenders, and prove the pixel-detector has teeth via a deliberate negative control** — is the single most portable idea in this batch and should be adopted as a standing methodology, independent of AppKit/SwiftUI specifics, for ANY UI stack with a compositor (including a future WebUI/TUI frontend).
- **Test-vehicle mismatch is a recurring, expensive failure mode.** Multiple entries (CM6/jetsam-kill, headless-webview-gesture-synthesis, CGEvent-can't-drive-webview-text, spawned-app screencapture-doesn't-composite) all reduce to the same root lesson: pick the RIGHT test vehicle for the bug's actual observability class (in-process webview test for webview render behavior; live-window screencapture for compositor bugs; host model tests for logic) — using the wrong vehicle burns many round-trips and can produce structurally unwinnable tests.
- **Staleness (of builds, of linked artifacts, of the task board, of doc comments) is the dominant source of wasted cycles in this project.** SwiftPM incremental-build staleness (rsync-mtime-preserved, FFI-`.a`-not-a-tracked-input), VM `dist/` staleness, task-board `understanding`-field staleness, and doc-comment staleness all cost multiple burned sessions each. "Verify against current, real state before trusting cached/second-hand state" is the umbrella lesson.
- **Agent-orchestration failure modes are now well-characterized**: unbounded subagent fan-out (burned ~half a quota), account-wide session limits needing model-splitting, `Workflow` args not marshaling correctly, worktree disk exhaustion, and worktree isolation NOT preventing semantic overlap between concurrently-dispatched agents. These should all be encoded as day-one operating rules in the next project rather than rediscovered.
- **The "engine tested ≠ feature shipped" trap recurred multiple times** (FormulaEngine with zero view consumers; xlsx mode unreachable despite a passing hosting test) — a fully green test suite proves the MODEL layer, never that a view/route actually reaches it; always grep for a live, call-graph-reachable consumer before claiming a feature is shipped.
- **A large cluster of concrete, load-bearing perf fixes (2026-05-18 sweep)** — lazy virtualization, cache-on-cheap-metadata, republish-loop dedup, Myers-diff over naive O(n×m), FFI context-pointer retain/release, sweep-line overlap resolution — reads almost as a pre-built checklist for the next project's own perf-hardening pass.

## Decision records found — decision + rationale + outcome

- **Ad-hoc signing → real (even self-signed) local signing identity**, because TCC keys ad-hoc grants on a per-build code-directory hash that changes every rebuild, causing permanent re-prompt loops; a real identity keys on `(identifier, cert-leaf-hash)`, both stable. Outcome: worked, one-time re-prompt cost, then durable.
- **Never subclass NSLayoutManager / attach NSRulerView to the hosted text view**, structural prohibition over a fix, because the compositor bug's only reliable detector (screencapture) is expensive/VM-gated and the prohibition has zero false-greens. Outcome: became the primary, load-bearing defense; the pixel test is explicitly demoted to "belt and suspenders."
- **Hybrid syntax-highlighting architecture: keep the editor's own incremental parser for its native language set; add the separate whole-document engine only for the languages the incremental parser doesn't cover** — rejected a full cutover to the whole-document engine because it would regress fence-highlighting, auto-indent, comment-toggle, and large-file perf for the editor's incremental hot loop. Outcome: adopted as-is, documented via a full spike doc.
- **Migration policy: engines with an approved native-language port take user-facing bugfixes only on the old-language twin** (no perf/refactor/feature work) — to avoid double-investment during a staged rewrite. Outcome: actively enforced per this file's later entries (referenced repeatedly as ongoing policy).
- **AX automation stays a separate, structural lane from screenshot-based UI automation**, owner-decided explicitly, because in-process accessibility trees are empty for SwiftUI-hosted views and the two lanes have genuinely different strengths (structural/pixel-free vs pixel-only/vision-based). Outcome: foundation built (click-target registry + event synthesis), explicitly incomplete as of the range covered.
- **Mermaid runtime script attachment: evict-per-document, not install-once** — revisited from a pure perf decision to a security decision once it was recognized that user-script injection bypasses CSP. Outcome: shipped as an active install/evict state machine, not a one-time flag.
