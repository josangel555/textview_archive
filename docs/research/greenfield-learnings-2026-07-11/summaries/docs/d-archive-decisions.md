**`archive/CORE_ARCHITECTURE_RESEARCH_2026-05-30.md`** — 9-agent web survey of how real editors detach core from UI (VS Code, Neovim/Kakoune/Emacs, xi-editor, Zed/Helix, JetBrains, macOS XPC, CM6/Scintilla/tmux/Figma/Jupyter) · status: current, foundational
- learnings: **the load-bearing finding for the whole reusable-core thread**: xi-editor's own post-mortem is direct primary-source evidence that a process-separated, async core↔UI boundary on the *interactive read path* is a mistake ("async is a complexity multiplier"; "if we just had the text available as an in-process data structure... it would have been quite straightforward"). Every surviving system (Zed/GPUI, CM6, Helix, Scintilla) keeps that specific seam synchronous and in-process.
- learnings: async/RPC is fine — but only at coarse, genuinely-remote seams (LSP/DAP, collab, remote-dev), never fine-grained per-keystroke queries. The reconciliation for a remote-vision app: keep the core API synchronous; treat *remote* as a separate coarse state-sync transport (level-triggered snapshot+delta, optimistic-local) rather than making the core API itself async.
- learnings: XPC (Apple's async cross-process answer) is explicitly the wrong model to imitate for cross-platform reuse — it's Apple-only and doesn't map to a browser/Linux/TUI client.
- carry-forward: PORT — this survey (and its conclusion) is directly reusable as the architectural north star for the next project's Rust-core-behind-multiple-front-ends design; the citations (matklad, xi retrospective, Zed/GPUI blog) are durable references worth re-citing.

**`archive/CORE_DESIGN_HARDENING_2026-05-30.md`** — 14-agent adversarial hardening pass (9 lenses + 3 pre-mortems + completeness critic) on the converged reusable-core design, fact-checked against the live codebase · status: current, high-value
- learnings: verdict was "shape is sound, sequencing/scope is not" — the design's expensive one-way doors (Rust/FFI, wire freeze, capability handshake, optimistic-local) were being pressure-tested as if committed, while gated on an unanswered product-identity question ("is the Mac app the product, or is the core the product?"). This meta-point (harden decisions before the gating question is answered) is itself a reusable process lesson.
- learnings: 29 concrete risks (R1-R29) each with a fix, e.g.: no per-doc version/`clientSeq`/`siteId` in the wire envelope (retrofitting after freeze = flag-day migration); UTF-16/NSRange baked into wire position types (LSP's most-regretted decision, about to be repeated); content modeled as `String` not `(bytes, encoding, eol)` (silently corrupts non-UTF-8/non-LF files on save); closed Codable/uniffi enums break additive wire evolution; Rust+UniFFI has a ~1,416ns/call + memcpy floor vs swift-bridge's <1ns zero-copy, meaning "near-free doc-text reads" dies once UniFFI is chosen for hot paths.
- learnings: **19 named "one-way doors"** (§4) each with cheap "insurance to take NOW" — the single most reusable artifact in this whole batch for the next project: reserve `clientSeq`/version/`siteId`/correlation-id in every envelope, keep the wire as an open-tagged shape with an `unknown(...)` fallback, use UTF-8 byte offsets (not UTF-16/NSRange) as the wire-native position unit, model content as `(bytes, encoding, eol)` from day one, decide the FFI ABI's zero-copy story before doc-text hot paths depend on it.
- carry-forward: PORT — the one-way-doors table (§4) and the risk register (§3, esp. R1/R4/R6/R16/R18) should be copied near-verbatim into the new project's design doc as a pre-flight checklist, since they're mistakes-to-avoid independent of which specific stack is chosen.

**`archive/CORE_LINUX_PORTABILITY_2026-05-30.md`** — import-surface analysis of how portable ViewerKit/ViewerCore actually are to Linux · status: current
- learnings: the codebase was *closer* to portable than assumed — only 8 import/API blockers total, but the validator caught **2 more Combine-coupled `ObservableObject` Core types** (`LSPNavigationStore`, `LSPDiagnosticsStore`) that earlier passes missed, because they resolve Combine via Foundation's Apple-only re-export with no explicit `import Combine` — a subtle grep-miss trap worth remembering when auditing for portability.
- learnings: concrete portability map: NSColor→RGBA (trivial, 2 files), CoreServices/FSEvents→a `FolderWatching` protocol with inotify on Linux (largest single item), CryptoKit→swift-crypto or hand-roll, SQLite3 needs a modulemap shim, Combine `ObservableObject`s need AsyncStream/callbacks. Most compile-blockers vanish entirely under a Rust core (`notify`, `rusqlite`, `sha2` crates are natively cross-platform) — a genuine point in Rust's favor.
- learnings: the two hardest items — the event/reactive-state boundary and the Command/Query/Event protocol — are language-agnostic and must be solved either way (Swift-portable or Rust); this is the argument for "harden the boundary first regardless of language" that recurs across this whole doc cluster.
- carry-forward: DISTILL — the specific Swift blocker inventory won't transfer to a fresh Rust-first project, but the *methodology* (import-surface grep + explicit blocker/shimmable/already-portable table) is a good template if the new project ever needs a similar audit, and the meta-conclusion (boundary > language) is directly portable.

**`archive/CORE_UI_BOUNDARY_AUDIT_2026-05-30.md`** — audit of how the (Swift) UI actually calls Core today, what's leaky, and 3 candidate interface shapes · status: current
- learnings: `DocumentModel` (the ~2261-LOC `@MainActor ObservableObject` orchestrator) lives in ViewerUI, not Core — the months-long "extract a reusable core" work is really "extract the orchestration state machine out of the UI layer," not "move ViewerCore" (which was already clean, only 2 AppKit imports).
- learnings: **the biggest gap found was the missing server→client event/notification stream** — the existing MCP surface (`AutomationHost`, 10 tools) is request/response only and explicitly *drops* notifications (`MCPServer.swift:117-122`). Any remote/browser/live-diagnostics UI needs a duplex push channel; this was correctly flagged as the #1 build-first item.
- learnings: recommended interface = "Option C": one serializable Command/Query/Event protocol as the contract, with an in-process Swift fast-path for the Mac UI (near-zero tax locally, same contract remotely = same UI over a transport swap). This became the converged design in the companion `STATE_ARCHITECTURE` doc.
- learnings: **DSL/MCP drift is a live, already-observed failure mode** (ScriptRunner DSL vs MCP tool catalog vs CM6 bridge — three vocabularies with zero shared code) — a concrete warning against letting multiple serialization surfaces for the same capability set diverge, worth designing against from day one in the next project (one generated catalog, not three hand-maintained ones).
- carry-forward: DISTILL — the "what can move down to Core" candidate list (tab state machine, sidebar tree logic, dirty-tracking/save orchestration, git-log markdown assembly) is codebase-specific, but the boundary-shape reasoning (Option A/B/C tradeoff table) and the DSL-drift warning are directly reusable for structuring a new Rust-core/Swift-UI boundary from the start.

**`archive/RUST_CORE_PLAYBOOK_2026-05-30.md`** — 16-agent-researched, production-grade Rust playbook for the headless core (workspace layout, dependency shortlist, sans-IO architecture, testing, build/CI) · status: current, high-value reference
- learnings: **sans-IO synchronous functional core** (`&mut self` state machine, time/randomness injected as parameters never read ambiently, effects returned as data not callbacks) is the single highest-leverage architectural decision, validated against quinn-proto, Crux, and Firezone as reference implementations, not just the xi post-mortem.
- learnings: bincode is dead (RUSTSEC-2025-0141, permanently unmaintained) — use `postcard` for Rust-to-Rust wire, `rmp-serde` (MessagePack) for cross-language (Swift/JS) wire, with the `to_vec_named()` (not `to_vec()`) trap called out explicitly (default encodes structs as arrays, Swift/JS `Codable` expects maps).
- learnings: mmap is fundamentally incompatible with `#![forbid(unsafe_code)]` (constructors are `unsafe`, external truncation → uncatchable SIGBUS) — default to safe seek+buffered reads, quarantine mmap into a separate leaf crate only if profiling proves random-access GB-file reads need it.
- learnings: concrete crate-layout convention (flat `crates/` a la rust-analyzer, `textview-core`/`textview-proto`/`textview-ffi`/`textview-tui`/`textview-wasm`/`textview-remote`/`xtask`), with the FFI crate as the *only* place unsafe lives, `forbid(unsafe_code)` everywhere else — this is exactly the shape reflected in the live `rust-core/` directory today, i.e. it was adopted.
- learnings: 10 open decisions (§10) each with a recommendation and one-way-door flag — e.g. hand-written `extern "C"` + cbindgen over swift-bridge (bus-factor-1, pre-1.0, no slice/Arc/Box support) or uniffi (double-serializes complex types); LSP async routing needs a spike, not upfront commitment; postcard/rkyv are dead ends for the Swift/JS cross-language tier by design.
- carry-forward: PORT — this is close to a drop-in playbook for the next project's Rust core: the lint config, `deny.toml`, CI job list, profile snippets (§7-9), and dependency shortlist with verdicts are largely stack-agnostic-enough to reuse directly, updating only crate versions.

**`archive/REUSABLE_CORE_STRATEGY_2026-05-30.md`** — the top-level Rust-core decision doc: goal, target matrix, gains/losses, phased ROI-gated recommendation · status: current, foundational
- learnings: the deciding question ("is the macOS app the product, or is the reusable core the product?") is framed as gating everything else — a reusable pattern for scoping any multi-front-end rewrite before committing to it.
- learnings: target matrix is the crisp argument for Rust: a Swift core is fine for "Mac + maybe a Mac TUI" but **fails Linux + Web outright** (no production Swift→WASM, FSEvents/AppKit/NSColor don't port) — this is the concrete evidence, not a vibe, for choosing Rust when Linux/browser targets are real.
- learnings: **the de-risking insight is the single most important sentence in the doc**: "the boundary matters more than the language" — harden one stable, serializable, transport-agnostic core API first; that alone (a) lets a TUI/WebUI be driven by the *existing* Swift core with no rewrite, (b) lets Rust be adopted subsystem-by-subsystem later with Swift tests as the oracle, (c) directly enables the remote/browser vision. This principle should anchor day-1 architecture in the next project even before any language choice.
- learnings: recommended phasing (harden boundary → one Rust pilot behind uniffi, e.g. the large-file pager → migrate perf/portable-critical subsystems → full Rust core only if multi-platform is committed, never hypothetical) is a sound incremental de-risking template, avoiding the "rewrite stalls at 80%, two implementations diverge" trap it names explicitly.
- carry-forward: PORT — for a project that is *already committing* to "Rust core supporting WebUI/TUI/remote transport" from day one (per the rebuild brief), this doc's phased caution is less load-bearing (the "should we rewrite" question is pre-answered), but the boundary-first principle and the target-matrix reasoning for *why* Rust over Swift-portable remain directly applicable evidence to cite.

**`archive/RUST_DEPENDENCY_AND_SIZING_2026-05-31.md`** — empirical dependency-blast-radius + bundle-size study (measured, not estimated, with `cargo tree` + real release-profile builds) · status: current, high-value empirical data
- learnings: **comrak's default features are a bloat illusion** — 67 transitive deps balloon from bundling its own CLI (`clap`) + syntect→onig (a C regex engine); `default-features = false` drops it to 13 pure-Rust deps with zero C, and syntect isn't even needed since tree-sitter does highlighting. This is a concrete "read the actual feature flags, don't trust the crate's default reputation" lesson.
- learnings: **postcard was reversed from the playbook's own recommendation** — its "tiny" reputation is for `no_std`/embedded; on a desktop host it drags in `heapless`+`cobs` (15 deps) and buys nothing. `rmp-serde` alone (5 deps, cross-language) replaced it for the wire tier. Shows the value of measuring rather than trusting a crate's marketing framing, even when a prior research doc recommended it.
- learnings: measured bundle sizing is genuinely reassuring — a full Rust core `.dylib` (pulldown-cmark + rmp-serde + tree-sitter-rt + notify + memmap2 + tracing + serde, opt-z+fat-LTO+strip+panic=abort) is only **441 KB**; the 36 MB shipped app is dominated by tree-sitter grammars (16 MB) and CM6/mermaid JS (4.2 MB), not the core logic itself. A Swift→Rust core swap is roughly bundle-size-neutral on macOS.
- learnings: `edition = "2024"` requires `#[unsafe(no_mangle)]` (not `#[no_mangle]`) — a hard compile error otherwise; noted as an empirically-confirmed gotcha worth keeping in institutional memory.
- carry-forward: PORT — the measured numbers (comrak no-default = 13 deps, postcard rejected, rmp-serde = 5 deps, dylib = 441 KB) are directly reusable inputs for the next project's initial Rust dependency choices, saving a re-measurement pass; re-verify crate versions are still current before trusting exact byte counts.

**`archive/STATE_ARCHITECTURE_2026-05-30.md`** — the converged core/UI state-architecture design (sessions, ownership split, subscriptions, optimistic-local, transport) synthesized from the whole research cluster · status: current, the capstone design doc
- learnings: **ownership split is the keystone pattern**: Core owns *domain* state (documents, content, edit state, git status, open-tab set); Client owns *view/ephemeral* state (scroll, cursor/selection, focus, fold state, viewport). This makes "reconnect can't move your scroll" true *by construction* rather than by careful bookkeeping — directly reusable for the new project's session-persistence design. (Note: the hardening doc found this split was *not yet true* in the shipped code as of 2026-05-30 — `SessionSnapshot` was persisting viewMode/zoom/scroll as Core-owned state — so treat as an aspirational target requiring deliberate schema discipline, not something that falls out for free.)
- learnings: level-triggered (not edge-triggered) subscriptions as the default push model — "here is the current state of X" rather than "X changed by delta Y" — validated against the Kubernetes reconciliation model and matklad's explicit recommendation; robust to dropped/reconnected links because a resync is just a resend of current truth, no missed-delta bookkeeping.
- learnings: single-writer-per-session (Core hosts N independent sessions, each pinned to ≤1 attached client) is explicitly what makes optimistic-local apply tractable *without* CRDT/OT — collaboration/sharing is deliberately deferred rather than half-built.
- learnings: hexagonal sync ports (`HostPorts`: `read`, `runProcess`, `watch`, `now`) injected at Core init, executed on whichever host the Core actually runs on (so "remote" just means the ports resolve against the Linux box's filesystem) — a clean, reusable abstraction shape for keeping the core testable and environment-agnostic.
- learnings: optimistic-local apply flagged as *likely necessary, not optional* for any remote vision — validated against Figma/Mosh/Fleet/vscode-neovim, all of which predict-locally to hide RTT; without it every keystroke over SSH blocks on a round-trip. Explicitly scoped as a client-side transport-adapter concern that must NOT leak into the local in-process path or the pure core API.
- learnings: rejected list is as valuable as the accepted list — no async core API, no fire-and-forget edge events, no sync-blocking boundary stretched over network, no rewriting the Mac GUI, no collab/shared sessions yet, no offline editing (explicit non-goal).
- carry-forward: PORT — §3 (converged decisions), §4 (rejected-with-reasons), and §5 (the consolidated shape + hypothetical `CoreClient`/`HostPorts`/`CoreEngine` interface sketch) are near-directly transferable to the next project's initial architecture doc, since the new project explicitly wants Rust-core-behind-multiple-front-ends from day one — this doc is effectively pre-written groundwork for that exact goal.

## Key learnings from this batch

1. **The xi-editor post-mortem is the single most load-bearing piece of external evidence in the whole codebase's architecture history.** It appears (directly or via its conclusion) in the editor-choice research, the core-architecture survey, and the state-architecture design: keep the interactive read path (UI querying text/cursor/layout) synchronous and in-process; confine async to genuinely coarse, remote, or crash-prone seams (LSP, collab, remote-dev). This should be a first-class citation in the new project's architecture doc.
2. **"The boundary matters more than the language"** (from `REUSABLE_CORE_STRATEGY`) is the de-risking principle that should anchor the new project even though it's committing to Rust from day one — a crisp, versioned, transport-agnostic Command/Query/Event protocol with reserved envelope fields (`clientSeq`, per-doc version, `siteId`, correlation-id) from the very first commit avoids the flag-day-migration trap this project's hardening review caught (R1/R6/R8/R9/R13 in `CORE_DESIGN_HARDENING`).
3. **Empirical measurement beat intuition repeatedly**: the vim-mode bundle estimate was corrected from 280 KB to ~100 KB via Bundlephobia; postcard was *reversed* from an earlier recommendation once actual `cargo tree` numbers showed it drags 15 deps on a desktop host; comrak's real dependency count only became visible after checking `default-features = false`. Pattern: research docs that make numeric claims without a measurement command run were later corrected by ones that did — prefer measuring early in the new project too.
4. **Concrete, durable design primitives worth carrying forward wholesale**: sans-IO synchronous functional core (`&mut self`, effects-as-data, time/RNG injected); Core-owns-domain vs Client-owns-view state split; level-triggered (not edge-triggered) subscriptions; single-writer-per-session as the thing that makes optimistic-local tractable without CRDT; UTF-8 byte offsets (never UTF-16/NSRange) as the wire-native position unit; content as `(bytes, encoding, eol)` never `String`.
5. **Editor-stack research (CM6 vs Scintilla vs NSTextView-family) held up in practice** — CM6 shipped, vim mode shipped, both per the original recommendation — validating the research methodology (side-by-side tables, decision trees keyed to explicit constraints, six-month-risk framing) as worth reusing even where the specific verdict may differ for a project that might target non-macOS front-ends from day one.
6. **A recurring failure mode to design against explicitly**: multiple serialization/vocabulary surfaces for the same capability drifting apart (ScriptRunner DSL vs MCP tool catalog vs CM6 bridge, "zero shared code" per the boundary audit). The fix named repeatedly across docs — one generated source-of-truth catalog, everything else derived — should be built in from day one in the new project rather than retrofitted.
