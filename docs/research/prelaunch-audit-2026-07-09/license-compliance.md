# Pre-Launch Product Review — Third-Party License & Attribution Compliance

**Dimension:** Bundled crate / tree-sitter grammar / Mermaid+CodeMirror JS / font attribution in
NOTICES, and copyleft/GPL contamination reaching the shipped closed binary.
**Repo:** `/Users/me/Documents/workspaces/claude/markdown_viewer`
**Date:** 2026-07-10
**Reviewer:** automated pre-launch audit (license-compliance lens)

---

## Executive summary

The project maintains a real attribution artifact — `THIRD_PARTY_NOTICES.md` — generated by
`scripts/gen-third-party-notices.sh` and guarded by `Tests/ViewerCoreTests/ThirdPartyNoticesTests.swift`,
plus a genuine copyleft firewall (`rust-core/deny.toml` license allow-list enforced by the
PR-blocking `supply-chain-gate` in `.github/workflows/pr.yml`). That firewall is working: **no
GPL/LGPL/EPL/strong-copyleft code reaches the shipped binary** — verified against `Cargo.lock` and
by grepping the bundled `mermaid.min.js`.

However, the **attribution side is materially incomplete for a public closed-source launch**, and
the single largest gap is structural:

1. **`THIRD_PARTY_NOTICES.md` is never bundled into the shipped `.app`.** Both the file header and
   the generator comment claim `scripts/build-app.sh` copies it into `Contents/Resources/`, but
   `build-app.sh` contains no such copy and the built `dist/TextView.app` contains no notices file.
   MIT/BSD/ISC/Apache-2.0 all require the copyright + license text to travel with binary
   redistribution — so today the shipped app carries **zero** third-party attribution.
2. **No Rust crate is attributed anywhere.** The 65 MB statically-linked `libmdvcore_ffi.a` pulls in
   ~30 shipping Rust crates (pulldown-cmark, regex-lite, memchr, unicase, bitflags, serde/rmp,
   tree-sitter runtime + highlight + regex/aho-corasick, and ~21 tree-sitter grammar crates). None
   appear in the notices. The generator's claim that these are "attributed via the rust-core
   notices" is a phantom — **no rust-core notices file exists** anywhere in the tree.
3. **~15 Rust-linked tree-sitter grammars** (rust, java, c, cpp, c-sharp, kotlin, lua, python, bash,
   yaml, html, css, go, ruby, sql) ship in the staticlib but are attributed nowhere; only the 6
   Swift-package grammars are listed.
4. **The Mermaid bundle is under-attributed.** `mermaid.min.js` is a fat bundle embedding DOMPurify
   3.2.1 (Apache-2.0 / MPL-2.0, © Cure53), cytoscape, dagre, katex, lodash, and d3 — attributed as a
   single "Mermaid, MIT, © Knut Sveidqvist" entry.
5. **The notices test has no teeth over the Rust or transitive-JS supply chain** — it asserts a
   hardcoded Swift-only subset, so none of the above can ever turn the gate red.

None of these are code-crash/data-loss defects, but items 1–3 are genuine **legal launch blockers**
for a publicly distributed closed-source binary. All are documentation/packaging fixes (no product
code change), so remediation is low-risk.

## Methodology

What I examined (static analysis only; no build, no window-opening tests):

- `THIRD_PARTY_NOTICES.md` (735 lines) — full read.
- `scripts/gen-third-party-notices.sh` — full read (the generator + its `--check` mode).
- `Tests/ViewerCoreTests/ThirdPartyNoticesTests.swift` — the CI guard.
- `scripts/build-app.sh`, `dist/TextView.app/Contents/Resources/` — to confirm what is actually
  bundled.
- `rust-core/Cargo.toml` (workspace), `Cargo.lock` (full crate enumeration — 150+ entries),
  `crates/{ffi,core,highlight,serve}/Cargo.toml` — to determine the *shipping* dependency graph vs
  the full workspace.
- `rust-core/deny.toml` + `.github/workflows/pr.yml` + `nightly-supply-chain.yml` — the
  copyleft/license enforcement path.
- `rust-core/link/` — confirmed `libmdvcore_ffi.a` (65 MB staticlib) + `mdv-serve` (31 MB) are the
  linked/shipped artifacts.
- Bundled web assets: `Sources/ViewerUI/Resources/mermaid/` (LICENSE, VENDOR.md, and grep of the
  2.5 MB `mermaid.min.js` for embedded license banners / sub-libraries / copyleft strings),
  `Resources/codemirror/` (BUILD.md), `Resources/canvas/` (hand-written, no third-party).
- Font sweep: `find` for `*.ttf/*.otf/*.woff*` across the repo — **none bundled** (app relies on
  system fonts).

What "shipping graph" means here: the macOS app links `rust-core/link/libmdvcore_ffi.a`, built from
`mdvcore-ffi → {mdvcore-core, mdvcore-highlight}`. `core` deps = serde, regex-lite, pulldown-cmark,
rmp-serde, memchr. `highlight` deps = tree-sitter, tree-sitter-highlight, tree-sitter-language, and
21 grammar crates. Workspace-only members (`tui`, `pm`, `web`) and build-deps (`cbindgen`, etc.) are
**not** in the app binary and are correctly out of scope for attribution.

## Findings

### F1 — `THIRD_PARTY_NOTICES.md` is not bundled into the shipped app  (P1, launch-blocking)

- **Evidence:**
  - `THIRD_PARTY_NOTICES.md:9-10` — "`scripts/build-app.sh` copies this file into
    `Contents/Resources/` of the assembled `.app`."
  - `scripts/gen-third-party-notices.sh:16-18` — same claim.
  - `grep -n -i 'notice\|THIRD_PARTY' scripts/build-app.sh` → **no matches**. `build-app.sh` never
    references or copies the file.
  - `find dist -iname '*notice*' -o -iname 'THIRD_PARTY*'` → **no matches**. The built
    `dist/TextView.app/Contents/Resources/` contains icons and language bundles but no notices file.
- **Impact:** MIT, BSD-2/3-Clause, ISC, and Apache-2.0 (all the licenses in the shipping graph) each
  require the copyright notice + permission/license text to be reproduced "in all copies or
  substantial portions" / "in the documentation and/or other materials provided with the
  distribution." A binary-only `.app` with no notices file (or About-box license screen) satisfies
  none of them. This is a straightforward compliance violation the moment the app ships publicly.
- **Suggested fix:** In `scripts/build-app.sh`, after assembling the bundle, `cp
  "$ROOT/THIRD_PARTY_NOTICES.md" "$APP/Contents/Resources/"` (or surface it via an in-app
  "Acknowledgements" menu item). Add a bundle-content assertion (see F5) so a missing notices file
  fails a gate. Also run `gen-third-party-notices.sh --check` in the PR gate to catch staleness.
- **Fix size:** S · **Fix risk:** safe

### F2 — Zero Rust-crate attribution; the "rust-core notices" it points to do not exist  (P1, launch-blocking)

- **Evidence:**
  - `scripts/gen-third-party-notices.sh:52-54` — comment: "The rust core carries its own copy of the
    full grammar set — those are attributed via the rust-core notices, not this Swift-package list."
  - `find rust-core -iname '*notice*' -o -iname 'license*' -o -iname 'copying*'` (excluding
    `target/`) → **no matches**. There is no `rust-core/NOTICES` / `THIRD_PARTY` file. The referenced
    attribution does not exist.
  - `rust-core/link/libmdvcore_ffi.a` (65 MB) is statically linked by the app (`Package.swift:20`).
    Its shipping graph (from `crates/{ffi,core,highlight}/Cargo.toml`) includes at minimum:
    `pulldown-cmark 0.13.4`, `regex-lite 0.1.8`, `memchr 2.8.1`, `unicase 2.9.0`, `bitflags 2.11.1`,
    `serde 1.0.228`, `rmp-serde 1.3.0` / `rmp 0.8.15`, `byteorder 1.5.0`, `tree-sitter 0.25.10`,
    `tree-sitter-highlight 0.25.10` (which pulls `regex 1.12.3`, `regex-automata`, `regex-syntax`,
    `aho-corasick 1.1.4`, `streaming-iterator`), `tree-sitter-language 0.1.7`.
  - None of these crate names appear in `THIRD_PARTY_NOTICES.md` (which contains only SwiftPM +
    Mermaid + CodeMirror sections).
- **Impact:** Every one of those crates is MIT / Apache-2.0 / BSD / Unicode-3.0 and requires
  attribution in binary redistribution. The single most-used shipped component (a 65 MB static lib)
  has no attribution at all. Apache-2.0 crates additionally require NOTICE-file propagation.
- **Suggested fix:** Extend `gen-third-party-notices.sh` to enumerate the *shipping* Rust graph
  (e.g. `cargo tree -p mdvcore-ffi --edges normal --target aarch64-apple-darwin` restricted to the
  ffi/core/highlight closure) and emit each crate's license from `~/.cargo/registry/src/**/<crate>/`
  (`LICENSE*` / `COPYING`). Do not hand-maintain — generate, so it can't drift.
- **Fix size:** M · **Fix risk:** safe

### F3 — ~15 Rust-linked tree-sitter grammars ship unattributed  (P1, launch-blocking)

- **Evidence:**
  - `rust-core/crates/highlight/Cargo.toml` links: `tree-sitter-json, -rust, -javascript,
    -typescript, -java, -c, -cpp, -c-sharp, -swift, -kotlin-ng, -lua, -python, -bash, -yaml, -html,
    -css, -go, -ruby, -md, -xml, -sequel` (21 grammar crates), and `crates/ffi/Cargo.toml` depends on
    `mdvcore-highlight`, so all 21 enter the shipped staticlib.
  - `THIRD_PARTY_NOTICES.md` lists only 6 grammars (javascript, json, markdown, swift, typescript,
    xml) — the Swift-package fold/structural set. The generator comment
    (`gen-third-party-notices.sh:48-54`) explicitly drops "the 8 highlight-only grammars" from the
    Swift list on the theory they're covered by the (non-existent, see F2) rust-core notices.
  - Net: `rust, java, c, cpp, c-sharp, kotlin-ng, lua, python, bash, yaml, html, css, go, ruby,
    sequel` (15 grammars) are attributed **nowhere**. Each grammar crate carries its own copyright
    holder (e.g. `tree-sitter-kotlin-ng`, `tree-sitter-sequel`, `tree-sitter-ruby`) and license.
- **Impact:** The app ships parse tables (and generated C) for 15 languages whose upstream copyright
  and license notices appear in no shipped or repo artifact — a per-grammar attribution violation.
- **Suggested fix:** Folded into the F2 generator change: since these grammars come in through the
  Rust graph, enumerating the shipping Rust closure attributes them automatically. Verify each
  grammar's license file is present in its registry checkout (some tree-sitter grammars are
  Apache-2.0, e.g. several `tree-sitter-*` repos — confirm and reproduce accordingly).
- **Fix size:** M · **Fix risk:** safe

### F4 — Mermaid bundle under-attributes its embedded third-party libraries  (P2)

- **Evidence:** grep of `Sources/ViewerUI/Resources/mermaid/mermaid.min.js`:
  - `@license DOMPurify 3.2.1 | (c) Cure53 and other contributors | Released under the Apache
    license 2.0 and Mozilla Public License 2.0` — DOMPurify is embedded (Apache-2.0/MPL-2.0, a
    **distinct copyright holder, Cure53**, with non-MIT terms).
  - Sub-library string counts in the bundle: `dagre` ×15, `cytoscape` ×15, `katex` ×11, `lodash` ×5,
    plus the d3 family — all bundled into the single minified file.
  - `THIRD_PARTY_NOTICES.md:681-705` attributes this as one entry: "Mermaid 11.4.1 … MIT … Copyright
    (c) 2014-2024 Knut Sveidqvist." The embedded DOMPurify/cytoscape/dagre/katex/lodash/d3
    copyrights and DOMPurify's Apache-2.0/MPL-2.0 terms are not reproduced.
  - **Positive sub-note:** grepped for `EPL-2/eclipse public/GPL/LGPL/elkjs` → only "Mozilla Public"
    (the DOMPurify dual-license banner). **elkjs (EPL-2.0) is NOT bundled** — the `elk` string hits
    are layout-name registrations, not the elkjs library. No copyleft-only code is present; DOMPurify
    is dual-licensed so Apache-2.0 can be elected.
- **Impact:** Because `mermaid.min.js` is shipped verbatim, its embedded libraries are redistributed;
  DOMPurify's Apache-2.0 in particular requires reproducing its license/NOTICE. Attributing only the
  top-level Mermaid package under-discloses at least DOMPurify (Cure53) and the d3/dagre/cytoscape/
  katex/lodash copyright holders.
- **Suggested fix:** Add a "Mermaid bundled dependencies" subsection reproducing DOMPurify's
  Apache-2.0 notice + the MIT/ISC/BSD notices for d3, dagre, cytoscape, katex, lodash (their license
  texts are in the `mermaid` npm package's `dist`/`node_modules` or upstream repos). Simplest robust
  path: ship Mermaid's own `THIRD_PARTY_NOTICES`/`LICENSES` if the npm tarball provides one.
- **Fix size:** M · **Fix risk:** safe

### F5 — Notices CI guard has no teeth over the Rust or transitive-JS supply chain  (P2)

- **Evidence:** `Tests/ViewerCoreTests/ThirdPartyNoticesTests.swift` — `required` is a hardcoded
  12-name list (10 SwiftPM names + "Mermaid" + "CodeMirror"). It asserts those substrings exist and
  the file is >2000 chars. It never consults `rust-core/Cargo.lock`, the highlight grammar list, or
  the mermaid bundle contents. Adding/removing a Rust crate or grammar — or the DOMPurify gap — can
  never fail this test.
- **Impact:** False-green gate. It gave the team confidence attribution was "guarded" while F2–F4
  went undetected. It also cannot catch F1 (it reads the repo file, not the bundled one).
- **Suggested fix:** (a) Drive the required-name list from the shipping Rust graph + grammar manifest
  rather than a literal list; (b) add a test that asserts the notices file exists **inside a built
  bundle** (VM/packaging tier); (c) wire `gen-third-party-notices.sh --check` into the PR gate so
  staleness is a red gate.
- **Fix size:** M · **Fix risk:** safe

### F6 — Minor version/copyright drift in Mermaid attribution  (P3)

- **Evidence:** Bundled `Sources/ViewerUI/Resources/mermaid/LICENSE` reads "Copyright (c) 2014 -
  **2022** Knut Sveidqvist"; the generator heredoc and `THIRD_PARTY_NOTICES.md:686` read "2014 -
  **2024**." `VENDOR.md` pins 11.4.1. The two copyright ranges disagree (cosmetic — both cover the
  shipped version).
- **Impact:** Cosmetic inconsistency; no legal exposure.
- **Suggested fix:** Have the generator read the bundled `mermaid/LICENSE` verbatim (like it does for
  SwiftPM checkouts) instead of an inline heredoc, so the copyright year can't drift.
- **Fix size:** S · **Fix risk:** safe

### F7 — CodeMirror attributed as one blanket MIT entry  (P3)

- **Evidence:** `THIRD_PARTY_NOTICES.md:707-733` attributes the whole `@codemirror/*` +
  `@lezer/*` + `@codemirror/legacy-modes` set as a single "MIT, © 2018-2021 Marijn Haverbeke and
  others" block. `codemirror/BUILD.md` lists ~15 distinct packs (lang-markdown, -javascript,
  -python, -json, -rust, -java, -cpp, -sql, -html, -css, -xml, -go, legacy-modes, plus the `@lezer`
  parsers).
- **Impact:** Low — all packs are genuinely MIT and the Haverbeke "and others" attribution is
  substantially accurate; some `@lezer/*` grammars carry their own copyright lines that aren't
  reproduced. This is polish, not a violation, since the CodeMirror LICENSE covers the org's packages.
- **Suggested fix:** Optionally enumerate the pinned packs from
  `scripts/codemirror-build/package.json` and reproduce each package's LICENSE, matching the rigor of
  the SwiftPM section.
- **Fix size:** S · **Fix risk:** safe

## Positive observations

- **Copyleft firewall is real and PR-blocking.** `rust-core/deny.toml` sets an explicit license
  allow-list (`MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unicode-3.0, Zlib`) with MPL-2.0 scoped as an
  exception **only** to `cbindgen` (a build tool, never linked). It is enforced by the
  `supply-chain-gate` job in `.github/workflows/pr.yml` (not just nightly), so a new GPL/LGPL/EPL/
  AGPL dependency fails the PR. Verified against `Cargo.lock`: no strong-copyleft crate is present.
- **No copyleft reaches the shipped binary.** The one MPL-2.0 mention in `mermaid.min.js` is
  DOMPurify's *dual* Apache-2.0/MPL-2.0 banner (Apache electable); elkjs/EPL-2.0 is **not** bundled.
- **No fonts are bundled** — the app uses system fonts (no `*.ttf/*.otf/*.woff*` in the tree), so
  there is no font-license obligation to satisfy.
- **Deterministic vendoring discipline** for the JS bundles: `mermaid/VENDOR.md` pins version +
  SHA-256 + a `MermaidVendorTests` SHA guard; CodeMirror is a reproducible build from a pinned
  `package.json`. This makes the *provenance* auditable even where the *attribution* is incomplete.
- **The notices generator is source-of-truth-driven for SwiftPM** (reads each checkout's real
  LICENSE/NOTICE and fails loudly on a missing one) and propagates the swift-markdown `NOTICE.txt` —
  the right pattern; it simply needs to be extended to Rust and to the transitive JS libs.
- **Exact version pinning** across `Cargo.toml` and `Package.resolved` keeps the audited license set
  stable (no floating ranges that could silently swap a license).

## Coverage gaps (not examined / could not verify statically)

- **Exact per-crate license strings for the full Rust shipping closure.** I enumerated the crates
  from `Cargo.lock` + the crate manifests but did not run `cargo tree`/`cargo about` to produce the
  authoritative shipping-only closure or read each crate's actual `LICENSE` text from the registry
  cache. The remediation for F2/F3 should generate that closure and reproduce each license verbatim;
  a couple of tree-sitter grammars may be Apache-2.0 (NOTICE-bearing) rather than MIT — confirm at
  fix time.
- **`mdv-serve` daemon (`rust-core/link/mdv-serve`, 31 MB).** If it is distributed alongside the app,
  it carries the same Rust attribution obligations as the staticlib; I did not confirm whether the
  packaging ships it. Same F2/F3 fix covers it.
- **Whether an in-app "Acknowledgements"/About license surface exists** as an alternative to a
  bundled file. I checked the file-copy path and the built bundle; I did not exhaustively grep the
  SwiftUI menu/about code for a runtime-rendered license screen (none was evident, but I did not
  prove its absence).
- **The full set of libraries embedded in `mermaid.min.js`** — I confirmed DOMPurify, cytoscape,
  dagre, katex, lodash, d3 by banner/string grep, but a minified bundle can embed more (e.g.
  `marked`, `stylis`, `dayjs`, `roughjs`) whose copyright lines were stripped by minification. A
  definitive list requires the upstream Mermaid dependency manifest.
- **Runtime/dynamically-fetched content** (e.g. any CDN or remote asset the WebViews might load) —
  out of scope for a static bundled-attribution review.
