# UI/Live-App Test Audit — Second Half (alphabetical), `Tests/ViewerUITests/`

Scope: the 51 paths from `OpenAsSniffAndHostedViewTests.swift` onward (alphabetical midpoint of 101 files). Of these, 8 are `PageObjects/*` infrastructure (not suites) and 4 are `Harness/*` (covered in the mechanism section). That leaves **39 test suites** examined against the actual harness + app-side script-runner code.

## The tiering mechanism (ground truth, not the blog version)

Before the table, the three things that actually determine a faithful tier here — because the conventional "unit / integration / UI" ladder mis-describes this repo:

**1. There is no XCUITest in this repo at all.** "Live-app" here means `AppLauncher.runScript` direct-`exec`s `dist/TextView.app/Contents/MacOS/MarkdownViewer` with `--script PATH`, the app's `ScriptRunner.runScript` drives `model.*`/`sessions.*` methods directly, dumps `DiagnosticDump.dump(window:)` JSON per step, and exits. **The assertions read a JSON view-tree projection (`model.*` + realized NSView walk), never pixels and never synthesized events.** This is the key fact: a `MultiScenarioTestCase` test is *not* exercising the AppKit event loop, hit-testing, key dispatch, or SwiftUI gesture plumbing — every suite's own header admits this ("the AppLauncher harness can't synthesise keyboard events"; "SwiftUI context menus are not introspectable from a JSON dump"). It is exercising **`DocumentModel`/`SessionsAppCoordinator` reachability through a real process boundary + real window + real launch sequence.**

**2. PNG capture is in-process `cacheDisplay`, not a WindowServer screenshot** (`DiagnosticDump.captureWindowToPNG` → `bitmapImageRepForCachingDisplay` + `cacheDisplay(in:to:)`). This is the most-misunderstood lever in the suite and it splits the "visual" tier in two:
   - `cacheDisplay` re-renders the **AppKit/SwiftUI layer tree on demand** into a bitmap — it needs **no Screen Recording permission and no foreground window**. So AppKit-drawn chrome (tab bar, mode bar, status bar, NSTextView source) *can* be faithfully rastered off-screen.
   - **WKWebView content cannot.** WebKit composites in a separate `WebContent` process whose backing store is only populated for on-screen/un-occluded windows; `cacheDisplay` snapshots the host view but the web layer comes back blank. That is the real reason `AppLauncher`'s header says "PNG snapshots come back blank" — it's a *WebView* limitation, not a generic off-screen one. The repo half-knows this (the comment blames occlusion generally) — see the candid-limits section.

**3. The bare `swift test` sweep is deliberately not the full set.** Two independent gates carve suites out of the unfiltered run, both because of **process-global corruption that test-side teardown cannot reach**, not because the tests are slow:
   - `WebViewTestTeardown.skipUnlessEnabled()` (`MDV_RUN_WEBVIEW_TESTS=1`) — in-process live-`WKWebView` hosting suites. The header documents the true root cause as an `AG::precondition_failure` in SwiftUI's **AttributeGraph** (a stale `ViewGraphRootValueUpdater` drained by a later runloop spin), with WebContent-process exhaustion as a secondary effect.
   - `MultiScenarioTestCase` / `LaunchHarness.isAppBuilt` — `XCTSkip` unless `dist/TextView.app` exists. On a host without the built bundle these silently skip; they're the VM-only set per `CLAUDE.md`.

With that, "lowest faithful tier" = the cheapest level at which the assertion's *observable* is still genuinely produced. I use: **L1 pure-logic** (value/type, no app objects) · **L2 model/coordinator** (`@MainActor` graph, no NSApplication/window) · **L3 in-process hosting** (`NSHostingView`, realized NSView tree; sub-split L3-web when a live WKWebView is minted) · **L4 launched-app JSON** (real `.app`, `--script`, JSON dump) · **L5 real-screen** (WindowServer pixels via `screencapture`).

## The genuine real-screen-only set — and exactly why

**Exactly one suite in this half is irreducibly L5: `SourceViewVisualRegressionTests`.** The reasoning, from first principles on the mechanism rather than "visual tests need a screen":

The bug it guards (SwiftUI sibling views compositing blank) is a **WindowServer-level compositor pathology** — sibling layers fail to composite *when the real window server flattens the layer tree*. The whole suite header and the `DiagnosticDump` comment converge on the load-bearing point: it must capture via `screencapture(1)` precisely *because* that goes through the WindowServer, whereas the cheaper in-process `cacheDisplay` path **re-renders each layer independently and therefore hides the bug.** So the test's fidelity depends on using the *one* capture path that the rest of the harness deliberately avoids. You cannot move it down:

- L4 (`cacheDisplay` PNG) would render the strips correctly even when the real screen shows them blank → false green. The suite literally exists to *not* be fooled by `cacheDisplay`.
- L3/L2 don't run the WindowServer compositor at all.

It is also the only suite that needs **foregrounding** (`osascript activate`) — because an occluded window has a stale framebuffer — and the only one that needs **Screen Recording TCC permission** (cross-process `screencapture` of even your own window's server-side buffer). Its many `XCTSkip` branches (no build / `MDV_SKIP_VISUAL` / no permission / tiny image) are honest about how rarely it actually executes.

The `MultiScenarioTestCase` L4 suites (`OpenInNewSessionUITests`, `SessionsKeyboardUITests`, `SessionTabBarUITests`, `ScenarioTests`) are **not** real-screen — they're "launched-app JSON," a tier whose only irreducible value is *the AppDelegate↔coordinator wiring exists in a real process*. `RenderedFindBarTests`' two view-tree tests are L3-web (live WKWebView minted in-process) but still not L5 — they assert subtree shape, not pixels.

## Over-placed suites — concrete moves

Ranked by signal-to-cost:

1. **`SessionsKeyboardUITests` + `SessionTabBarUITests` (L4 → L2).** Both assert pure `SessionsAppCoordinator` state (`dump.model.sessions`, `activeSessionID`) that `SessionTabPersistenceTests` already proves directly at L2 in-process. Their L4 cost (build the `.app`, VM-only, launch+exit per scenario, ~20-25s timeouts) buys only "the script verb is registered in `ScriptRunner`." Move the behavioral assertions to L2 coordinator tests; if you value the verb-registration smoke, keep *one* thin L4 scenario per file. The `+`-button a11y-id check in `SessionTabBarUITests` is already a no-op (soft `_ = page.newSessionButton`) and carries nothing — delete or convert to a real L3 hosting assertion.

2. **`ScenarioTests` (L4 → L2, mostly).** zoom-persists-across-toggle, mode round-trip, title-changes, folder-open — all `DocumentModel`-drivable in-process. The single thing needing a higher tier is `assertHasWebView` (a realized `WKWebView` node = L3-web). Cost: low-moderate; you'd lose process-boundary smoke that overlaps `InteractionScriptTests`.

3. **`RenderedFindBarTests` (split).** The 3 model-state tests are L2 and shouldn't sit behind the `MDV_RUN_WEBVIEW_TESTS` gate at all — pull them into an un-gated `DocumentModel` test class. Near-zero cost, and it shrinks the surface exposed to the AttributeGraph-abort gate. Keep the 2 view-tree tests gated at L3-web.

Everything else in the half is at its faithful floor. Notably the large `*RepublishInvariantTests` family (Panel/Sidebar/Tab/TrackedRepos/SessionState) **cannot** go lower than L2 — their observable is "`objectWillChange` fire count on a live `ObservableObject` graph," which doesn't exist below the model tier. They're correctly placed despite living under `ViewerUITests/` (they're there only because the types ship in `ViewerUI`).

## Candid limits / non-obvious angles

- **The "live-app" tier tests reachability + wiring, not interaction.** No suite in this half drives a real `NSEvent`, menu selector, drag, or SwiftUI gesture. `SessionsKeyboardUITests` calls itself a keyboard test but explicitly skips the key-dispatch chain; `OpenInNewSessionUITests` skips the context-menu itself. The honest gap across the whole half: **the SwiftUI control → action-method binding is never verified** — every "UI" test enters at the action method. A faithful check of that binding needs XCUITest (absent) or an `NSApp.sendAction`/responder-chain harness (only `find` uses `sendAction`, and nothing asserts on it).

- **`cacheDisplay` is an underused lever.** Because in-process raster needs no permission and no foreground, the repo *could* faithfully visual-test all **AppKit-drawn** chrome (tab/mode/status strips, NSTextView source rendering, contrast via the `contrastsWithBackground`/`color_distance` fields `DiagnosticDump` already computes) at L4 — no VM screen, no TCC. The half doesn't exploit this: visual assertions are either L1 constant pins (`SidebarSectionHeaderRecipeTests`) or the single heavyweight L5 suite. The middle ground — off-screen `cacheDisplay` snapshots of non-WebView surfaces, asserted on the existing JSON visibility fields — is the biggest unclaimed fidelity-per-dollar in this set.

- **The two skip gates are load-bearing and fragile.** `WebViewTestTeardown` documents that the real failure is SwiftUI AttributeGraph corruption surviving into a *later, unrelated* test's runloop spin — i.e. the bare-sweep green is contingent on these suites staying gated out, and any new in-process SwiftUI-hosting suite added to the un-gated sweep can re-trip the abort and silently truncate the alphabetical tail (M→Z). That's a structural hazard, not a per-test one.

- **Structural/constant pins are honest but brittle by construction.** `SearchAnywhereSectionLayoutTests` (greps source for `Divider()`) and `SidebarSectionHeaderRecipeTests` (asserts metric constants) pass on code shape, not behavior — both headers say so. They're fine as drift tripwires but should not be read as visual coverage.

- **Disciplined determinism is the norm here, worth preserving.** `SessionAutosaveTests` (`autosaveDebounce:0` + flush hooks), `WalkthroughAutoAdvanceTests` (tests the dwell helper, not the timer), `RepoFocusTrackerTests` (asserts watcher counts, never a fired FSEvent), and `TrackedReposChannelReadTests` (injectable `fileExistsProbe`) all push timing/IO-dependent features down to L1/L2 via seams instead of climbing to a flaky higher tier. This is the repo doing the right thing; the over-placed Sessions UITests are the exception, not the rule.
