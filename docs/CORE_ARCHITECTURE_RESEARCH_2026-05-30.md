## Detached-Core Editor Architectures: A Comparative Survey (read-only research, 2026-05-30)

### Landscape

Every mature editor/IDE eventually confronts the same question: where does the boundary between *editing logic/state* and *the UI that renders it* fall, and is that boundary synchronous or asynchronous? The evidence clusters sharply. On the **interactive read path** — the UI querying text/cursor/layout it is about to paint — the surviving designs (Zed, Helix, CodeMirror, Scintilla) keep the core **in-process and synchronous**, and the one prominent project that made that boundary async+detached (xi-editor) produced a public maintainer post-mortem calling it a mistake ([xi retrospective](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)). Async/RPC is near-universal — but only at **coarse, genuinely-remote or crash-prone seams**: LSP/DAP language tooling, network collaboration, remote-dev backends, plugin isolation. The JetBrains arc (IntelliJ → Gateway → Fleet) and Neovim/Kakoune show how to stretch a core across a wire when you *must*, and what it costs: optimistic-local UIs, request-id correlation, staleness/cancellation bugs, and user-visible temporary inconsistency. The cross-cutting rule that emerges: **one authority on state; views are projections; the relocatable boundary is placed coarsely and semantically (workspace/compute vs UI), never at a fine-grained per-keystroke data query.**

### The Xi async-core cautionary tale vs counter-examples

**What xi regretted** (all verbatim-verified against the 2020-06-27 retrospective):

- *"I now firmly believe that the process separation between front-end and core was not a good idea."* — and explicitly distinguished from the plugin split, which "is supportable (similar to the Language Server protocol)."
- *"Async is a complexity multiplier."* "The reality was that adding async made everything more complicated, in some cases considerably so. A particularly difficult example was dealing with word wrap." Even scrolling "took months to get it right."
- The decisive sync sentence: *"By contrast, if we just had the text available as an in-process data structure for the UI to query, it would have been quite straightforward."*
- *Why interactive ≠ request/response:* "in an interactive system... you have to display something, even when not all subqueries have completed" — async forces rendering of partial/stale intermediate state.
- *Community:* "monolithic architectures, perhaps ironically, are better for community."
- **Not a wholesale failure**: the rope and syntect-based syntax highlighting (an *async background plugin*) were cited successes — async was fine for genuinely-background, non-interactive work.

**The counter-examples don't refute the lesson — they obey it.** Neovim, tmux, VS Code-remote, Jupyter, and Figma all run async cross-boundary protocols successfully, but they (a) keep state authority in **one** place, (b) **batch** aggressively (Neovim's redraw batches to a `flush`), (c) place the seam **coarsely** (workspace vs UI; kernel vs frontend), and (d) use **optimistic-local** prediction so the user never waits (Figma "applied immediately instead of waiting for acknowledgement"; Mosh predictive local echo; Fleet "fully execute an instruction locally first"). Xi's mistake was specifically a **fine-grained, cross-process, synchronous-but-remote** layout query path — the worst of both worlds. matklad ([LSP could have been better](https://matklad.github.io/2023/10/12/lsp-could-have-been-better.html)) independently names the failure mode: fire-and-forget RPC over a fast-changing document loses causality, so clients "show stale highlighting" or "conservatively re-query... wasting the CPU."

### The macOS-native answer, and where it stops short

Apple offers **two conflated mechanisms**:

1. **NSDocument + responder-chain MVC** — the in-process answer. `NSDocument` is the model-controller ("should not contain or require... objects specific to the app's UI"); `NSWindowController` is the view-controller; commands route up the responder chain (window → windowController → document → documentController) with no explicit wiring. **Synchronous ordinary method dispatch, no IPC.** This is exactly the "functional core, imperative shell" shape and matches the owner's preference.
2. **XPC / NSXPCConnection** — the cross-process answer, for **privilege separation and crash isolation**, *not* UI-core ergonomics. Verified verbatim: "Because communication over XPC is asynchronous, all methods in the protocol must have a return type of void"; the sync proxy invokes blocks "on the calling thread before the message to the proxy returns" and is the documented **exception** Apple/DTS discourage (blocking + Mach-port DoS). *(Correction applied: the Quinn/DTS thread #736816's concrete scenario is the Mach-port-queue DoS, not a deadlock walkthrough — the deadlock framing was an overstated attribution and is downgraded to "implied.")*

**Where it stops short for web/Linux/terminal:** SwiftUI, AppKit/UIKit, NSDocument, the responder chain, and NSXPCConnection are **all Apple-OS-only** and absent from open-source Swift ([Swift Forums](https://forums.swift.org/t/swiftui-for-non-apple-platforms-like-android-web-windows/25455)). The Swift *language* runs on Linux/Windows, so a core ports **only if** kept rigorously free of Apple-only frameworks and behind portable abstractions (80–90% sharing is aspirational/secondary-sourced, dependent on Foundation coupling). **XPC has no non-Apple equivalent** — a browser/Linux/ratatui front-end cannot speak it; you would need a portable transport (socket + JSON-RPC / framed binary). So an XPC-centric core is the *least* portable choice for cross-ecosystem UIs.

### What this means for us

Our target: a reusable core (Swift today, maybe Rust later) behind a macOS SwiftUI/AppKit GUI, a browser WebUI, a macOS ratatui terminal, and a Linux terminal — with headless-on-Linux-driven-by-browser and Mac-UI-in-remote-mode visions. Owner controls both sides; **prefers synchronous, direct/functional/callback boundary; wants to avoid async contagion.**

**Where the evidence STRONGLY SUPPORTS the sync preference:**
- For the **local, in-process** front-ends (macOS GUI, in-proc terminal), every survivor agrees: synchronous in-process core + thin imperative shell is the simple, correct, testable choice (CM6, Scintilla, Zed/GPUI, Helix). Xi's post-mortem is direct primary-source vindication. You control both sides, so there is zero protocol-versioning tax for the in-proc case.
- Function-coloring (Nystrom) and "interactive systems must always have something to paint" (Levien) are the two forces that punish an async core boundary hardest — both argue for keeping the editor↔state query path sync.
- Threading guidance (corrode.dev, WyeWorks) for a possible Rust core: "prefer synchronous Rust first"; keep a sync compute core, isolate async to an I/O thread talking over channels. Avoids coloring entirely.

**Where the evidence CHALLENGES it — see `contradicts_our_lean`.** In short: the *remote* visions (headless Linux + browser; Mac UI over SSH) are precisely the regime where every system that achieved it went async-batched + optimistic-local. A purely synchronous blocking boundary stretched over SSH inherits XPC's discouraged-sync-proxy hazards (head-of-line blocking, a UI that freezes on every network round-trip). The honest framing: **sync for the in-process seam is well-supported; sync for the remote seam is contradicted by the field.**

**The reconciliation our use-case can exploit:** make the boundary a **synchronous, in-process, functional/callback API** for all local front-ends (the common case, and what the owner wants), and treat *remote* as a separate, coarse, **state-synchronization** seam (level-triggered snapshot/delta sync à la matklad/Fleet/Figma), not as "make the core API async." The core API stays sync; remoting is a transport adapter that runs the core headless and ships batched state deltas + optimistic local apply. This is exactly the discriminator the survivors landed on.

### Recommended pattern to steal — and from whom

1. **Core API shape — steal from Zed/GPUI + CodeMirror 6 + Helix:** synchronous in-process, functional/immutable core (rope/persistent text, `Transaction`/`ChangeSet`, multi-cursor `Selection`), UI accesses via direct `read()`/`update()`-style calls. Run-to-completion effect flushing (GPUI) to avoid reentrancy. This satisfies the owner's sync/callback preference and is the field's consensus for the interactive path.
2. **Don't put a process boundary on the interactive read path — steal the *anti-pattern* from Xi:** never make the UI query layout/text across a process or async boundary. That is the one design with a primary-source post-mortem against it.
3. **Place the relocatable seam coarsely — steal from VS Code-remote + Jupyter:** one core authority; a single coarse "headless core ⟷ thin client" seam for remote/web, not fine-grained per-keystroke RPC.
4. **For remote/web transport — steal from Figma + Mosh + Fleet:** authoritative core + **optimistic local apply** + reconcile; **batched, level-triggered state-sync** (snapshot + deltas), not edge-triggered RPC notifications (matklad's explicit recommendation for fast-changing docs).
5. **Plugins/LSP/language tooling — steal from LSP itself:** that's the *one* split Levien endorses; async JSON-RPC to genuinely separate, possibly crash-prone, programs is fine. Keep it off the core's hot path.
6. **Transport hygiene — steal from matklad/Tauri:** "treat the wire as a serialization format, not your data model"; define and validate everything crossing the boundary as an explicit trust boundary.
