# Rust-Core PoC — plan + starting point (2026-05-31)

> Answers "what's the plan for the PoC, where do we start." The PoC is a
> **separate track** from the pre-PoC WAVE work (`docs/research/next-priorities-2026-05-31/`).
> Locked Rust decisions live in `archive/RUST_CORE_PLAYBOOK_2026-05-30.md`,
> `archive/RUST_DEPENDENCY_AND_SIZING_2026-05-31.md`, and the memory note
> `project_rust_core_decision`.

## 1. Purpose — decide by building, not arguing

Product identity is intentionally unanswered: is `TextView` a Mac app that
*happens* to have a reusable core, or is the **core** the product and the Mac
app one front-end among several (TUI / Web / Linux)? We answer that from a
lived vertical slice, cheaply — not from a design doc.

## 2. The thesis the PoC must test

> The core owns state + logic (sans-IO, synchronous, functional). Each UI is a
> thin **projection** that sends commands and renders snapshots over a compact
> binary FFI.

If that is ergonomic + fast + maintainable for **one real feature end-to-end**,
the split is real and worth generalizing. If the FFI friction / debugging tax /
build complexity outweighs the reuse, we learn that now for the price of one
feature.

## 3. Staged vertical slice (each stage gates the next)

### Stage 0 — Toolchain spike (the riskiest plumbing, done FIRST)
- One Rust crate (`staticlib`/`cdylib`) exposing `#[unsafe(no_mangle)] extern "C"`
  (edition-2024 — the `unsafe` attribute is mandatory; see the playbook gotcha).
- `cbindgen` generates the C header.
- Integrate into the `.app`: dylib in `Contents/Frameworks/` (or an
  `.xcframework`), called from Swift through a tiny bridge; return a trivial
  value (`add(a, b)`).
- **Proves:** FFI codegen, cbindgen, SwiftPM/xcframework wiring, **signing of the
  embedded binary**, and the measured size delta against the caps (37 MB total /
  16 MB exec). Nothing else proceeds until this is green — every later stage
  rides on this plumbing.

### Stage 1 — One pure capability over the FFI
- Port a single **pure transform that already has a Swift impl** so we can A/B.
  **Recommended: CSV parse** (`CSVParser`) — self-contained, zero extra deps,
  a strong perf story, and a non-trivial structured result that exercises the
  real wire.
- Raw CSV bytes cross by **opaque handle** (never by value); parsed rows return
  over the **`rmp-serde` (MessagePack)** wire with DIY framing.
- **Proves:** the wire codec, the opaque-handle discipline, sync
  request/response, and a measurable **perf + binary-size A/B** vs the Swift
  `CSVParser`.

### Stage 2 — Stateful slice (the actual product test)
- The core owns the parsed table **and the active filter query** — i.e. *state*.
  The UI sends `setFilter(q)`; the core returns the **level-triggered**
  visible-rows snapshot. The SwiftUI side becomes a pure projection.
- **Proves:** state ownership in the core, the level-triggered push/subscription
  engine, the `CoreClient` interface, and hot-reload / idempotency. **This is the
  decision-relevant milestone** — it's the first time the UI is genuinely a
  projection over core-owned state.

### Decision gate (after Stage 2)
Judge four axes from the lived slice: **ergonomics** (FFI friction, debugging,
build loop), **performance** (the A/B numbers), **size** (against the caps), and
**maintainability** (how painful was the round-trip). That verdict answers
product identity.

## 4. Why CSV as the first slice (and the alternatives)
- **CSV** — cleanest first cut: pure, dep-free, perf-rich, has a Swift baseline,
  and naturally grows from pure (Stage 1) into stateful (Stage 2, filter state).
- **Syntax-highlight (tree-sitter)** — higher perf signal but pulls grammar deps
  and the C bridge into the PoC; better as the *second* slice once the plumbing
  is trusted.
- **Markdown → render-model** — realistic but bigger; defer.

## 5. Locked decisions feeding the PoC (already settled)
- **FFI:** hand-rolled `extern "C"` + `cbindgen`, separate isolated crate (NOT
  uniffi / swift-bridge). Doc text by **opaque handle**, never by value.
- **Wire:** `rmp-serde` (MessagePack); `postcard` dropped. DIY the framing.
- **Adopt:** tree-sitter, comrak (`default-features=false`), notify, tracing,
  serde, rustls. **Roll our own:** the reducer/state core, wire framing, RPC
  dispatch + correlation, the level-triggered push engine, error types, channels.
- **Crash reporting + telemetry = DIY.** `ropey` deferred (no GB editing in PoC).
- **Sizing:** Rust code is tiny (~0.5–3 MB); the macOS app stays ~36 MB (the
  16 MB grammars + 4.2 MB JS dominate, not the core). Full model in
  `archive/RUST_DEPENDENCY_AND_SIZING_2026-05-31.md`.
- **Still owed before real adoption:** `cargo deny` + `cargo audit` on the final
  crate set.

## 6. Relationship to the pre-PoC WAVE work
Independent track — the toolchain spike (Stage 0) **blocks nothing** and can
start any time. But the two foundations being built core-shaped in WAVE 1 —
the **session/state value type** and the **observability sink** (both designed
sans-SwiftUI, FFI-shaped) — are precisely what make the *eventual* full port
cheap: the PoC validates the FFI/wire mechanics; those foundations validate the
state *shape* that will cross it. They converge later.

## 7. Where to start THIS week
**Stage 0, the toolchain spike.** One crate, one `extern "C"` function,
cbindgen, link it into the `.app`, call it from a throwaway SwiftUI button,
measure the size delta. Green plumbing first; capability second.
