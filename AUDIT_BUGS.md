### S1

#### [S1] mdv-web has no Host/Origin validation and ignores HTTP method — DNS-rebinding turns the loopback file browser into remote arbitrary-file exfiltration
- **Subsystem:** `rust-core/crates/web` (Filesystem containment boundary)
- **Location:** `rust-core/crates/web/src/main.rs:66`
- **Kind:** security
- **Description:** `handle_conn` drains and discards every request header (the `Host` header is never inspected) and `route()` parses the HTTP method into `_method` and discards it, so POST/PUT/GET are treated identically. There is no Host-header allowlist, no Origin/Sec-Fetch check, and no CSRF token. Binding `127.0.0.1` stops other hosts on the network but NOT a browser the user is already running: a malicious page can DNS-rebind an attacker-controlled hostname to `127.0.0.1` and issue cross-origin requests to `http://127.0.0.1:8765/view?path=/Users/<user>/.ssh/id_rsa`. Because the rebind makes the response same-origin to the attacker, the file contents become fully readable to attacker JS. Combined with the missing path containment (companion finding), this is full exfiltration of any file the running user can read while the dev server is up. The module doc's "localhost-only, single user, no auth" framing defends the wrong threat model.
- **Evidence:** `handle_conn` header-drain loop (lines 67-74) reads request-header lines until a blank line and discards them; grep confirms the only `Host:` token in the crate is the test fixture. `route()` binds `let _method = parts.next().unwrap_or("")` (line 89) and never branches on it. `/view` and `/browse` read attacker-controlled `?path` verbatim with no containment.
- **Suggested fix:** Read (don't discard) the headers and reject any request whose `Host` is not exactly `127.0.0.1:<port>` or `localhost:<port>` (421/403). Reject non-GET methods (405). Optionally add an unguessable per-session token printed at startup and required on `/browse` and `/view`. At minimum document that this binary must never run while browsing untrusted sites.

### S2

#### [S2] mdv-web /view and /browse serve ANY absolute filesystem path — `root` confinement is purely cosmetic (arbitrary file read / directory listing)
- **Subsystem:** `rust-core/crates/web` (Filesystem containment boundary)
- **Location:** `rust-core/crates/web/src/main.rs:96`
- **Kind:** security
- **Description:** `root` is canonicalized once at startup and advertised in the banner ("serving {root}"), but it is used ONLY as the default landing directory. The moment a request supplies `?path=`, that value is turned into a `PathBuf`/`Path` and passed straight to `read_entries`/`read_capped` (`fs::read_dir` / `fs::File::open`) with no canonicalize and no `starts_with(root)` containment check anywhere. Absolute paths are accepted verbatim, so `/view?path=/etc/passwd` reads the file and returns its bytes, `/browse?path=/` lists the whole disk, and `../` traversal works (`pct_decode` decodes `%2e%2e%2f`). Any local process — or, combined with the missing Host check, any browser tab — that reaches the port can exfiltrate any file the process can read. This is the load-bearing precondition that makes the DNS-rebinding finding catastrophic rather than annoying, and it is the web-tier analog of the `markdownviewer://` CRIT-1 boundary.
- **Evidence:** `/browse` arm: `let dir = q.get("path").map_or_else(|| root.to_path_buf(), PathBuf::from)`; `/view` arm: `Some(p) => render_view(Path::new(p), ...)`. `root` never appears in a `starts_with`/canonicalize confinement check (grep confirms `root` used only at startup-default and display sites).
- **Suggested fix:** After decoding `?path`, canonicalize it (resolving symlinks to close the TOCTOU/symlink-escape variant) and reject (404) anything whose canonical form does not `start_with` the canonicalized `root`. Apply to BOTH `/browse` and `/view` via a single `validated_under_root(root, candidate)` chokepoint. Update the doc/banner only after the check exists.

#### [S2] URLSchemePolicy temp-dir containment uses an unanchored prefix (no path separator) — sibling-directory bypass re-opens the markdownviewer:// CRIT-1 boundary
- **Subsystem:** `Sources/ViewerCore` (Filesystem containment boundary)
- **Location:** `Sources/ViewerCore/Security/URLSchemePolicy.swift:55`
- **Kind:** security
- **Description:** `containedPath()` is the fence every `markdownviewer://` path funnels through (invokable from any local process or any web page via `<a href>`). The HOME arm is correctly anchored with `home + "/"`, but the temp arm degrades to a bare `p.hasPrefix(temp)` in addition to the correct `p == temp` / `p.hasPrefix(temp + "/")`. The inline comment claims `temp` already ends in `/` on macOS — that premise is FALSE: `FileManager.default.temporaryDirectory.standardizedFileURL.path` returns `/var/folders/<rand>/T` with no trailing slash (verified at runtime). So `hasPrefix(temp)` matches any SIBLING under the per-user darwin folder whose name merely begins with the temp dir's last component, e.g. `/var/folders/<rand>/T-attacker/loot.txt` or `/var/folders/<rand>/Tevil/secret`. That parent dir is user-writable, so a local process can mkdir a `T`-prefixed sibling and have the URL scheme open a file outside the intended HOME∪TMPDIR boundary. This is the exact sibling-prefix class the HOME arm and the test suite guard against; the temp arm is the lone regression and the misleading comment will lead the next maintainer to believe it is safe. No test covers the temp-sibling case.
- **Evidence:** Line 55: `if p == temp || p.hasPrefix(temp + "/") || p.hasPrefix(temp) {` with comment (lines 56-58) claiming temp ends in `/`. Runtime probe: `temp = /var/folders/rw/.../T` (`hasSuffix("/") == false`); `containedPath(".../T-attacker/loot.txt")` returns the URL (bypass).
- **Suggested fix:** Drop the bare `|| p.hasPrefix(temp)` arm entirely; `p == temp || p.hasPrefix(temp + "/")` is already exhaustive and correct. Fix/delete the false comment. Factor a single `isContained(_:in:)` helper shared with `MCPToolCatalog` so the two boundaries cannot drift. Add `test_tempSiblingDirectoryPrefix_rejected` mirroring the existing HOME test.

#### [S2] PTYProcess never resets childPID — terminal restart() can never re-spawn a shell (dead-terminal + child retention)
- **Subsystem:** `Sources/ViewerUI` (Process/subprocess lifecycle & reaping)
- **Location:** `Sources/ViewerUI/Terminal/PTYProcess.swift:62`
- **Kind:** leak
- **Description:** `childPID` is assigned in `start()` (line 97) and NEVER reset to its negative sentinel in either teardown path — `terminate()` and `handleEOF()` both read `childPID` into a local but leave the stored property at the old, now-dead pid. `start()` guards with `guard childPID <= 0 else { lock.unlock(); return true } // already running`. `TerminalModel` owns one `PTYProcess` and `restart()` calls `pty.terminate()` then `pty.start()` on that same instance — but because `terminate()` left `childPID > 0`, `start()` short-circuits and NEVER calls `forkpty`. So the `[process exited]` recovery view and the explicit "Restart shell" menu button silently no-op, leaving the user staring at a permanently dead pane the UI claims to have revived. The same holds after a self-exit (`handleEOF`). The model also believes a child exists (`childPID>0`) for a pid that is gone — a functional dead-feature plus a state/resource-retention bug. Reachable from both the live Restart UI and `applicationWillTerminate` teardown.
- **Evidence:** Line 36 `childPID = -1`; line 62 guard; line 97 only set site. grep confirms NO reset in `terminate()` (254-280) or `handleEOF()` (191-206). `TerminalModel.restart()` (137) does `pty.terminate()` then `start()` on the same `private let pty`.
- **Suggested fix:** Reset `childPID = -1` under the lock in BOTH `terminate()` and `handleEOF()` (alongside the existing `didExit`/`masterFD` resets) so a subsequent `start()` passes the guard and `forkpty` runs again. Add a `PTYProcess`/`TerminalModel` lifecycle test asserting `restart()` respawns.

#### [S2] CSVParser.appendToField is O(n²) per cell — field.unicodeScalars.count rescanned on every appended scalar (~2400x slower than the Rust port)
- **Subsystem:** `Sources/ViewerCore` (O(n²)/quadratic hot-path work)
- **Location:** `Sources/ViewerCore/CSVParser.swift:182`
- **Kind:** perf
- **Description:** `appendToField` checks `field.unicodeScalars.count >= limits.maxCellChars` on EVERY appended scalar. Swift's `UnicodeScalarView` is not random-access and caches no length, so `.count` walks the entire UTF-8 buffer each call — O(currentFieldLength). Building a field of N scalars is O(N²). The PARSE-04 per-cell cap (`maxCellChars = 64K`) is what makes it exploitable: the cap check IS the O(N) op and runs on the way UP to the cap, so a field growing to 64K pays ~64K²/2 ≈ 2.1e9 scalar walks. This is the default live path: `RustCSVGate` defaults OFF and `CSVParser.parse` is the fallback even when Rust is enabled. Reached by ordinary input (one long unquoted cell, embedded JSON/base64) and by the PARSE-04 degenerate "no delimiter / unterminated quote → one giant field" shape. Runs synchronously on MainActor via `CSVTableView.reparse` (`.onAppear`/`.onChange`), freezing the UI. Measured 2.35s for a 60K-char field vs 0.001s tracked — ~2169-2422x. The Rust port (`csv.rs`) already fixed this with a separately-tracked `field_chars` counter.
- **Evidence:** `CSVParser.swift:182-192`: `if field.unicodeScalars.count >= limits.maxCellChars { ... } field.unicodeScalars.append(c)`, called per scalar at lines 228/234/270. Empirically reproduced under `swiftc -O`. Rust `csv.rs:133` `let mut field_chars = 0usize; // tracked separately to avoid O(n) char counts`.
- **Suggested fix:** Track field length in a local `var fieldScalarCount = 0` incremented on append and reset alongside `field = ""` in `commitField()`, and compare against `maxCellChars` instead of calling `field.unicodeScalars.count`. Restores O(1) per scalar. Add a perf-regression test asserting a 64K cell parses well under 100ms.

#### [S2] HexView repaints ALL search matches (up to 50k) on every arrow-step through matches — main-thread stall
- **Subsystem:** `Sources/ViewerUI` (O(n²)/quadratic hot-path work)
- **Location:** `Sources/ViewerUI/HexView.swift:718`
- **Kind:** perf
- **Description:** `HighlightKey` includes `currentMatch`, so each `stepMatch` (⌘G / arrow) changes the key, forcing `applyHighlights` to `removeAttribute(.backgroundColor)` over the entire `textStorage` and re-paint EVERY match — up to `matchCap = 50,000` — even though the only visual delta is which single match is orange (active) vs yellow. Each `paint()` loops over pattern-length bytes with up to two `addAttribute` calls per byte, all on MainActor inside `updateNSViewController`. Stepping through a file with tens of thousands of matches (e.g. a 2-byte pattern in a multi-MB blob) does O(matches × patternLen) attribute writes per keypress, pinning the main thread. Correct cost is O(2): un-tint the previously-active match, tint the new one. Bounded by `matchCap` so S2 not S1.
- **Evidence:** `applyHighlights`: `storage.removeAttribute(.backgroundColor, range: full)` then `for (i, off) in matches.enumerated() { let c = (i == currentMatch) ? active : base; paint(...) }` (up to 50_000 per step). `matchCap=50_000` (line 59); `stepMatch` only mutates `currentMatch` which is in the key.
- **Suggested fix:** Split the key: when only `currentMatch` changed (same matches/clickOffsets/width), take a fast path that repaints only the old-active and new-active ranges (yellow→base on previous index, base→active on new), skipping the full `removeAttribute` + full repaint. Track `lastActiveMatchIndex` separately.

#### [S2] mdvcore_session_table clones the whole parsed Table purely to serialize it (encode_frame takes a borrow)
- **Subsystem:** `rust-core/crates/ffi` (Redundant full-dataset clones)
- **Location:** `rust-core/crates/ffi/src/lib.rs:481`
- **Kind:** perf
- **Description:** `mdvcore_session_table` deep-clones the session's entire parsed `Table` (`session.table().clone()` — every cell `String`, the `Vec<Vec<String>>`, the header) and immediately passes a reference to `encode_frame`. `encode_frame`'s signature is `encode_frame<T: Serialize>(value: &T)` — it borrows and never consumes or mutates, so the clone is dead weight: `wire::encode_frame(session.table())` produces identical output. For a multi-MB CSV this is a full redundant allocation + per-cell `String` copy of the whole dataset on the critical open path (`RustCSVAdapter.rustParse → session.table()`), on top of the unavoidable serialization copy. The Rust-side twin of the snapshot clone.

#### [S2] SEC-006 runtime ReDoS wall-clock cap in HighlightedText.ranges is structurally dead code — stop-check only runs per emitted match, never during a backtracking stall
- **Subsystem:** `Sources/ViewerKit` (ReDoS / regex match-time bounding)
- **Location:** `Sources/ViewerKit/HighlightedText.swift:75`
- **Kind:** security
- **Description:** `HighlightedText.ranges(...,mode:.regex)` is documented as a two-layer ReDoS defense: a static shape guard (SEC-004 `isLikelyCatastrophicRegex`) plus a 250ms wall-clock cap inside `enumerateMatches` (SEC-006). Both fail to bound the worst case. (1) The 250ms budget is DEAD CODE: `NSRegularExpression.enumerateMatches` invokes the closure ONLY on a match; catastrophic backtracking burns CPU inside ICU while FAILING to match, so the closure never fires and `stop.pointee = true` is never reached. Reproduced: `(.*a){26}b` vs 40 'a's ran 30+s with zero block invocations. (2) The shape guard misses obvious exponential shapes — `isLikelyCatastrophicRegex` returns false for the quantified-group-with-unbounded-body class `(.*X){N}`, multiplicative bounded quantifiers `a{1000}{1000}`, and non-capturing/doubly-nested forms `(?:a+)+` / `((a+))+`. So a pattern that hangs also slips layer one. Reachability is currently public-API only (the live SearchAnywhere caller passes `.literal`), but this is a bottom-layer (ViewerKit) API explicitly designed for reuse and self-described as a live ReDoS defense; any future caller wiring a regex find field inherits a defense that does not work.
- **Evidence:** Lines 73-83: budget check `if elapsed >= budgetNanos { stop.pointee = true }` lives INSIDE the `enumerateMatches` block. Empirically: `(.*a){26}b` -> blockCalls=0, killed at 30s (SIGALRM). `isLikelyCatastrophicRegex("(.*a){26}b")==false`, `("a{1000}{1000}")==false`, `("(?:a+)+$")==false`.
- **Suggested fix:** Don't rely on the in-block stop. Run match enumeration on a worker with a hard wall-clock deadline (background queue + `DispatchSemaphore.wait(timeout:)`) and return `[]` on overrun, or precompute a bound from input size. Broaden `isLikelyCatastrophicRegex` to reject quantified groups whose body contains an unbounded quantifier and stacked/multiplicative bounded quantifiers. Also handle named-group introducers (see companion finding).

#### [S2] FindEngine.search enumerates user/automation regex with no wall-clock deadline — the SEC-006 boundedMatches defense is bypassed on the MCP `find` path
- **Subsystem:** `Sources/ViewerCore` (ReDoS / regex match-time bounding)
- **Location:** `Sources/ViewerCore/FindEngine.swift:70`
- **Kind:** security
- **Description:** `RegexComplexityGuard`'s own docstring states `reject()` only catches exponential shapes and that match-time enumeration over user-supplied patterns "must therefore ALSO be wall-clock-bounded — see boundedMatches (SEC-006)", naming `FindEngine` as the first intended caller. `FindEngine.makeRegex()` calls `reject()` at compile time, but `FindEngine.search()` then calls `regex.enumerateMatches(...)` directly with no deadline — it never routes through `boundedMatches`. grep confirms `boundedMatches` has exactly ONE caller (`TextDisplayView.swift:1295`). A polynomial-backtracking pattern that passes `reject()` (the guard explicitly does NOT model polynomial backtracking) can peg a core. Reachable from the MCP `find` tool (`regex:true` is a directly-settable arg) against a multi-MB document, blocking the MainActor where the MCP bridge runs search. The defense exists but the highest-risk input channel is the one path that skips it.
- **Evidence:** `FindEngine.swift:70` `regex.enumerateMatches(in: text, options: [], range: fullRange)` — no deadline; `makeRegex` (157) only applies `reject()`. `RegexComplexityGuard` names `FindEngine` as the protected site. MCP chain: `MCPToolCatalog.find -> automationFind -> FindEngine().search`.
- **Suggested fix:** Route `FindEngine.search`'s enumeration through `RegexComplexityGuard.boundedMatches` (it already returns `(matches, timedOut)`); surface `timedOut` to the MCP find result. Apply the same to `ViewerKit/HighlightedText.swift:75` if it can see user patterns.

#### [S2] PARSE-03 guards the visitor but not the cmark-gfm parse stage — ~6000 nested blockquotes (~12 KB) SIGSEGVs the app on the main thread
- **Subsystem:** `Sources/ViewerCore` (Parsing & adversarial input)
- **Location:** `Sources/ViewerCore/HTMLRenderer.swift:16`
- **Kind:** bug
- **Description:** PARSE-03's depth cap (`maxDepth=512`) bounds `HTMLVisitor` recursion, but it sits DOWNSTREAM of `Document(parsing: markdown)`. cmark-gfm parses adversarial input into a tree via its own recursive descent with no effective bound for our reachable input sizes, blowing the native C stack BEFORE the visitor (and the PARSE-03 guard) runs. The crash is a hard SIGSEGV, not graceful truncation. Bisected: threshold between ~5000 and 6000 leading `>` characters — ~8-12 KB, three orders of magnitude below the 4 MB `markdownRenderMaxBytes` cap that supposedly bounds renderer input. The render runs synchronously inside the SwiftUI body (`HTMLRenderer().renderPage` at `SplitPaneView.swift:144`), so opening a crafted/corrupt markdown file instantly kills the app with no recovery. The G5 hardening test deliberately stays under cmark's parser limit, so existing coverage never exercises the real attack. The off-main render hop may use a smaller stack, lowering the threshold further.
- **Evidence:** `HTMLRenderer.swift:16` `let document = Document(parsing: markdown)` — cmark recursion unguarded by PARSE-03 (which applies only at `visit()`). Empirically reproduced: SIGSEGV (rc=139) at n=6000+, OK at n<=5000, matching the claimed threshold.
- **Suggested fix:** Bound nesting BEFORE handing input to cmark: pre-scan for run-length of leading block-nesting markers (`>`/list indentation) and reject/truncate documents whose maximal nesting exceeds a safe ceiling (a few hundred), surfacing the `LargeMarkdownPlaceholderView` path. The input-side cap is the only reliable fix since cmark's recursion is native C and uncatchable. Add a regression test feeding 10k nested `>`.

#### [S2] IndentDetector mis-parses every CRLF (Windows) file — whole file collapses to one line; A/B parity with the Rust port is silently broken
- **Subsystem:** `Sources/ViewerCore` (Parsing & adversarial input)
- **Location:** `Sources/ViewerCore/IndentDetector.swift:20`
- **Kind:** bug
- **Description:** `detect()` splits lines with `text[pos...].firstIndex(of: "\n")` over the `Character` (grapheme) view. In Swift `"\r\n"` is a SINGLE grapheme cluster, so `firstIndex(of: "\n")` never matches the LF inside a CRLF pair. On any CRLF-authored file the loop returns nil on the first iteration and treats the ENTIRE file as one line — a real 4-space CRLF source reports "—" (no indent); a CRLF file beginning with spaces reports a bogus width. This is the exact `Character`-view-collapses-CRLF trap that `CSVParser` documents avoiding by iterating `.unicodeScalars`. The value is shown to the user in `StatusBar`, so every Windows-authored file shows wrong indent metadata. Compounding: the Rust port (`indent.rs`) splits with `text.split('\n')` which does NOT collapse CRLF, so the two implementations DISAGREE on CRLF input (Rust=Spaces(4), Swift=—). The `IndentDetectABTests` corpus has ZERO CRLF cases, so the `XCTAssertEqual(rust, swift)` parity gate is dishonest — it never exercises the divergent class.
- **Evidence:** `IndentDetector.swift:20` over the `Character` view; empirically `detect("def f():\r\n    pass\r\n")=="—"` while Rust yields Spaces(4). No CRLF test anywhere (grep + green filter run).
- **Suggested fix:** Iterate `text.unicodeScalars` (as `CSVParser` does) or split on the LF scalar and strip a trailing CR per line before the whitespace/first-char tests. Add CRLF cases to both `IndentDetectorTests` and the `IndentDetectABTests` corpus. The Rust side also needs a trailing-`\r` strip so an all-whitespace CRLF line isn't miscounted.

#### [S2] EditorWriter silently drops mode/owner/xattrs when the existing file is unreadable (EACCES) — 0600→world-readable downgrade
- **Subsystem:** `Sources/ViewerCore` (File I/O & metadata preservation)
- **Location:** `Sources/ViewerCore/EditorBuffer.swift:248`
- **Kind:** bug
- **Description:** The hand-rolled temp+rename path exists to replay the original file's mode bits, owner/group, and xattrs (quarantine, ACLs) onto the replacement before rename. But the metadata snapshot is taken from `open(targetPath, O_RDONLY | O_NOFOLLOW)`. That open fails with EACCES (not ELOOP, not ENOENT) for any existing file the process can WRITE but not READ — a 0200/0600-but-ACL-denied secret, a root-owned file writable via group/ACL, a file under a read-restricting ACL. On EACCES the code only special-cases ELOOP, so it leaves `existingMeta == nil` and writes a fresh temp + rename — the saved file inherits the temp's umask mode (default 0644), the writer's uid/gid, and an EMPTY xattr set. A 0600 secret silently becomes world-readable and quarantine/ACLs are dropped — the precise harm the doc comment says the function prevents. The same bug exists verbatim in `HexBinaryWriter` (`HexEditBuffer.swift:231-249`).
- **Evidence:** `EditorBuffer.swift:248` `open(targetPath, O_RDONLY | O_NOFOLLOW)`; only ELOOP special-cased (254); EACCES falls into the "any other error: no existing metadata" block (273-275). Confirmed empirically on darwin that EACCES is returned for write-but-not-read files. `HexEditBuffer.swift` has the same shape.
- **Suggested fix:** Distinguish EACCES from ENOENT. On EACCES (exists but unreadable), recover at least mode+owner via `lstat`/`stat` for replay, or refuse the save with a recoverable error rather than silently downgrading permissions. Do NOT treat "open for read failed" as "no existing file". Mirror the fix in `HexBinaryWriter`.

#### [S2] visible_text truncation: dead placeholder code + char-vs-byte prefix confusion + O(N) removeLast trim loop, and the entire branch is untested
- **Subsystem:** `Sources/ViewerCore` (MCP visible_text/state correctness)
- **Location:** `Sources/ViewerCore/Automation/MCPToolCatalog.swift:205`
- **Kind:** quality
- **Description:** The `visible_text` truncation branch stacks three defects and has zero test coverage. (1) Dead code: `let prefix = text.prefix { _ in true }` is an always-true predicate that walks the ENTIRE multi-MB string to produce a copy immediately discarded via `_ = prefix` — pure waste on the exact large-document case the cap defends. Every test only checks `truncated:false`, so all three are unverified.
- **Evidence:** `MCPToolCatalog.swift:205-228`: dead `prefix` (215-216), `var truncated = String(text.prefix(cap))` then `while truncated.utf8.count > cap { truncated.removeLast() }`; cap = `visibleTextMaxBytes` (`AutomationHost.swift:115`); `MCPToolCatalogTests` asserts only `truncated:false`.
- **Suggested fix:** Delete the dead `prefix` placeholder. Replace char-prefix + `removeLast` with UTF-8-boundary-correct byte truncation: `text.utf8.prefix(cap)` then decode the largest valid leading UTF-8 subsequence. Add a test feeding a >cap string (ASCII and emoji straddling the boundary) asserting `truncated:true`, `totalBytes==original`, and returned `utf8.count <= cap` with no broken code points.

#### [S2] rust-core CI gate does NOT enforce the no-panic policy on mdvcore-ffi — the only unsafe crate, exactly where a panic across the C ABI is UB
- **Subsystem:** `rust-core/crates/ffi` (CI gate / build-invariant enforcement)
- **Location:** `rust-core/crates/ffi/Cargo.toml:25`
- **Kind:** test-gap
- **Description:** `rust-core-gate.sh` runs `cargo clippy` and its header claims the deny lints (`unwrap_used`/`expect_used`/`indexing_slicing`/`panic`) caught panic-capable code before it shipped. But those four are clippy RESTRICTION lints — NOT members of the all/pedantic/correctness groups — so they fire only where opted in. `mdvcore-core` opts in via the workspace lints table; the FFI crate deliberately does NOT inherit workspace lints and its local `[lints.clippy]` defines only `all=deny` + two unsafe-block lints, never re-declaring the four no-panic lints. `lib.rs`'s crate-level attributes are `#![deny(unsafe_op_in_unsafe_fn)]` + an `#![allow(...)]` block with no no-panic denies. Net: the gate's no-panic enforcement has a hole on `mdvcore-ffi` — the single crate that opts out of `forbid(unsafe_code)`, hosting every `extern "C"` shim, `catch_unwind`, MsgPack decode, and raw bounds validation. So the ~30-40 byte header is drained byte-by-byte while the buffer still holds the full (up to 16 MiB) body, copying the remaining buffer twice per byte ≈ header_len × body_len byte-copies per message, on the dedicated MCP read thread. The header loop is capped at 8 KiB so it can't run away, but per-byte O(n) rebase against a megabyte-class body makes header parsing dominate frame handling. `read(exactly:)` avoids this via bulk-append; the header path does not.
- **Evidence:** `MCPFraming.swift:217-228` `readByte` does `buffer.removeFirst()` then `buffer = Data(buffer)`; `decode()` (72-82) drives it once per header byte.
- **Suggested fix:** Scan the header without byte-by-byte consumption: search the buffered `Data` for the CRLF-CRLF terminator with a single range scan, slice out the header, and hand the body region to `read(exactly:)`. Or add an index-cursor (offset Int) to `FileHandleReader` so `readByte()` is O(1) and only compacts when the buffer is exhausted.

#### [S4] Claude index scan redacts every record solely to count surfaced events — doubles per-line work
- **Subsystem:** ViewerCore/ClaudeLogParser + ClaudeSessionIndex + ClaudeMonitor (timeline, monitor view, transcript search)
- **Location:** `Sources/ViewerCore/ClaudeSessionIndex.swift:367`
- **Kind:** perf
- **Description:** In the per-line `fold`, the index calls `ClaudeLogParser.redact(obj)` (a full recursive deep-copy of the decoded JSON object) on EVERY record just to compute `eventCount` via `parseRecord(redacted).count`. `eventCount` is a count, not surfaced text — redaction (whose only purpose is to scrub display strings) changes nothing about the number of events `parseRecord` emits (it redacts values, not block structure).
