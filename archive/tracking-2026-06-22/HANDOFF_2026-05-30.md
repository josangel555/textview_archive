## 2. ⭐ THE CORE-SPLIT / REUSABLE-CORE CONVERSATION (the hard knowledge)

> This is the multi-hour design thread the user flagged as "lots of hard knowledge between us." The full record is in **`docs/STATE_ARCHITECTURE_2026-05-30.md`** (+ 4 companions, all on branch `docs/reusable-core`). ### 2.1 The goal
One **reusable core** across **macOS SwiftUI · browser WebUI · macOS terminal (ratatui) · Linux terminal**. Concrete vision: **core headless on a Linux box, full functionality via a browser**, and/or the **same Mac UI in "remote mode" over SSH**.

### 2.2 The deciding question (UNANSWERED — gates everything)
**Is the macOS app the product (other UIs nice-to-have), or is the reusable core the product (Mac app = one client)?** Plus: are Linux+Web *committed* or aspirational? Swift-portable-core vs Rust-core? (The protocol/boundary work is needed *either way*; only compile-blockers + WASM vanish under Rust.)

### 2.3 The user's HARD PREFERENCES (do not relitigate these — they're decided by the user)
- **Sync, two-way request/response boundary.** Strongly dislikes async. "async is a complexity multiplier" (agreed, citing xi).
- **Avoid events** unless a thing genuinely cannot be done with two-way req/response.
- Uncomfortable "emitting events not knowing who/when consumed."
- req/response **does NOT mean single-threaded** — wants a **worker pool** under a sync API (concurrent requests).
- Wants to **contain async** at the boundary (Swift/Rust *can* — unlike JS contagion): spawn a task from a sync fn, deliver via callback/channel; the caller chain stays sync. Rust can avoid `async` entirely (threads + channels).
- "**Keep downstream in sync**" — only the I/O boundary is async/threaded; results re-enter the sync world via callback/state.
- **Single writer per session**; no collaborative/shared editing (deferred). **No offline editing** (non-goal). **Core connectivity is integral** — disconnect = read-only cached view.
- Owns both sides of the interface → free to design the cleanest practicable interface (not bound to a generic protocol).
- **Optimistic-local apply**: flagged as "looks like a necessity" (for remote) but NOT yet designed — the open thread.

### 2.4 What we CONVERGED on (the model)
- **Sync functional core**, accessed via direct `read()`/`update()`-style calls (à la Zed/GPUI, CodeMirror `dispatch(transaction)`). req/response shape.
- **Two query tiers:** *queries* = cheap pure snapshot reads → truly synchronous, no thread hop; *commands* = I/O/heavy → worker pool, answer via completion; UI main thread never blocks.
- **Consistency:** per-document serialization (serial queue/actor per doc) + snapshot reads (IntelliJ read/write model). Different docs run parallel.
- **Hexagonal sync PORTS** for what the core needs from the world (`read(path)`, `runProcess(argv)`, `watch(path)`, `now()`); provided by wherever the core runs (the Linux box, when remote).
- **Push channel = capability-scoped, LEVEL-TRIGGERED subscriptions** (NOT an event bus): the UI registers callbacks for *only what it can render* (LSP-`initialize`-capabilities style); the core invokes only registered+declared callbacks. **Level-triggered = the callback delivers "here is the CURRENT state of X," not "X changed by delta Y"** (matklad's rec) → robust to missed messages / reorder / reconnect. "Everything is a request from someone" — a subscription is a *standing* request.
- **Two topic kinds:** *state* topics (level-triggered, coalescing 1-slot mailbox, "holding" is ~free since core already holds truth — git status, diagnostics, disk-changed, tab set, file-changed→re-snapshot) vs *stream* topics (FIFO appends, bounded buffer + budget — terminal output, tail-follow).
- **Threading:** don't thread-per-subscription; a **bounded channel holds-until-consumed for free**. Rust `std::thread` is fine for tens (2-3 clients × few subs = trivial); the channel is the right primitive.
- **Ephemeral connection, durable in-Core session (tmux/mosh/VS-Code-Server model):** wire = a DVI cable; session lives in core. Disconnect → cached read-only. Reattach → snapshot resync + client re-applies its OWN view state. Budget expiry → hard drop; reattach = clean full snapshot.
- **Ownership split (the key):** **Core owns DOMAIN** (open docs, content, edit state, git status, tab *set*); **Client owns VIEW** (scroll, cursor/selection, focus, fold, viewport). → reconnect can't move your scroll because it never left the client.
- **Single-writer sessions, pinned to one UI, transferable** (detach A → attach B). Core hosts N *independent* sessions. Domain mutations single-writer; *incidental* writes (telemetry/recents/cache) can be concurrent. Sharing a session = out of scope.
- **Session definition:** a durable in-Core bundle of `{open documents + domain state + working context (sidebar root, git roots)}`, owned by ≤1 client.
- **Errors:** command errors ride the req/response result; subscription errors are a payload on that subscription (level-triggered: current state *becomes* `.unavailable(reason)`); add a terminal payload for "permanently dead."
- **Transport-agnostic:** in-process direct call (local) | WebSocket (remote); core/UI transport-blind. We already have the req/response half (the MCP stdio server in `ViewerCore/Automation`); **missing the subscription channel** (the boundary audit's #1 gap).

### 2.5 What we REJECTED (and why)
- ❌ async core API (complexity multiplier; coloring). ❌ fire-and-forget edge events into the void (drift, stale, wasted re-query). ❌ sync-blocking boundary over the network (= xi's mistake + Apple's discouraged sync-XPC-proxy; freezes per round-trip). ❌ process/async boundary on the interactive read path (xi post-mortem). ❌ rewriting the Mac GUI (loses native integration). ❌ XPC as the cross-ecosystem boundary (Apple-only). ❌ collaborative/shared sessions now. ❌ offline editing.

### 2.6 The research evidence (9-agent web survey — `CORE_ARCHITECTURE_RESEARCH_2026-05-30.md`)
- **In-process interactive path = synchronous** is the field consensus (Zed/GPUI, CodeMirror 6, Helix, Scintilla; macOS NSDocument too but Apple-only).
- **Xi-editor = the cautionary tale**: creator publicly called the async front-end↔core *process separation* "not a good idea," "async is a complexity multiplier"; in-process sync query "would have been quite straightforward." (Async was fine only for genuinely-background work like the highlight plugin.)
- Systems that shipped **remote UI-driving** (VS Code-remote, Neovim, Jupyter, Figma, JetBrains Gateway/Fleet, tmux/mosh) ALL obey: **(1) one state authority, (2) aggressive batching, (3) coarse semantic seam (never per-keystroke RPC), (4) optimistic-local prediction** so the UI never blocks.
- **HONEST tension (`contradicts_our_lean`):** sync is well-supported for the *in-process* seam but the *remote* seam went async-batched + optimistic-local in every shipped example. **Resolution: keep the core API sync; make remoting a SEPARATE coarse state-sync transport adapter (snapshot + deltas + optimistic-local), NOT an async core API.**
- **Steal-list:** core shape ← Zed/CM6/Helix; anti-pattern ← xi; coarse seam ← VS Code-remote/Jupyter; remote transport ← Figma/Mosh/Fleet (optimistic-local + level-triggered delta-sync); plugins/LSP ← LSP itself (the one endorsed async split); wire hygiene ← matklad/Tauri ("treat the wire as serialization, not your data model").

### 2.7 Optimistic-local apply (THE OPEN THREAD — pick up here)
Likely necessary for the remote path (keystroke-over-SSH unusable otherwise). It's *latency hiding while connected*, not offline editing. **Single-writer makes it tractable** (no multi-writer conflict). Lives in the **remote-transport adapter + a thin client predictive layer** — the local in-process path never predicts. Working assumption: it adds **reconciliation + a client-seq/version**, NOT a new event firehose (the confirm/correct rides the command's own reply; level-triggered topics deliver corrected truth). Open: which mutations predict vs await; reconcile granularity; flicker-free correction; how much domain logic the client must embed.

### 2.8 The boundary audit facts (`CORE_UI_BOUNDARY_AUDIT_2026-05-30.md`)
- `DocumentModel` (~2261 LOC, `@MainActor ObservableObject`, ~81 `@Published`) is the orchestration **caller in ViewerUI, NOT a Core type.** The real (months-long) work = **extract the orchestration state machine out of ViewerUI into a headless core**, not "move ViewerCore" (mostly clean).
- `--mcp-stdio` is **NOT actually headless** (builds `DocumentModel` + `NSApplication.run()`).
- The **#1 gap = no server→client event stream** (MCP is request/response, 10 tools, drops notifications).
- 3 Combine-coupled Core types block Linux: `SessionsCoordinator`, `LSPNavigationStore`, `LSPDiagnosticsStore`.
- Recommended interface = **Option C: one serializable Command/Query/Event protocol + an in-process Swift fast-path for the Mac UI** (maps onto a future `uniffi`/`swift-bridge` Rust FFI).
- Rendering is already web-tech (`HTMLRenderer`, Mermaid, CM6) → a browser front-end reuses more than it rebuilds.

### 2.9 The two "stop-the-world" causes (distinct fixes)
- **Main-actor blocking** → freezes. Fix: heavy work off-main. *Orthogonal* to the god object.
- **Republish amplification** → broad re-renders. Fix: fine-grained models + direct `@ObservedObject` + narrow version channels (the coordinator split + `HighlightCacheActor.version` pattern).

### 2.10 DocumentModel decomposition on-ramp
1. Keep extracting coordinators — reframe as **domain state + pure sync transition fns + contained-deferral effects**, with a *thin* `@Published` projection (not `@MainActor ObservableObject`s holding logic).
2. Introduce the Command/Query/level-triggered-subscription boundary; `DocumentModel` becomes the Swift view-model.
3. Make deferred work off-main by construction.
4. Peel presentation concerns (zoom/theme/palette/alerts/view-nonces) up into the projection.

### 2.11 Rust lose/gain (`REUSABLE_CORE_STRATEGY_2026-05-30.md`)
Don't rewrite the GUI. Move `ViewerKit`+`ViewerCore` → Rust *behind a stable boundary, incrementally*, only if Linux/Web are committed. `uniffi`/`swift-bridge` generate Swift bindings from Rust (incl. enums-with-payloads, async) — the FFI tax is real but viable. Crate parity is strong (comrak, tree-sitter, notify, rusqlite, memmap2, portable-pty, russh). The boundary + event-stream must be built *either way*.

### 2.12 Terminal integration (decided shape)
**xterm.js renderer (Mac WKWebView + browser, one renderer) + PTY in the Core over the streaming channel.** PTY runs where the core runs (local Mac or Linux box). "shell = ssh host" gives SSH-out for free. The terminal is the **cleanest first consumer of the streaming/subscription channel** — build it to prove that channel. Security: PTY-over-network = RCE by design → localhost + SSH tunnel / token + TLS.

## 4. Test discipline + how-to
- **NEVER run UI/live-app tests on host.** Host-OK: `swift build`, `swift test --filter ViewerCoreTests`, `swift test --filter ViewerKitTests`, host-safe `swift test --filter ViewerUITests.<Suite>` (pure-logic @MainActor coordinator/model suites). **Never** unfiltered `swift test` on host (sweeps VM-only suites).
- **VM:** `rsync -az --delete --exclude='.build/' --exclude='.swiftpm/' --exclude='dist/' --exclude='.git/objects/pack/' <repo>/ macOS15:markdown_viewer/` then `ssh macOS15 'cd markdown_viewer && swift test'`. Creds: host `macOS15`, `vm-tester@<vm-ip>`, sudo `<vm-sudo-password>`. Don't `git pull` on VM (rsync mirror).
- **Build + install:** `bash scripts/build-app.sh release` → `rm -rf /Applications/TextView.app && cp -R dist/TextView.app /Applications/`. Caps: **37 MB total / 18 MB exec** (`check-bundle-size.sh`; exec bumped 16→18 on `audit/pre-launch` for the audit's legit growth). Build does local `--deep` signing (do NOT switch to inside-out signing pre-Phase-9).
- **Workflows:** multi-agent orchestration via the Workflow tool was used heavily today (next-steps fanout, multi-repo, rails, large-file, boundary investigation, research, the 47-agent audit). Pattern: scope→fan-out→triage→fix(worktree-isolated)→verify; merge green branches with `git merge --no-ff`; gate with build+host tests. **Watch for worktree leak/residue** (above).
