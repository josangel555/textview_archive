## 5. RECURRING HAZARD — workflows leak their branch into the main checkout
`Workflow` agents with `isolation:'worktree'` that are told to "create branch X +
commit" have, several times this session, ended up with **X checked out in the
MAIN repo** (not their isolated worktree), AND the real work landing on a
*sibling* superset branch (`X-work`, `worktree-<runid>`). The stay-in-worktree
guard prompt reduced but did not eliminate it. **Harvest procedure that works:**
`git branch --list 'X*'` + `git log --oneline main..<each>` → the SUPERSET branch
(most commits) is the real deliverable; ff `main` to it (or rebase+ff), then
`git switch main` in the main checkout, reap all extra worktrees (`unlock →
remove --force → prune`) + delete the leaked branches. This is exactly the state
to clean up for `fix-loadbug` next session (§0).

## 6. INSTITUTIONAL KNOWLEDGE (gotchas learned this session — also appended to LESSONS.md)
1. **SwiftUI over-observation is the dominant perf trap here.** A view holding
   `@ObservedObject var model: DocumentModel` re-bodies on EVERY model republish.
   `sourceScrollState`/`sourceSelection` fire per scroll-tick/caret → the always-
   on-screen `SidebarView` re-bodied on every interaction. Fix = narrow-channel
   ObservableObjects (`SourceViewChannel`, like `FindCoordinator`/
   `PanelLayoutStore`). When something "feels laggy on every interaction," suspect
   over-broad observation first.
2. **Never do filesystem I/O in a SwiftUI `body` getter.** `discoverRoot` walked
   ~64 `fileExists` toward `/` per sidebar pass. Cache it; recompute on the actual
   triggering event only.
3. **TESTING GAP that shipped a broken build:** the headless gate (T1/T1m/T2')
   NEVER launches the app to open a file (that's T4 LiveAppTestCase, self-skips on
   host, VM-only, VM wasn't run) AND `build-app.sh` runs ZERO tests before
   install. So live-app open/render/mode regressions ship silently. FIX in flight:
   a host-runnable live-app smoke (open each file type + cycle every view mode +
   assert content) wired into `build-app.sh` as a pre-install gate. **Until that
   lands, never trust a build for live behavior just because the headless gate is
   green.** The InteractionProfileHarness opens files but does NOT assert content
   loaded — also a coverage gap.
4. **"IOSurface 70MB" was a transient compositing peak, not a leak/the cost.** An
   early single heap-dump moment over-stated memory; re-measured base=36MB,
   2-source=84MB; the per-window cost is the SwiftUI/AppKit heap, ~same with/
   without a WebView. Don't over-index on one heap-dump instant — corroborate.
5. **GeometryReader that drives layout + writes `@State` it then re-reads = a
   per-frame layout-pass multiplier** (live-only; a one-pass headless harness
   can't see it). Use a non-layout-driving `.background(GeometryReader)` and
   epsilon-guard `@State` height writes.
6. **macOS-26 known red (allowed in the gate):** `MarkdownLinkPolicyTests.
   test_decide_sameDocFragment_isAllowed` (Foundation URL-fragment parser
   regression) — green on the macOS-15 VM/CI, red on host. The ONLY acceptable
   gate failure.
7. **Native profiling cheat-sheet:** `footprint`/`vmmap --summary` (real RSS, task
   access works on the local-dev-signed build); `heap <pid>` ("what's in memory"
   by class); `sample`→`scripts/lib/sample_flamegraph.py` (flame graph). All in
   `docs/MEMORY_AND_CPU_ACCOUNTING_2026-06-01.md` + `docs/PERFORMANCE_PROFILING.md`
   + the `mem-profile` skill (`.claude/skills/mem-profile/` — gitignored,
   local-only).
